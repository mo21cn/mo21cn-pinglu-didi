# 代码审查规范

> 代码审查（Code Review）集成在 Git 工作流中：所有合入 `develop` / `main` 的改动必须经过 Pull Request + 审查 + CI 通过。本文档定义审查的流程、标准与红线。

## 1. 审查流程

```
feature/* 分支开发完成
    → 推送并创建 Pull Request（目标 develop）
    → 自动触发 CI（lint / test）
    → 指定审查人（CODEOWNERS 自动指派）
    → 审查人 Review（提出意见 / Request changes）
    → 作者修订 → 复审通过 → Squash merge 到 develop
```

| 阶段 | 要求 |
|------|------|
| 提交 PR | 填写 PR 模板（关联需求、测试说明、自查清单） |
| CI 门禁 | 必须通过（否则不可合并） |
| 审查 | develop 需 ≥1 人 approve；main 需 ≥2 人 approve |
| 合并 | 通过后由作者 Squash merge，删除功能分支 |

## 2. 审查者职责

- 审查**正确性**：逻辑是否符合需求、边界条件是否覆盖。
- 审查**安全**：是否泄露敏感信息、是否有越权/注入风险。
- 审查**红线**：是否违反三条工程底线（见第 5 节）。
- 审查**规范**：命名、结构、注释、是否遵循提交规范。

## 3. 审查清单（Checklist）

### 功能正确性
- [ ] 与需求（F 编号）一致，无遗漏验收点
- [ ] 边界条件、异常路径已处理
- [ ] 有对应单元测试，关键逻辑有覆盖

### 安全与合规
- [ ] 无硬编码密钥 / 密码 / token
- [ ] 敏感数据已加密 / 脱敏
- [ ] 输入校验完整，无注入风险

### 性能与一致性
- [ ] 撮合 / 下单链路符合 P99 指标
- [ ] 泊位预约 / 过闸计划有防超卖约束（锁 + 唯一约束）
- [ ] 数据库查询有索引、无非必要全表扫描

### 工程规范
- [ ] 通过 lint / format / type-check
- [ ] 提交信息符合 Conventional Commits
- [ ] 文档已同步更新

## 4. 审查关注重点（按模块）

| 模块 | 审查重点 |
|------|---------|
| `match` | 撮合约束正确性、评分权重、P99 性能、可解释性 |
| `payment` | 分账金额精度、幂等、对账、资金留痕 |
| `agent` | **无直写**、审计留痕、降级开关、知识库隔离 |
| `cargo/ship/port` | 领域模型、稀缺资源防超卖、状态机 |

## 5. 三条工程红线（一票否决）

1. **确定性内核不经 LLM**：撮合排序、支付分账、防超卖、订单状态机不得引入大模型。
2. **Agent 无直写**：智能体写操作必须经业务领域 API，禁止直连数据库。
3. **交易全链路留痕**：实名、留痕、复核三标配，关键触点可审计。

> 违反任一红线，审查必须 `Request changes`，不得放行。

## 6. 审查时效

| 类型 | 目标时效 |
|------|---------|
| 常规 PR | 1 个工作日内完成首轮审查 |
| 紧急 hotfix | 2 小时内响应 |
| 核心模块（match/payment/agent） | 须专项审查，可跨团队复核 |
