# 汇报演示脚本与答辩口径

> 适用版本：**v0.5.0**（UI V2 全量改版 + 交易三级页闭环 + Agent 领域覆盖 5/5）
> 定位：**原型可用**。五核心域（货 / 船 / 港 / 撮合 / 交易）+ Agent 领域覆盖 **5/5** + 1 个 RAG 检索层全部打通，前端为演示级完成度。
> 本文是汇报当天的操作手册：先照第 1 节把环境跑起来，再按第 2 节顺序演示，第 3–5 节是答辩备用弹药。

## 1. 演示前置（约 3 分钟）

### 1.1 启动后端

```bash
cd backend
uvicorn app.main:app --reload
```

**不需要任何环境变量前缀**：入库的 `backend/.env.development` 已内置 `WECHAT_MOCK=true`（无 appid 也能登录）与 `LLM_MOCK=true`（智能体走内置规则模板）——**clone 后直接启动即得完整演示态**，零 Key、零网络依赖。若想显式覆盖，`LLM_MOCK=true WECHAT_MOCK=true uvicorn app.main:app --reload` 效果完全相同。
（`--reload` 仅在代码变更时有用；若环境不支持热重载，去掉该参数即可。首次启动会自动创建 SQLite 表。）

**为什么建议 `LLM_MOCK=true`**：模板模式能保证合同文字逐次一致、可复现。合同 Agent 现已具备降级（TODO-10 已闭环）——LLM 故障时接口仍返回 200，补充条款回退平台内置标准条款并在页面上标注「已降级」，外网抖动不会让演示翻车，只是文字换成内置模板版。
`LLM_MOCK=true` 下 Mock 输出与真实模式**同构**（同样的 JSON 结构、同样的风险条目），演示效果一致但零网络依赖。
如需展示"真实大模型"，再切回真实 Key，并优先演示客服对话（容错更好）。

```bash
#                    macOS/Linux 用 .venv/bin/python scripts/seed_demo.py
```

脚本幂等：实体按自然键复用，**重复执行不会产生重复数据**。输出末尾会打印演示锚点（订单/泊位/预约 ID），先抄下来备用。

### 1.2b 铺智能合同仿真案例（可选 · 检查合同风险引擎用）

```bash
cd backend
python scripts/seed_contract_cases.py
# 未激活虚拟环境时同上，用 .venv 内的 python 显式执行
```

`seed_demo.py` 铺的是交易主链路锚点；本脚本独立铺「合同风险引擎」样本，两者关注点不同、可分别重跑。
订单归属 `seed-shipper`、承运船归属 `seed-owner`，**两个角色在「订单」页都能看到同一批案例**，点卡片「查看合同」即可进入合同预览三级页。

| 订单（以脚本实际输出为准） | 点「查看合同」应看到 |
|---|---|
| `#7` 已完成 | 无风险（干净合同） |
| `#11` 待支付 | R1 运费未支付（高） |
| `#10` 面议 | R1 未支付 + R2 运费未锁定（高） |
| `#12` R3 | R1 + **R3 装货日期临近（中）** + R8 违约金标准未量化（低） |
| `#13` R4 | R1 + **R4 船舶证书临期（中）** + R6 滞期费未约定 + R7 货物保险未约定 |
| `#14` R5 | R1 + **R5 液货/危险品运输（中）** + R6 + R7 |
| `#15` R9 | R1 + **R9 在途不可抗力风险（低）** |

规则分两类，答辩时可直接区分：**订单事实类** R1 未支付 / R2 运价未锁定 / R3 装货日期临近 / R4 证书临期 / R5 液货危险品；**商务条款类** R6 滞期费未约定 / R7 货物保险未约定 / R8 违约金标准未量化 / R9 在途不可抗力 —— 后四条对齐开发计划的验收口径「风险点识别覆盖 **滞期费 / 不可抗力 / 违约金 / 保险**」。

R6–R9 只在订单处于 `matched` / `shipped` 时评估：**已签收/已撤销的订单不再提示条款完备性**，所以 `#7 已完成` 能稳定呈现为「干净合同」，不被噪音污染。R7 的触发口径是「高货值货类（集装箱/液货）**或** 运费 ≥ 3 万」，不是所有订单都提示。

R3 / R4 能正常成单的原因：撮合的**硬约束只要求「船舶证书覆盖装货日」**，证书余量与装货日窗口不是硬约束而是**合同风险引擎（`contract.check_risks`）的规则**，所以「临期但未过期」的样本可以正常出单、再由风险引擎命中——这正是「确定性内核产事实、规则引擎判风险、LLM 只写标准条款」三层分工的体现，答辩时可直接作为口径。

边界：已撤单订单后端拒绝生成合同（`订单已撤销，无法生成合同` → 400），故页面不显示「查看合同」，也不铺撤单样本。

### 1.3 小程序侧

微信开发者工具导入 `miniapp/`，**开箱即用，无需配置身份**：开发期点「货主」自动登录演示账号 `seed-shipper`、点「船东」自动登录 `seed-owner`（映射见 `miniapp/utils/auth.js` 的 `DEV_ROLE_CODE`）。

演示数据全部挂在 `seed-shipper` / `seed-owner` 名下，所以身份**必须**落在有数据的账号上——用别的 code 登录会当场注册出空账号，订单页不报错但列表全空，很容易误判成功能故障。

需要其它身份时，再在 Storage 面板设 `dev_login_code`（优先级最高）：

- `seed-port` → 港口方（**内部运营台专用**；C 端身份选择已下线该身份，仅直连后端接口时使用）

后端地址在 `miniapp/utils/request.js` 的 `BASE_URL`（默认 `http://127.0.0.1:8000`）。

**域名校验已默认关闭，开箱即用**：入库的 `miniapp/project.config.json` 中 `"urlCheck": false`（第 8 行），clone 后不需要任何手动设置。若本地设置把它覆盖回了 `true`，去 **详情 → 本地设置 → 勾选「不校验合法域名、web-view（业务域名）、TLS 版本以及 HTTPS 证书」**即可。

> 历史备注（已修复）：此前"小程序端走查不通过"的根因就是这个开关 —— 请求 `http://127.0.0.1:8000` 被安全域名校验拦掉，而页面把失败吞成了空列表 / 网络异常提示。现公共配置已固定为关闭。

**可能需要自带一份私有配置**：`miniapp/project.private.config.json` **已被 `.gitignore` 忽略**（官方推荐做法：公共配置进 `project.config.json`，个人 / 开发期配置进私有文件），它携带 `appid: "touristappid"`（游客态，**无需真 appid 即可用工具打开项目**——公共配置里的 appid 是占位符 `wxYOUR_APPID_HERE`）。换机器后若工具提示 appid 无效，按下面内容建一份：

```json
{
  "appid": "touristappid",
  "projectname": "pinglu-didi",
  "setting": { "urlCheck": false }
}
```

真机演示需把 `BASE_URL` 改为局域网 IP（真机同样不校验域名，但手机与电脑要在同一网段）。

## 2. 演示路径（约 12 分钟）

按顺序走，每条都标了"这一步要讲什么"。

### ① 首页身份选择 → 货主

双身份浮窗（货主 / 船东），一键以货主身份进入工作台。
**讲**：货主与船东共用一套账号体系，JWT 里带 `role`，切换角色换的是 token 而不是账号——所以同一个人可以既是货主也是船东。港口方是**内部运营角色**，不在 C 端暴露（运营台入口见第 ⑨ 步）。

### ② 货主找船页（02）

**讲**：顶栏三个入口各有分工——**搜索**进「智能搜索」（一句话描述，系统自动判别你想干什么，结果按意图渲染成卡片或回答）、**✨Ai** 直达「智能填写」解析态、**客服**进平台问答。顶栏左上角是**用户头像 + 用户 ID**（矢量人物头像占位，点击进「我的」），旁边 `📍南宁 · 平塘港` 是常用港（可切换，撮合评分会用到船籍港就近）。下方「我要发货」是货主唯一的主操作，其余是推荐位（推荐船源与推荐航线目前是演示数据，见第 5 节）。

点**搜索**可以先讲统一入口：`POST /agent/route` 把三个 Agent 收成一个门，意图优先级是 **合同 > 合规 > 货源解析 > 客服（长尾兜底）**。**注意它不是弹窗**——用的是和「客服」完全相同的对话页外壳，所以长句不会被挤断，结果还能是结构化卡片。例如输入「帮我发一批货」→ 判为货源解析（直接出 7 字段解析卡，可一键带去发布页）；输入「甲醇能不能运」→ 判为合规（出合规卡，逐条列阻断/提示与建议）；输入「合同有哪些风险」→ 判为合同；输入「怎么注册」→ 落到客服兜底。每条回答上都会标注「已识别：XX · 置信度」，路由是产品能力，要让人看得见。

一个好演示的边界：**以船东身份**输入「我要发一批 500 吨水泥」，系统**不派发**，而是回一句「需要货主身份」并给出切换按钮——因为货源解析只对货主开放。这体现的是「**Agent 无直写 + 权限前置**」，不是失败。

### ③ 发布货物（04）→ 先选发货方式 → 试一次"一句话发货" + 合规预检

**进页第一步：发货方式选择弹窗**（点底部 tabBar **中间凸起的「+发货」**进入本页，即自动弹出）。
两张横向渐变卡片 —— **自主发货**（橙）与 **委托发货**（蓝），右侧是设计稿上的「默认」标记（**纯展示，不可点**）。

| 操作 | 结果 |
|---|---|
| 点 **自主发货** | 弹窗关闭，留在本页自行填写发布（**正常演示走这条**） |
| 点 **委托发货** | 进通用占位页 `pages/preview/preview`，居中一行小灰字「功能预览，即将开放」 |
| 点弹窗外**遮罩** | 等同自主发货，留在本页；再点一次「+发货」可重新唤起 |

**讲**：这是**纯前端交互、零接口调用**（弹窗与占位页都不发请求），版本号仍停在 v0.5.0。
「委托发货」（平台承运、由平台组织运力）本轮未开放，我们**不铺假页面**、直接明说"即将开放"——
占位页做成了通用件，后续其它未开放功能直接复用，不用一页页重画。

> ⚠️ 别踩的坑：船东角色下同一个凸起位是「**+发布空船**」，进的是发布空船页，**不会**弹这个窗。
> 两个角色共用一套 tabBar 但映射不同，属于预期行为，不是 bug。

**进入表单后**再演示"一句话发货"，两种方式都可以：顶栏 **✨Ai** 进「智能填写」解析态，或直接在本页点「✨ 智能填写货源」。

输入一句自然语言，例如「下周三从南宁运 1200 吨水泥熟料到贵港，运费 4 万 8」。
**讲**：这是**货源解析 Agent**。它把口语抽成结构化草稿并回填表单——注意三个细节：
1. 解析结果先以**卡片**呈现（逐字段列出识别值，港口已换成中文名，空字段标「未识别」），点「带去发布页填写」才回填；
2. 回填后表单里出现高亮的待确认字段，说明模型对某些字段没把握，**交由人确认**；
3. Agent **不直接写库**，只产草稿（落在本机 `cargo_draft_v1`），真正的写入是走 `POST /cargo/shipments` 业务接口 —— 这是我们的三条工程底线之一（**Agent 无直写**）。

**顺带演示 F17 合规初筛**：表单填好（或回填完）后点「发布前合规预检」。这是**纯确定性规则引擎，零 LLM**——查禁运/管制品、危险货申报资质、集装箱航线适配、装货日期是否过近或已过。它**只出结论、不阻断写入**（发布权仍在人手里），分三档：通过 / 有提示 / 未通过。
- 想演示「未通过」：货源名里带「烟花爆竹」或「甲醇」等管制词 → 阻断级结论；
- 想演示「有提示」：装货日期填明天 → 提示装货窗口过近。

发布空船页（05）同样有一个「🛡 船舶合规预检」，查证书过期/临期、主尺度比例异常、吃水需核实、船籍港缺失——同样是零 LLM 的规则引擎。

### ④ 智能找船（撮合页）

**讲**：这是全场景最硬的一块，用三个数字讲：
- 头卡「确定性内核 · 零 LLM」：撮合**不经大模型**，是纯函数引擎，同样输入必然同样输出，可复现、可回归测试；
- 四项评分条 `40 / 20 / 20 / 20`：载重利用率 40 + 船型适配 20 + 船籍港就近 20 + 证书余量 20，凑成 0–100；
- 下方「未入局候选」：被硬约束刷掉的船**不会静默消失**，会带原因计数返回 —— 演示可信度的关键。

### ⑤ 下单 → 订单页（06）

选中最优船源下单。订单页顶部是自绘导航（标题「我的订单」，**右侧刻意留空**），下面是统计行、待办卡、订单列表。
**讲**：货源至多只能有一个生效订单，下单时对货源行加锁做并发保护——**防重复出单**，和后面港口的防超卖是同一套思路。
**顺带一提**：这一页是 `navigationStyle:custom`（自绘导航），顶部内边距必须显式取 `wx.getWindowInfo().statusBarHeight`，否则统计行会顶到状态栏、被右上角胶囊压住——这是自绘导航最常见的一个坑。右侧不放消息铃铛也是同一个原因：**微信胶囊常驻右上角（约 562~736rpx）**，在那儿放控件就是「看不见的假入口」。

### ⑥ 查看合同（三级页 ★ Agent 亮点）

点订单卡「查看合同」进三级页（长按可快速弹层预览）。

**讲**（这是 Agent 架构的主展示面）：
- 头卡标明「核心条款零 LLM」：**金额、船名、港口、日期都来自订单数据字段，不是模型编的**；模型只负责生成叙述性条款；
- 风险卡按 `high → medium → low` 排序：合同 Agent 会做**风险点提示**，已撤销订单会被拦下并返回 400；
- 底栏 PDF / 签署是**占位**：本轮不落库、不签署，措辞用的是"合同预览"。
- **这里可以主动交代**：权威留痕（`contracts` 表 + 版本快照）是下一版任务，原型阶段刻意不做，避免出现"看起来签了其实没签"的假象。

### ⑦ 去支付（三级页）

**讲**：一张单据的**完整资金留痕**。金额在创建支付单时锁定，此后订单字段变化不影响本单金额。时间轴展示 创建锁价 → 支付成功 → 退款/关闭。
点「模拟支付成功」（联调期以 Mock 回调替代微信支付）。

### ⑧ 撤单 → 退款联动

回到订单页撤单，再进支付详情。
**讲**：**退款不开放独立端点**，只能由撤单联动触发。这样做是为了让"资金流"和"订单流"只有一条状态机说话，避免两边各说各话。用演示数据里的 `#9 已退款` 订单可以一眼看到联动结果（订单 cancelled / 支付单 refunded）。

### ⑨ 切换角色 → 船东（撮合的另一侧）→ 港口方运营台（内部）

**先切船东**（「我的」页切换角色，或首页身份卡）：进「我的船队」，点 **`桂平航 6688`**（散货船 · 1500 载重吨 · 已认证）上的「智能找货」。

**讲**：同一个撮合引擎的反向视角——硬约束从"这条船能不能装这批货"变成"这批货喂不喂得饱这条船"。当前有 3 条货源进局，按综合评分降序排列（`100 / 92 / 86.67`）；下方「未入局候选」同样带原因计数（`cargo_not_published: 7`，表示 7 条未发布货源压根没进池子，而不是被静默过滤掉）。

**可以主动交代一句**：船队里另一条 `横州集运 101`（900 载重吨集装箱船）算出来是 **0 候选**——这是硬约束的**正确结果**而不是缺陷：当前演示货源都是 1000 吨以上的散货，既超它的载重吨、船型也不兼容。（若被问"为什么这条船点进去没结果"，这就是标准答案。）

**再进港口方运营台**：「港口」页 →「港口服务 / 业务办理」→ 预约审核 / 泊位管理 / 新建泊位。

⚠️ 港口方身份已从 C 端下线，此时页面会提示「运营台为港口方内部功能，暂未对外开放」。要演示这一段，用 Storage 面板把 `dev_login_code` 设为 `seed-port` 后重新登录（或在「我的」页退出后重进），即可作为内部账号进入运营台。

### ⑩ 泊位管理 → 点 DEMO-01 → 档期详情

**讲**：甘特条把"已确认占用"摊开，徽章显示**峰值 2 / 2 船位**（已打满）——因为 #5 和 #6 两个窗口在时间上重叠，正好占满并发容量。
下半页是「预约前置校验链」四条硬约束：船舶已审核 / 载重吨咬合 / 吃水校验 / 适靠船型。这四条在**船东提交申请的瞬间**逐条比对，不满足直接 409，连队列都进不去。

## 4. 预期提问与口径

**Q：撮合为什么不用大模型？**
A：撮合要可复现、可回归、可审计。同样的输入必须给出同样的排序，否则甲方无法验收、我们也无法定位"为什么这单没匹配上"。所以我们把撮合做成确定性内核，大模型只用在不要求确定性的地方（语言理解、文本生成）。

**Q：Agent 会不会乱写数据？**
A：不会。架构上 Agent 拿不到写权限，它产出的是草稿/建议，落库必须走业务领域 API 的事务，可回滚、可审计。这是硬约束，不是约定。

**Q：支付这块能用真实微信支付吗？**
A：渠道已抽象（`channel=mock` / `wechat_mp`），换真实支付要补三件事：`prepay_id` 下单、回调验签、船东提现分账。当前是联调通道，界面口径也是"模拟支付"。

**Q：合同的风险点和"合规预检"是大模型判断的吗？**
A：不是。两个都是**确定性规则引擎**，大模型一个字都不参与判断。合同风险是 `contract.check_risks` 的 R1–R9（订单事实类 + 商务条款类），合规初筛是 `compliance.py` 的 9 条规则（货源侧禁运品/资质/航线/日期，船舶侧证书/主尺度/吃水/船籍港）。口径是「**确定性内核产事实 → 规则引擎判风险 → LLM 只写标准条款**」三层分工：LLM 只负责把已经判定好的事实写成通顺的条款文字，它既不能决定风险是什么，也不能引入数字——所以同一单每次生成的风险点完全一致，可回归测试。

**Q：合同有没有法律效力？**
A：当前是**合同预览**，不落库、不签署。要形成有效留痕需要 `contracts` 表 + 版本快照 + 签署存证，这是下一版明确任务，我们不在原型阶段假装做到了。

**Q：数据是真实的吗？**
A：业务链路是真实的（真实接口、真实状态机、真实并发保护）。三个地方是演示数据，我们主动标注：① 货源大厅的推荐位；② 港口页的 4 组服务入口（港航/船闸/航道，占位）；③ 我的页面的会员卡与资产行。港口的泊位与预约是真实数据，`DEMO-` 前缀是演示专用泊位。

**Q：并发下会不会超卖？**
A：演示给你看过了——第 ⑪ 步那个 409 就是并发保护的结果。生产环境（MySQL）确认时对泊位行加 `FOR UPDATE` 行锁，把同泊位的确认串行化；开发/测试用 SQLite 单连接天然串行。

> **这四条已在 CI 中自动执行**（`.github/workflows/ci.yml` 的 `frontend-static` 与 `frontend-e2e` 两个 job），
> 改前端 push / 开 PR 即触发，不必只靠本机手工跑。

> 涉及 UI 改动时请在本机手动跑一次。
>
> 数字口径：`verify_frontend_e2e` 在数据充足的库上是 **176**，在**空库 + seed** 的干净环境（CI 首跑 / 甲方 clone）是
> **155** —— 差额是「库内没有对应样本就自动跳过」的条件断言，两种情况下都应为 **FAIL 0**。
