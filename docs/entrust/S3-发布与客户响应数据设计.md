## 1. 裁定三给出的口径（逐条登记）

| 项 | 裁定 |
| --- | --- |
| A：客户身份 | **客户 = 当前委托的货主本人**，复用现有账号与 `owner_user_id`；**不新增全局 `customer` 角色** |
| A：客户入口 | 扩展现有「我的委托／委托详情」，加入「待确认报价、合同、响应记录」 |
| A：权限 | **组织经理权限不能代替客户确认权限**；按**具体委托归属**判断，不只看全局角色 |
| B：发布版本 | 增加**独立的发布记录**，绑定**精确成果 revision**，并保存**当时的客户白名单快照** |
| B：客户响应 | 绑定发布记录，记录接受／拒绝、**客户身份**、时间；**幂等且事务内处理并发** |
| B：后续修改 | 内部编辑产生新版本，**不改已发布快照**；新版本重新发布后，旧待响应版本**不得继续接受** |
| 冻结细节 ① | **新建内部草稿不等于自动撤销旧报价** —— 只有显式重新发布／撤回才改变旧报价的可响应状态 |
| 冻结细节 ② | **已接受的旧版本永久保留**；后续变更需要新的客户确认，不能覆盖此前的接受事实 |
| 客户下载 | 必须**限定到该发布记录明确授权的文件**，不能因为客户属于同一委托授权就把内部供应商报价和其他附件全部开放 |
| 航段 | 需要**最小结构化航段对象**（稳定 ID、所属委托、运输方式、起终点、顺序），任务与候选运力引用对应航段；**不建通用路线图或优化引擎** |

| 表 | 一句话 | 它挡住的错误形态 |

| `ent_offer_release` | 对客发布记录（精确 revision + 白名单快照 + 授权附件 + 三态） | 「发布后按现在的规则重算」⇒ 客户已看到的内容被悄悄改掉；「有更新的记录」被当成"旧报价已撤回" |
| `ent_offer_response` | 客户响应（`UNIQUE(release_id)`） | 「先查后写」在并发下必然漏 ⇒ 同一次发布被响应两次 |

### 2.1 为什么发布记录要存**快照**而不是只存 revision

发布记录存了 `snapshot_json`（发布那一刻的**客户白名单投影**结果）。理由：

- 客户是照着**当时看到的那份内容**做决定的。若发布后按"现在的投影规则"重算，
  改一次内部字段归属就可能悄悄改变客户已看到的内容 —— 而记录上还写着"同一个版本"。
- 合同 §3.2 明确要求区分「**read-only preview**」与「**completed business action**」，
  以及「model proposal」与「authorized business execution」；快照是让"客户看到的"
  这个事实**可回溯**的最小手段。

### 2.2 为什么 `status` 是显式三态，而不是"取最新一条"

裁定三冻结了两条语义，它们都**不能**从"有没有更新的记录"推出来：

- **新建内部草稿 ≠ 撤销旧报价** ⇒ 不能因为有人开了新草稿就把旧发布标成失效；
- **已接受的旧版本永久保留** ⇒ 旧发布被"取代"后仍然要能被读出来（连同它的响应）。

所以 `released → withdrawn / superseded` 必须由**显式动作**写下来，并留 `closed_by` /
`closed_at` / `close_reason`。**由推断得出的状态是不能审计的。**

### 2.3 「同一发布只能被响应一次」为什么必须落在**唯一约束**上

裁定三原话是"幂等且事务内处理并发"。应用层"先查有没有响应、没有再插"在并发下
两个请求可以同时通过检查 —— 于是同一次发布被接受两次，而两次都"看起来"合法。
`UNIQUE (release_id)` 是数据库层面的事实判据；应用层再叠加幂等键（`ent_idempotency`）
负责"同键重放返回同一结果"。

### 2.4 客户身份的落法

`customer_user_id` 存的是**委托的货主本人**，而**不是**一个新角色：

- 判权时按**该委托的归属**判（`ent_assignment.owner_user_id == 调用者`），
  **不**依据全局角色 —— 裁定三明确"组织经理权限本身不能代替客户确认权限"；
- 这意味着**同一个账号**在卖家侧（组织经理）与买家侧（货主）看到的入口与能力不同，
  而这正是"按具体委托归属判断"的意思。

## 5. 下一条交付：**发布 → 冻结内容 → 客户响应** 纵向切片（切口冻结）

> HO 0917-3 执行顺序原文：*「下一条完整交付应是：经理发布指定版本 → 货主查看冻结内容 →
> 接受／拒绝 → 经理看到响应。权限、失效版本、重复请求和并发处理随这条业务一起完成。」*
> 本节把这句拆成**可逐条验收的出口**，并按"业务结果"而不是"建表/按钮"来写。

### 5.1 出口（按顺序，每一步都要有可运行结果）

| # | 出口（可运行的业务结果） | 判据（正向） | 判据（负例，与正例同等重要） |
| --- | --- | --- | --- |
| 1 | **经理发布指定版本** | 指定 `artifact_id` + `revision_no` ⇒ 新增一条发布记录：`status=released`、绑定**精确 revision**、`snapshot_json` = 发布那一刻的**客户白名单投影**结果、`customer_user_id` = 该委托货主 | 无权者（非组织成员 / 无 `quote:publish`）⇒ 404/403；对**不存在的 revision** ⇒ 400（不得"取最新"）；对**已作废（void）**的 revision ⇒ 400 |
| 2 | **货主查看冻结内容** | 货主在「我的委托／委托详情」看到该发布：**内容是 snapshot**（不是按现在的投影规则重算）；内部成本/会话/未授权附件**不在**其中 | 非该委托货主（含**同组织的经理**）⇒ 404；未发布的草稿 ⇒ 不可见；**下载**只放行该发布记录明确授权的文件 |
| 3 | **客户接受／拒绝** | 一次性写入响应：`accept`/`reject` + 客户身份 + 时间 + 目标 revision ⇒ 经理侧立即可见 | **经理冒充客户** ⇒ 403（组织权限不能代替客户确认权限）；对**未发布**或**已被取代/撤回**的版本响应 ⇒ 409；**同一发布重复响应** ⇒ 幂等键同键返回首次结果、**不同键**被 `UNIQUE(release_id)` 挡住（409） |
| 4 | **经理看到响应** | 发布记录上能看到响应方、结论、时间与**精确版本** | 响应不得改写已发布快照（改内容 ⇒ 只能产生**新 revision + 新发布**） |
| 5 | **失效语义**（裁定三冻结细节） | 显式 `withdrawn`（撤回）改变可响应状态 | **新建内部草稿不改变**旧发布的可响应状态；已接受的旧版本**永久保留**（连同响应） |

### 5.2 实现面（只列"必须新增"的部分）

- **命令 + 端点**（`scope_matrix` 会增 ⇒ 条目数测试要一起改）：
  - `POST /entrustments/{eid}/offer-releases`（发布；幂等）
  - `GET /offer-releases/{id}`（经理视角）与 `GET /my-offer-releases`（货主视角，**白名单投影**）
  - `POST /offer-releases/{id}/responses`（客户响应；幂等）
  - `POST /offer-releases/{id}/withdraw`（撤回；幂等）
- **并发**：`ent_offer_response` 的 `UNIQUE(release_id)` 是**唯一判据**；
  应用层"先查后写"在并发下必然漏 ⇒ 需 **MySQL 真实并发用例**（CI 第 6 个 job 已在跑 MySQL 8.0）。
- **发布前来源门槛**（裁定二的具体化）：发布命令**必须**能区分"已核对来源"与"未核对来源"，
  未核对的提案**不得**被发布；核验动作要留下**核验对象 + 记录**，不是一个勾选。
- **界面**：货主侧扩「我的委托／委托详情」（待确认报价 + 响应记录）；经理侧在成果/发布处给出
  "发布这一版"与"看响应"。⚠️ 界面必须显示**冻结内容**与**当前内部版本**的差别，不能只显示"已发布"。
