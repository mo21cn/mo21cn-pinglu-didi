## 1. 合同对这条的要求（逐字）

* **BP-03 第 8 条**：`Generate one structured contract draft/template from the accepted
  facts and approved scope.`
* **包边界**：`One domestic contract template is sufficient.` ⇒ 模板可以是**常量**，
  不需要模板设计器；真正要证明的是**派生关系**。
* **D1-08**：`Contract draft derives from accepted facts; evidence and status remain
  distinct from live e-signature`；判据原文是 `Contract version and linked evidence
  inspection` —— 要能**逐项检查它是怎么来的**，不是"有一份合同"。
* **§10.1 第 7 步**：`Create the contract and record labeled sample signature evidence.`
* **持久化产物**：`... contract revision, evidence references.`

`S3-范围与依赖评估.md` 把它的依赖写成一句话，本切片就是按那句话做的：

> **E | 合同生成规则** | 第 8 条要求"从已接受事实派生"，需要一个**可核对的字段来源表**
> （哪些字段来自哪份已接受版本）

## 2. 本切片的立场：**"派生"与"编造"只差一件事 —— 每个字段有没有来源行**

三种"看起来也能用"的做法，逐条否掉：

| 做法 | 为什么不成立 |
| --- | --- |
| 在合同 payload 里给每个字段挂个 `source` 键 | 合同是要**发布给客户**的（`contract_review` 在 `registry.CUSTOMER_VISIBLE_TYPES` 里）。把 `release:12@v3` 这类内部编号写进正文，等于把审计信息当业务内容发出去；而客户投影按**字段名**裁剪，payload 里多出来的键是"未知字段"，注册表只能报不能删 |
| 只在派生记录上写一个 `derived_from` | 那是"整份合同有一个来源"，不是"**每个字段**各有来源"。一份合同里金额来自客户接受的那一版报价、当事方来自委托单、生效日来自接受时间、正文框架来自模板 —— 它们来源**不同**，混成一条就无法核对 |
| 不落库，读的时候现推 | 现推只能推出"按现在的规则会是什么"，而客户接受的是**当时那一版**（裁定三冻结细节②：已接受的旧版本永久保留）。事后重推会在数据被编辑后悄悄给出**不同**的答案，而记录上仍写着"同一个版本" |

所以第 2 张表是**字段来源表**，并且服务层里有一条**闸门**（`contracts._assert_every_field_has_source`）：

> 合同 payload 里**每一个**出现的字段路径，都必须在字段来源表里有对应的行；
> 缺一个就**中止**，不产生"看起来完整"的合同。

反向也查（来源表不能指向合同里不存在的字段路径）。这条闸门不是文档里的承诺 ——
将来有人往 payload 里加字段却忘了登记来源，它会**当场炸**，而不是安静地多出一句无出处的条款。
用例里有一节专门证明"这道闸门真的会拦"（否则"逐字段可核对"只是文档里的一句话）。

## 3. 两张表与它们各自挡住的那件事

| 表 | 一句话 | 它挡住的错误形态 |
| --- | --- | --- |
| `ent_contract_derivation` | 派生记录（**已接受的那一条发布** + 精确报价版本 + 产出的合同版本 + 模板版本） | 「合同是从哪来的」只写在某人的记忆/聊天里 ⇒ D1-08 的 inspection 无从下手；`UNIQUE(release_id)` 挡「同一份已接受事实派生出一式两份合同」 |
| `ent_contract_field_source` | 字段来源表（逐 `field_path` 的 `value_text` + `source_kind` + `source_ref`） | 「合同里那句"合同价款 36000"是哪来的」答不出来 ⇒ 甲方改了内部底稿后无法判断客户手上的合同是否还成立 |

### 3.1 为什么 `release_id` 是 UNIQUE

并行/重试是真实的（经理点两次、网络重发、两个经理同时点）。判据必须是 **DB 约束**：
`UNIQUE (release_id)`。应用层"先查有没有、没有再插"在并发下两个请求可以同时通过检查 ——
于是同一份客户接受派生出一式两份合同，**而两份各有独立的版本链**，事后审计无法判断
哪一份才是"客户接受事实"的那一份。这与 `ent_offer_response` 的 `UNIQUE (release_id)`
是同一条理由（裁定三原话："幂等且事务内处理并发"）。

### 3.2 为什么同一 `field_path` 可以有多行来源

唯一键是 `(derivation_id, field_path, source_kind, source_ref)`，**不是** `(derivation_id, field_path)`。
理由是一个真实场景：运输范围那一条条款由**三段航段**构成 ⇒ 三行来源（`leg:1` / `leg:2` / `leg:3`）
指向**同一个** `field_path`。按 `field_path` 去重会把"另外两段也在里面"这条事实丢掉。
用例 `test_legs_make_one_clause_with_one_source_row_per_leg` 钉住这一条。

### 3.3 为什么派生记录与合同成果必须**同一个事务**

既有 `artifacts.create_artifact` **内部自己 commit**（被很多路径复用）。复用它就会变成两次提交：
"先提交合同成果、再提交派生记录"。中途失败就留下**一份没有派生记录的合同草稿** ——
而"这份合同从哪来"正是本切片的全部价值：**一份查不到出处的合同比没有合同更糟**（它会被当真）。
⇒ `contracts.derive_contract` 在一个事务里写四张表（`ent_artifact` / `ent_artifact_revision` /
`ent_contract_derivation` / `ent_contract_field_source`），最后一次性提交。
注册表的字段契约校验**没有绕过**（照旧调 `registry.validate_payload`）。

## 5. 一处刻意的设计决定：读取端点**不给货主本人放行**

字段来源表里是 `release:12@v3` / `leg:4` / `assignment:7` 这类**内部编号** —— 那是审计信息。

`authz.assert_can_view_entrustment` / `assert_can_view_assignment` 都有一个旁路：
"是货主本人就直接通过"。本切片的读取端点**不能用它们**，用的是
`assert_can_view_org`（**没有货主旁路**，见它自己的 docstring）。

这与上一轮修掉的**投影泄漏**（`GET /entrustments/{id}/offer-releases` 曾恒回经理投影，
而货主本人被放行 ⇒ 客户拿到 `data_origin.basis` 与 `source_gate` 明细）同源但**不同型**：

* 那次是"**两个入口判据不一致**"⇒ 对齐；
* 这次是"**这条通道本就不该有客户面**"⇒ 不给旁路。

客户要看合同，走的是**已有的发布通路**：把这份 `contract_review` 发布出去
（`POST /entrustments/{eid}/offer-releases`，`contract_review` 本就在客户可见白名单里），
客户在 `/my-offer-releases` 读**冻结快照**。不为"客户看合同"新开通道 ——
否则"客户能看到什么"会有两个判据（与 §6.3 的白名单下载同一条纪律）。

用例 `test_derivation_read_is_org_side_only_and_404_before_derivation` 把这条决定钉住了：
谁哪天顺手换成 `assert_can_view_entrustment`，那条断言会红。

## 6. 一处必须说清的口径解释：`approved scope` 取的是哪个范围

合同 BP-03 第 8 条原文是 `from the accepted facts **and approved scope**`。
本切片的落法：

| 合同内容 | 来源类别 | 来源标识 | 为什么是它 |
| --- | --- | --- | --- |
| 价款 / 费用包含 / 费用不含 / 有效期 / 报价备注 | `accepted_release` | `release:<id>@v<n>` | 客户接受的**就是这一版**；取自发布时冻结的快照，不回头读成果当前版本 |
| 运输范围 | `leg`（有航段时，逐段一行）或 `assignment` | `leg:<id>` / `assignment:<id>` | "三段式方案"的结构化载体是 `ent_leg`（HO 0917-3 裁定：最小结构化航段对象） |
| 当事方 | `assignment` + `organization` | `assignment:<id>` / `org:<id>` | 货主来自委托单归属、承运方来自组织；都不取"现在谁是经理"这类会漂移的值 |
| 生效日 | `customer_response` | `response:<id>` | 合同的效力起点是"客户接受了那一版"，不是"生成时间" |
| 条款键名 / 当事方角色 / 常驻声明 | `template` | `domestic-transport:v1` | 模板常量（包边界允许）；常驻声明写明"样件模式、不构成实时电子签署" |

⚠️ **如实登记一处解释**：上表把 `approved scope` 读作"**委托单已受理的作业范围**"
（航段 + 委托归属），理由有二 ——

1. **委托受理本身就是"批准范围"这个动作**：货主提交、组织受理，范围在那一刻定下；
2. BP-03 第 3 条（采购确认）在本轮**仍未实现**，若把 `approved scope` 读成"采购确认的
   `agreed_scope`"，第 7 步会被第 4/5 步卡住。

**若 HO 认为 `approved scope` 特指采购确认**，处置是**追加**：`source_kind` 取值域是
`contracts.ALL_SOURCE_KINDS`（加一个 `procurement_confirm` 即可），来源表按行追加，
**没有迁移代价、不影响既有数据**。这一点写在这里，免得后来者以为是漏读。

### 7.1 权限为什么是 `entrust:quote:create` 而不是 `quote:publish`

派生 = **产出成果**（与 `POST /entrustments/{eid}/artifacts`、`POST /agent/jobs/{id}/adopt`
同一类动作）⇒ 用创建权限。它**不是**发布：发布是把成果发给客户，两者可以分给两个人
（经理拟定、负责人发布），合用一个权限会抹掉这条区分。

### 7.2 派生产物的 `source` 为什么是 `manual`

`artifacts` 只有 `agent` / `manual` 两态。派生**不是模型产出**（不存在"模型声明过什么来源"
这回事）⇒ `manual`。它的可核对性由**字段来源表**承担 —— 比 `ent_offer_source_check`
更具体（那里是"人核过没有"，这里是"这个值从哪来"）。

⚠️ 这意味着发布派生出合同时，`offers.source_gate` 会判"人工直写 ⇒ 无待核验项 ⇒ 放行"。
**这是对的，不是漏洞**：合同不需要"核验模型的来源声明"，它需要的是逐字段来源可查，
而那由本模块自己的闸门与 `ent_contract_field_source` 保证。

### 7.3 本轮实测缺陷（如实登记）

| 缺陷 | 形态与修法 |
| --- | --- |
| `_fmt` 只接 `datetime` | 读取路径炸 `AttributeError: 'str' object has no attribute 'strftime'` —— SQLite 把 DATETIME 列读回来是**字符串**。修法：与 `offers._fmt` **逐字一致**（两边各写一份的代价就是"写入路径全绿、读回来那条路炸"） |
| 非数值金额被当金额 | 冻结快照里 `amount` 可能是一句人写的"面议"，写进价款条款会让下游拿到**看起来是金额的字符串**。修法：`_numeric()` 判不出就计入 `absent_quote_fields`，**不替业务解释**（合同把"金额正确性"列为不可省项）。另：`bool` 在 Python 里是 `int` 子类，不挡住会把 `True` 当成金额 `1` |
| **MySQL 列注释写成两行相邻字面量** | `ent_contract_field_source.source_kind` 的 `COMMENT` 被折成两行（`… / leg /'` + 换行 + `' organization / template'`）。三引号体内这就是 **SQL 原文** ⇒ MySQL 报 `1064`，CI 的「数据库迁移（MySQL 8.0）」与「并发集成（MySQL 8.0）」**两个 job 双红**，而**本机零症状**（本机无 MySQL ⇒ 该分支的 SQL 从不执行）。修法：合并为一条注释；防回归闸门见 §9。**这是本轮最贵的一个缺陷，代价是两个 CI job** |

## 9. CI 首轮红复盘：一个本机看不见的 MySQL 语法错误（2026-09-17）

> 这一节记的是**过程事实**，不是又一项成果。写它的理由：同一个错误在本机怎么测都测不出来，
> 而它一次性打掉两个 CI job。

### 9.1 症状

PR #139 首轮 CI 六个 job，**4 绿 2 红**：

| job | 结论 |
| --- | --- |
| 后端 lint + test | SUCCESS |
| 前端静态契约（结构 / 路由 / UI 交互） | SUCCESS |
| 前端端到端（真后端载荷驱动） | SUCCESS |
| 数据库迁移（SQLite 冒烟 + 幂等） | SUCCESS |
| **数据库迁移（MySQL 8.0 真实执行）** | **FAILURE** |
| **并发集成（MySQL 8.0 真实执行）** | **FAILURE** |

两个红 job 的日志尽头是同一行：

```
pymysql.err.ProgrammingError: (1064, "You have an error in your SQL syntax; …
near '' organization / template',\n  `source_ref` VARCHAR(160) NOT NULL\n    COMMENT '…
```

### 9.2 真因：折行折在了 SQL 里

| 写法（当时的意图） | 实际发生什么 |
| --- | --- |
| 把过长的 `COMMENT` 文案在源码里**折成两行**，指望像 Python 那样自动拼接 | `"""…"""` 里没有"相邻字面量拼接"这回事 —— 两个引号串**原样**进了 SQL。MySQL 看到 `'a' 'b'`，在第二个引号处判语法错误 |

⇒ 这类缺陷的共同点：**错误信息指向的位置完全正确，而本机没有任何路径能到达那里。**

### 9.3 ⚠️ 并发 job 那 14 条是 ERROR，不是"并发用例红"

`test_mysql_integration.py` 的 14 条全部是 **setup 阶段的 `ERROR`**（建表就失败了），
**没有一条并发断言真的执行过**。⇒ 这一轮**没有任何**并发正确性证据：既不能算通过，
也不能算"并发实现有问题"。汇报时必须写成"**未执行**"。

（同一形态在 #140 上重现了一遍：它叠在 #139 之上，于是同一个错误又红了一次 ——
这也是"叠放式 PR 的下游分支会继承上游的红"的直接例证。）

### 9.4 本机为什么全绿 —— 是结构性失明，不是"忘了测 MySQL"

| 本机会跑的路径 | 为什么不碰那段 SQL |
| --- | --- |
| `migrate.py`（SQLite 分支） | SQLite 分支既不写列注释，也不执行那条语句 |
| pytest（含 `test_migrate.py` 的迁移冒烟） | 同上，全部跑在 SQLite 上 |
| 13 项本地门禁 | 只含上述两项 + 根脚本 lint / 前端静态 |
| 本机有没有 MySQL | **没有**：未装 `mysqld`、无 `docker`、3306 关闭（本轮再次核实） |

⇒ 根因不是"没测 MySQL"，而是**MySQL 分支的 SQL 在本机既没有执行路径、也没有任何静态检查**。

### 9.5 补的闸门：`tests/test_migration_sql_literals.py`

零依赖（不连库、不引三方包）、两个方言都查、两条断言：

1. **相邻字符串字面量** —— 状态机逐个区分「空串 `''`」/「SQL 的 `''` 转义」/
   「MySQL 的反斜杠转义 `\'`」三种合法形态，只报真正非法的相邻形态；
2. **双方言列名集合一致** —— 同名条目若两边都能解析出列名，集合必须相同：
   本地只跑 SQLite，**漏改 MySQL 侧的唯一症状就是不存在的症状**。

有效性**实测取证**（不是"应该能抓到"）：

| 时点 | 结果 |
| --- | --- |
| 修复前 | **FAILED**，精确命中 `migrations/ent_contract.py` 的 `id=2 [mysql]`，并给出源文件第 **151** 行（与实际缺陷行一致） |
| 修复后 | `2 passed` |
| 全仓扫描 | 34 条带方言分支的条目**零误报**；两方言列名集合**全部一致** |

它是一条 pytest 用例 ⇒ 落在既有的「后端 lint + test」job 与本地门禁的 pytest 组里，
**不新增 CI 步骤**。

### 9.6 仍然覆盖不到的（不掩饰）

* 闸门只拦"**纯文本层面就非法**"的写法。**列类型可移植性、索引/键长上限、字符集与排序规则、
  外键行为、`ALTER` 的方言差异** —— 这些都必须在 MySQL 8.0 上真实执行才算数，本机**无法替代**。
* 因此**本机 13 项门禁全绿 + 全量 pytest 0 失败，依然推不出 MySQL job 会绿**。本轮唯一能推出的是：
  「相邻字面量」与「只改一边」这两类**以后不会再漏到 CI**。
* 这次「本机 → CI」偏差与 DR-0002 把 MySQL 放进 CI 的理由是同一件事；它第二次证明：
  **本机跑不到的路径必须由 CI 承担，且只有在 CI 上跑过才算数。**
