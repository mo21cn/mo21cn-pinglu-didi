## 2. 本切片的立场：**"确认"与"选中"分得开，靠的不是两个端点，而是一条规则闸门**

只把两个动作做成两个端点，**证明不了**它们分开 —— 真正的判据是
`A chosen quotation alone does not create confirmed capacity.`，
而它只能靠"只做前一步时，后一步的痕迹**一点都没有**"来证明。

所以本地交付里有两条硬结构：

**① 确认是一条独立记录，不是候选行上的一个状态值。**
`ent_capacity_candidate.status` 的取值域里本来就有 `confirmed`，但它承载不了第 3 条：

| 第 3 条要求 | 候选行的一个状态值为什么不够 |
| --- | --- |
| `an authorized action` | 状态值没有 actor 与时间 —— 谁确认的、什么时候，全都没有 |
| `identified evidence` | 状态值没有证据引用（"有证据"与"证据是这一份"是两件事） |
| 判据要能**复算** | 候选行的吨位/有效期/证据**可以被改**；改完再读，确认还在、判据已经不成立，而记录上看不出来 |

⇒ 确认落成**只增不改的独立记录**，并把 `evaluate()` 读到的每一个值**整体冻结**在行上
（需求量、吨位、船数、拆批、有效期、证据类别与引用）。这不是冗余：冻结的是
"当时拿这些输入判的"，不是"候选行现在长什么样"。
（同一条论据见 `ent_offer_release.snapshot_json`、`ent_contract_field_source`。）

**② 写库前有一条闸门**（`capacity._assert_every_rule_reported`）：
规则集里**每一条**都必须产出一条判定，且**没有一条**是 fail，否则当场中止。

没有它，"某条规则这次没跑"在数据上与"跑了且通过"**完全一样** —— 确认记录照样存在，
逐规则判定表少一行而已，**没有任何下游症状**。这与
`contracts._assert_every_field_has_source` 是同一类闸门，只是对象从"字段"换成"规则"。

## 3. 确定性规则从哪来（不是我的发明）

容量规则有**逐字来源** —— `backend/scripts/fixtures/demo1_canonical.json`：

> `"候选适用于某数量 ⇔ candidate.capacity_tonnes ≥ 该水运段的实际承运量；若候选声明`
> `single_vessel 且 no_partial_load，则该承运量必须由一条船装下（不允许拆批）。"`

以及 `DEMO-1-fixture-manifest.md` 第 25 行：
**「若允许拆批或多船承运，950 吨未必装不下」**。

本模块据此把三种形态**分开**，而不是笼统地比大小：

| 候选形态 | 判据 | 依据 |
| --- | --- | --- |
| 单船 + 不拆批 | `capacity_tonnes ≥ 需求` | 整批必须一船一程装下（canonical C-900：950 > 900 ⇒ 不适用） |
| 多船（`vessel_count > 1`） | `capacity_tonnes × vessel_count ≥ 需求` | 可分配到多条船（canonical：900 × 2 = 1800 ≥ 950 ⇒ **未必**装不下） |
| 允许拆批（`allows_partial_load`） | 通过，并**记下需几趟** | 可多趟承运 ⇒ 量不再是上限；但趟数必须写在判定里，"通过"两个字不是判定说明 |

### 3.1 四条规则（`RULESET_VERSION = "v1"`，顺序即展示顺序）

| # | 规则 | 判据 | 不通过时说什么 |
| --- | --- | --- | --- |
| 1 | `demand_known` | 委托货量有值、为正数、且单位是**吨** | 未知/非正数/单位不是吨 —— 不同口径之间**没有可判定的换算关系**，不许硬比大小 |
| 2 | `evidence` | 证据**类别**在取值域内 **且**有**引用** | 只有类别没有引用 ⇒ 不算 `identified` |
| 3 | `validity` | `valid_until ≥ 判定基准日` | 过期；**没登记有效期也算不通过**（未知有效期 ≠ 未过期） |
| 4 | `capacity` | 见上表三条分支 | 写出**缺口吨数**（如「900.000 × 1 = 900.000 吨 < 需求 950.000 吨，缺口 50.000 吨」） |

四条**全部评估**（不做 fail-fast）：调用方拿到"只差一条"的拒绝、改完再撞下一条，
一次演示要来回四五轮。逐条如实报是同一份工作量，但让人一次改完。
规则之间**允许**因同一根因同时不通过（需求量未知 ⇒ ①④ 都不通过）；
刻意**不**做"根因归并" —— 归并后"一共几条规则被判过"就不再等于 `ALL_RULE_CODES`，
而那道闸门正是本模块的核心不变式。

**判定的输入落在哪**：需求量取 `ent_assignment.quantity`（整单货量），不按航段分摊 ——
canonical 是公—水—公同一批货过驳，水运段承担的正是整单货量。判定说明里会写
`assignment:<id>.quantity` 这个出处。若将来要按航段分摊，处置是给 `ent_leg` 加
`quantity` 列并改 `_assignment_demand` 这一处。

## 4. 两张表 + 一列，各自挡住什么

| 对象 | 一句话 | 它挡住的错误形态 |
| --- | --- | --- |
| `ent_capacity_confirmation` | 确认记录（独立记录 + **判定输入冻结快照** + 证据引用 + 指向成果版本） | 「确认」只剩一个状态值 ⇒ 说不清谁在什么时候凭哪份证据确认的；候选行一改，判据与结论就脱节 |
| `ent_capacity_rule_check` | 逐规则判定（`rule_code` / `seq` / `detail`） | 「规则跑没跑」看不出 ⇒ "这次没跑某条规则"与"跑了且通过"在数据上完全一样 |
| `ent_capacity_candidate.evidence_ref`（**追加列**） | 证据**引用** | 只有 `evidence_kind`（"是单据"）没有引用（"是**哪一份**"）⇒ 不构成 BP-03 第 3 条的 `identified evidence` |

### 4.1 为什么 `UNIQUE (candidate_id)` 而不是"先查后写"

并行/重试是真实的（经理点两次、网络重发）。一条候选被确认两次 ⇒ **同一候选产出两条
独立的采购确认版本链**，`recheck` 与后续复核会面对"哪一条才是那次确认"，而它无从回答。
⇒ 判据是 DB 约束，应用层"先查后写"在并发下必然漏（与 `ent_offer_response` 同一条理由）。

**一条候选只能确认一次。** 要改资源或改结论，登记**新的候选行**再确认 ——
它的吨位/有效期/证据都是新的，而"已作出的确认不能被覆盖"。
这条与"过期须先取得合法续期"是同一条纪律：**续期＝登记新候选，不是把老候选的有效期改掉**
（改掉之后旧确认的判据就无从复核了）。

### 4.2 为什么迁移模块叫 `ent_commitment_capacity.py`（不是笔误）

迁移条目按**模块文件名排序**应用（`migrate.py:load_entries`），**没有**声明式依赖。
本模块 id=3 要 `ALTER ent_capacity_candidate`，而那张表由 `ent_commitment.py` 建 ——
叫 `ent_capacity*.py` 会排在 `ent_commitment.py` **之前**，于是在一张还不存在的表上做 ALTER。

实测症状：`no such table: ent_capacity_candidate`，**且只在全新库上出现**
（已有库因为表已存在而全绿）—— 也就是说，它会躲过本机回归、在 CI 的新库上红。
既有 ALTER 型模块都恰好满足这条（`ent_artifact_assignment` > `ent_artifact`、
`ent_extract` > `ent_attachment`、`ent_revalidation` > `ent_exception`），
本切片只是把这条隐含规则**显式写进模块文档**。

## 6. 一处刻意的设计决定：**整组端点都没有客户面**

六条端点**一条都不给货主本人放行** —— 全部走 `assert_can_view_org`（**没有货主旁路**）
或写侧的 `assert_can_write_entrustment`。理由逐条：

* 候选行带**承运人**与**供应商单价**（`rate` / `rate_unit` / `currency`）；
* 确认行带 `agreed_amount` / `currency` / `supplier` —— 注册表已把这三个字段标为
  `internal_fields`；
* 确认详情里的**逐规则判定**写着需求量、运力、缺口这些内部比较过程。

把任何一条交给客户，就是把内部成本口径送出去。**客户不是没有渠道了解商业承诺** ——
他看到的是**对客报价的冻结快照**（`/my-offer-releases`），那份内容由发布那一刻的服务端
白名单投影决定。

这与 §6.3 的白名单下载、以及合同派生读取端点不给货主放行是同一条纪律：
**"客户能看到什么"只能有一个判据**，而那个判据在发布通路上。
用例 `test_owner_and_outsider_cannot_read_capacity`（四个端点 × 货主/局外人）把这条钉住。

## 7. 两处必须说清的口径解释

### 7.1 登记只拒"录错了"，不拒"还没齐"（需 HO 认可）

登记**允许**没有证据、没有有效期。理由不是宽松，而是：如果把它们也压在登记上，
**BP-03 第 3 条 `expired ... cannot be confirmed` 那条规则就永远触发不了** ——
过期数据根本进不来，那条规则就变成了装饰。

⇒ 分工是：**登记**拒"结构上不可能有意义"的输入（承运人空、吨位非正数、单价与计价单位
半边缺、证据类别不在取值域、航段跨单）；**确认**判"当前适不适用"（有效期、容量、
证据齐不齐）。后者才是会随时间变化的那些。

### 7.2 拆批分支给「通过 + 趟数」而不是「不通过」（需 HO 确认）

`allows_partial_load` 是**资源自己的属性**（"这条船接受不足整船的货"）。
把它读成"必须走变更案件"等于替业务做了决定；而 canonical 夹具的原话是
**「若允许拆批……950 吨未必装不下」**，所以本切片让它**通过**，但**必须把趟数写进判定**
（`需 2 趟`），而不是给一句"通过"。

**若 HO 认为拆批也必须落在正式变更里**，处置是把它归入 fail 并追加一条业务变更 ——
一行判定 + 一条用例，**无迁移代价**。

### 8.1 权限为什么是 `entrust:quote:create`

确认运力 = **产出可见的业务记录**（产出 `procurement_confirm` 成果），与
`POST /entrustments/{eid}/artifacts`「产出成果」同一档。它**不是** `quote:publish`
（那是发给客户），也不是 `task:dispatch`（那是派活）。
本切片**不新增权限常量** —— 新增一个要在授权取值域、界面授权配置、矩阵三处同步，
而现有"产出成果"的语义已覆盖。⚠️ **若 HO 认为采购确认需要更窄的权限**
（它是对外承诺的供应商侧动作），处置是新增一个权限常量并在三处登记。

### 8.2 判定失败**不落库**（刻意的两处不对称）

* **库里**的 `ent_capacity_rule_check` **只有通过**的判定 ⇒ 所以它**没有 `outcome` 列**：
  有行就是通过，写一个恒为 `pass` 的列是造一个假字段。
* **409 响应体里**的判定**可能**是 `fail`，且带 `outcome` —— 那是为了让"被拒绝"与
  "已确认"在客户端**形状一致**，一套渲染就够。

拒绝的证据是**响应体里的逐条原因**，不是一条历史行。这与
`ent_offer_release` 的三态、`ent_offer_response` 的一行，属于同一种刻意的不对称。

| 缺陷 | 形态与修法 |
| --- | --- |
| **约束错误被一律说成"已被确认过"** | 初版 `except IntegrityError` **无条件**抛 `CapacityStateError("...已被确认过...")`。并发预跑里漏传 `entrustment_id`（`ent_artifact.entrustment_id` 是 **NOT NULL**）⇒ **两个线程都拿到"已被确认过"，而库里一条确认行都没有**。修法：**确实查到确认行**才翻译成 409，否则**原样抛出**。把约束错误一律改写成语义错误，等于把"代码写错了"伪装成"业务不允许"，而那类伪装下次会以同样面目出现（"并发时偶发 409，重试即可"）。已加回归用例 `test_unrelated_integrity_error_is_not_reported_as_already_confirmed` |
| **`entrustment_id` 曾是可选的** | 与上一条同源。它要写进 NOT NULL 的列，给一个 `None` 默认值只会让报错迟到一个数据库层、且形态是 `IntegrityError`。修法：改成**必填关键字参数**，让调用点当场失败 |
| **迁移模块名排序** | `ent_capacity.py` 排在 `ent_commitment.py` **之前** ⇒ 在还不存在的表上 ALTER。症状只在**全新库**出现（`no such table: ent_capacity_candidate`），本机已有库全绿。修法：改名 `ent_commitment_capacity.py` 并把这条例外规则写进模块文档（见 §4.2） |
| **数值列跨后端类型不同** | MySQL 把 DECIMAL 读回来是 `Decimal`、SQLite 是 `str`。响应模型声明 `str` 时，MySQL 上会直接校验失败（**本地全绿、CI 红**）。修法：在 `_row_to_*` 里就归一成**定长文本**（3 位吨位 / 4 位单价），两个后端给出同一个字符串。与 `_fmt`（时间列）踩过的坑同源，只是换成数值列 |
| **判定文案里的反引号** | `identified evidence` 之类若用反引号包裹，会在**小程序界面里原样渲染**（界面文案不是 Markdown）。修法：交付文案一律用「」。收尾时**又抓到同类一条**：`"**未知有效期不等于未过期**"` 的 `**` 会被**字面渲染成星号**，已改成「」。 |
| **mypy 不从一个 `bool` 变量反推类型** | `demand_ok = demand is not None and demand > 0 and ...` 之后，mypy **不认为**后续分支里 `demand` 已非 None ⇒ 三处 `demand / capacity`、`supply >= demand`、`demand - supply` 报 `Decimal \| None`。同族还有 `_as_date(x).isoformat() if _as_date(x) else None`（两次调用之间的类型关系它不认）。修法：条件里**显式重写** `demand is None or not demand_ok`（**逻辑等价**，只为收窄，注释里写明是给类型检查器看的）；日期**只解析一次**存本地变量。⚠️ 这一条本地 pytest 全绿也照样红 —— 它与"数值列跨后端类型"是同一类：**判据在门禁里，不在用例里**。 |
| **新文件漏跑 `ruff format`** | `ruff check` 绿 ≠ `ruff format --check` 绿（前者查规则，后者查排版）。新写的 3 个文件（服务层 / API 层 / 用例）全部被判"would be reformatted"。修法：`ruff format <files>`（**CI 与本机门禁都查 format**，别只跑 check）。 |

### 8.4 界面切片实测缺陷（2026-09-17 补 —— 运力界面）

| 缺陷 | 形态与修法 |
| --- | --- |
| ⛔ **「本次确认覆盖的范围」在真机上根本填不进去** | `detail.wxml` 的两个输入框（范围 / 备注）写的是 `data-df="cap-scope"` 与 `data-df="cap-note"`，而页面 `onCapInput` 的映射表里**只有 `capForm` 那九个字段**。`bindinput` 照常触发、`ds.df` 也照常读到，查表查不到就**静默空转**：输入框一个字符都写不进去，而页面看起来一切正常。后果不是"少一个字段"，是 **`onSubmitCapConfirm` 在页内校验处直接返回**（提示「请填写本次确认覆盖的范围」）⇒ **真机上运力确认永远提交不了**。修法：映射表的值由**裸字段名**改成 **setData 路径**（`capForm.xxx` / `capScope` / `capNote`），并把"为什么后两个不在 `capForm` 里"（它们属于**这一次确认**，随确认条开关生灭；混进草稿会让"取消再打开"把上一次的范围带过来，看起来像已经填好了）写进注释。**由本地复现的 e2e 抓到**：⑰ 段按 `data-df` 驱动页面，四条逐规则判定一条都没拿到。 |
| ⚠️ **e2e 的 `session-context` 回放表只按一张委托写了键** | `route()` 按 `entrustSessionContext[aid]` **精确匹配**，而这张表只按 **⑮ 段挑中的那张委托**（有成果的那张）写入；⑰ 段挑的是「组织侧可达的第一张」⇒ 两者不一定是同一张。缺键时 `fetchSessionContext` reject，被详情页 `.catch` 吞成 `null` ⇒ `ctx.entrustment_id` 取不到 ⇒ `canRecordCapacity` 变假。⚠️ **症状极具误导性**：它长得像「该组织缺 `entrust:quote:create`」，而同一段第 ③ 步却把三条候选**直接写进去了**（后端允许）—— "前端说不行、后端说行"才是真信号。修法：⑰ 段选完 `aid` 后**用真接口补一份该单的 `session-context` 进回放表**，取不到就**显式失败**（授权定位是写权限的前置，后端 `_write_scope` 要求 (货主, 组织) **恰好一条**生效授权）。 |
| 口径复核：`canRecordCapacity` **不是过严** | 复核后端 `capacity_api._write_scope`：成员资格（404）→ **唯一**生效授权（409）→ `entrust:quote:create`（403/409）。前端"授权可唯一定位 ∧ 该组织有该权限"与之逐条对齐，故上一条**只是缺载荷，不是判据写错** —— 不改前端口径。 |
