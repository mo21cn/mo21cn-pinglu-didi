## 2. 三处必须写明的口径

### 2.1 为什么重开**另开一个权限码**

结案是"对客户宣告做完"，重开是**撤销那次宣告** —— 两者敏感度不同。
并进 `complete` 会让"能结案"自动蕴含"能撤销结案"：那意味着**任何一次误结案都可以被
同一个角色随手撤销**，而"受控"这个词就只剩形式。
（实现上两者**共用一份判据** `_assert_can_operate`，只是传入不同的码 —— 这样将来改判据
不会只改一半。）

### 2.2 为什么 `reason` 必填、且必须落 append-only 表

* **必填**：没有理由的重开，在审计上等于"结论可以随时改"。它在契约层是
  `min_length=1`，服务层再兜一次（⛔ 不靠单层）。
* **留痕**：重开会把 `completed_at` 清成 NULL ⇒ 清空之后，"**曾经结过案**"这句话
  就只剩 `ent_assignment_reopen` 这一处能回答。所以那一行必须记下
  **被撤销的那次结案时间**（`previous_completed_at`）、谁撤的、为什么、从第几版撤的。
  否则历史被抹平，而合同要求 `retain the complete history`。

### 2.3 重开**不**恢复取消资格（Q2）

`cancel` 只对 `submitted` 生效的既有口径**一个字没动**：重开回到 `claimed` 之后，
取消这条边**依然不存在** —— 重开只能再走 `complete`。
它由 pytest 的 `test_reopen_never_restores_cancel` 专门钉住（断言"**不该成功**"，
而不锁死具体状态码：403/404/409 都算拒绝，唯一不能出现的形态是成功）。

## 3. 两个"不算"的边界

| 情形 | 判据 | 为什么 |
| --- | --- | --- |
| 非 `completed` | **409** | 重开是**撤销一次既有的结案**，不是通用回退；否则它会长成"任何状态都能往回走"的后门 |
| `completed` 却没有 `completed_at` | **409（报错）** | 状态与事实不一致 ⇒ 拒绝重开。⛔ 不留一条"没说清撤销了什么"的留痕 |

## 4. 并发与原子性

与 `complete` 同构：**行锁**（`locks.lock_assignment_row`，MySQL 才加 `FOR UPDATE`）
＋ 锁后重读 ＋ 条件 UPDATE（`status` 与 `revision` **双条件**都在 SQL 里）。
⇒ 两个经理同时重开，恰好一个成功；另一个要么在锁后重读时看到状态已变，要么条件 UPDATE
`rowcount=0`。MySQL 并发锚点见 `tests/test_mysql_integration.py`（本机无 MySQL，只由 CI 执行）。

## 5. ⛔ 本切片刻意不做

* **取消**：Q2 明确"重开不恢复取消资格"，本切片**不**新增任何取消路径。
* **"重开后再结案"的专用命令**：重开之后回到 `claimed`，再结案由既有 `complete` 负责 ——
  不需要第二条命令，也不需要"跳过五维度"的捷径。
* **批量/免理由重开**：与"受控"直接冲突，不在本切片。
* **界面上按委托列表批量重开**：不在本切片。
