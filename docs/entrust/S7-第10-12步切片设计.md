## 1. 结论先行

1. **第 10–12 步是一条串联链**：
   **第 10 步**（记录交接 / 缺失证据 / 争议额外项）→ **第 11 步**（用证据解决 + 确认结算）
   → **第 12 步**（按 §6.4 前置结案）。第 12 步的 `complete`（=`S4-b`）只是**检查**，
   它的前置 4/5（结算已批准、余额已结清）**只有第 11 步的实体存在才有判据**。
2. ⭐ **"交接"不需要新建实体**：合同 S4 段第 4 条明写
   `Do not invent a "handover artifact" when handover is represented by a task.`
   ⇒ 交接＝**任务**（`ent_workflow_task`，装卸/交接类任务 ＋ 它要求的证据）。
   这与本仓"DR-0016 任务/成果影响映射"是同一套东西，**不要**另起一张 `ent_handover` 表。
3. ⭐ **真正缺的是「费用行」这一个实体**：合同 S4 段第 9/10 条要求的
   `receivable/payable lines` ＋ `one extra waiting-time charge`，字段面已由合同点名
   （`quantity` / `unit` / **Decimal** `amount` / `currency` / `counterparty` / `basis` / `status`），
   且第 10 条要求 **disputed 不得进 confirmed totals**。
   实测：全仓 **34 张 `ent_` 表里没有它**（§2）⇒ 这是第 10 步的**唯一新建实体**。
4. ⭐ **执行顺序（HO 0918-2 裁定；含对初稿的修正）**：
   **S7-1 / S7-2 → S7-3（结算与收付依据）→ `S4-b`（结案）→ `S4-c`（重开）**。
   ⚠️ **初稿把 `S7-3` 写成依赖 `S4-b`** —— 那与"结算是结案的前置"**互为循环**，是错的。
   **`S7-3` 不依赖 `S4-b`**：它自己产出"结算版本 ＋ 内部/客户确认 ＋ 收付依据"，
   `S4-b` 只负责**检查**这些事实。
   ✅ 可以**提前写**结案规则与拒绝用例；但**结案的成功路径必须等真实结算事实接通**
   —— 不得以默认值或直接改库补齐。

| # | 问题 | **裁定** | DEMO-1 的最小实现边界 |

### 4.1 Q5 需冻结的语义（HO 原文要点）

1. **客户确认绑定精确结算版本**，记录客户身份、时间与决定；
2. **客户只看对客费用及证据白名单**，不暴露内部供应商成本；
3. **确认后修改相关费用，必须形成新结算版本**；**旧确认保留，但不能替新版本过关**；
4. **客户确认结算 / 记录收付证据 / 经理执行结案，是三个独立事实**；
5. **收付可以使用明确标注的合成样本证据**，不接真实支付、不宣称真实资金到账。

### 4.2 依赖顺序修正（HO 明确要求改写本文档）

```
S7-1 / S7-2  →  S7-3（结算与收付依据）  →  S4-b（结案）  →  S4-c（重开）
```

⛔ **`S7-3` 不依赖 `S4-b`**（初稿写反了，形成循环依赖）。

## 5. HO 界定的四条边界（实现时的硬约束）

1. **缺证据不必另造一套工作流**：优先从**现有任务的必需证据与已登记证据派生缺项**，
   在**原任务**提供补录入口；需要分派时再**复用现有任务能力**，不建设通用等待引擎。
2. **争议"已解决"≠"应计入"**：解决结果可能是**认可 / 调减 / 拒绝** ⇒ 必须明确
   **最终金额**与**是否计入**；否则一个 `resolved` 状态会让合计规则产生歧义。
3. **`financial_status` 的展示前提是"派生逻辑接通"**，不是"等到 `complete` 上线"。
   **只有迁移默认值时不能展示**；`S7-3` 已能根据真实费用、确认与收付依据计算时即可展示。
4. **不扩展财务系统**：本期**不做**多币种兑换、税务、发票、银行接入、自动支付、授信、
   通用会计账簿。**不可省**的是：费用身份、版本、证据、**Decimal**、权限。

### 5.1 可直接执行的八条

1. **Q1=C**：按币种和应收/应付分别合计；DEMO-1 仅支持 CNY。
2. **Q2=B**：争议必须经显式动作并附证据解决；记录认可/调整/拒绝的金额结果。
3. **Q3=A**：`waiting_time` 使用普通费用行。
4. **Q4=A**：第 10–12 步经现有产品界面演示。
5. **Q5**：结案检查客户对最终适用结算版本的确认；原报价接受不能替代；不另建完成确认回路。
6. **修正依赖**：`S7-1 / S7-2 → S7-3 → S4-b → S4-c`；**`S7-3` 不依赖 `S4-b`**。
7. **优先复用**任务、证据、案件、版本及客户详情入口；不建通用等待引擎；
   不扩展支付、授信、税务、多币种业务；财务派生**未接通时不展示默认状态**，接通后可**先于** `complete` 展示。
8. **PR #158 按既有规则合入**（HO 建议先按上述裁定修正设计稿；**不要求**把 S7 实现塞进该 PR）；
   **O-8** 做**一次**同库连续两跑的定向验证，**不阻塞**独立业务开发；最终仍按完整 13 步及 D1-01–D1-18 收口。

## 7. S7-1 实施记录（2026-09-18，**后端**）

**做了什么**

* 迁移 `ent_charge`（**只增不改**）：费用行 ＋ 争议处置的**金额结果**（`resolution_outcome`
  / `resolution_amount` / `counts_in_total`）＋ `revision` 乐观锁；
  `assignment_id` / `direction` / `charge_kind` / `quantity` / `unit` / `amount` /
  `currency` / `counterparty` / `basis` / `status` ＋ 处置留痕（人、时间、依据、证据引用）。
* 服务层 `charges.py`：`record_charge`（→ `draft`）/ `confirm_charge` / `dispute_charge`
  / `resolve_charge` / `list_charges` / `summarize_charges`。
  状态迁移收在**唯一一处** `_transition`（条件更新 ＋ `rowcount == 0` ⇒ 409）；
  金额一律 `Decimal`，出参是**字符串**并按列定点位数 `quantize`
  （SQLite 的 NUMERIC 亲和性会丢掉末尾零，不抹平就会"同一契约两种字面值"）。
* 端点 `charges_api.py` 5 条：读清单与合计 / 登记 / 确认 / 提争议 / 处置；
  权限矩阵 **87 → 92**；路由已注册。
* 用例 `tests/test_entrust_charges.py`（功能 ＋ 负例 ＋ 幂等）。

**凭什么判定**

* 合同「**争议不进已确认总额**」与裁定 Q1=C / Q2=B / Q3=A **各自有专门用例**；
  其中 Q2 的**两个方向各钉一次**（`counts_in_total` 真 ⇒ 按 `resolution_amount` 计入；
  假 ⇒ 不计入）—— 只钉一边的话，"恒计入"或"恒不计入"都能通过。
* 合计**由服务端算**，并回 `counted_lines` / `excluded_lines`：这个合计"怎么来的"可被复核
  （不计入的行**仍然成组出现**，只是计入数为 0 —— 把整组藏起来会让"少了这一笔"没有出处）。
* 负例覆盖：货主本人读 ⇒ **404**（费用带对手方与依据，是内部成本口径，与运力那组同型）；
  局外人 ⇒ 404；**另一货主的授权不含写权限 ⇒ 403**（看得见、写不了 —— 两个维度分开判的
  可观测后果）；对 `draft` 提争议 ⇒ 409；`revision` 过期 ⇒ 409；缺 `basis` / 数量与单位
  不成对 / `counts_in_total=True` 却没给 `final_amount` ⇒ 400；同键重放 ⇒ 只一行。

**还差什么（如实登记）**

* ⛔ **客户侧投影没有**（裁定 Q5 第 2 条「客户只看对客费用及证据白名单」）：
  它需要"哪些费用是对客的"这个口径 ⇒ 归 **S7-3**；本切片不假装已支持。
* ⛔ **界面没有**：费用行的读与写在界面上都还没有入口。裁定 Q4=A 要求第 10–12 步
  **经现有产品界面演示** ⇒ S7-1 之后要补界面，否则那一格仍然只能在接口层演示。
* ⚠️ **`financial_status` 的派生未接通**：按 §5 第 3 条，此时**不得**在界面/接口上
  当作结论展示（"只有迁移默认值时不展示"）。
* ⚠️ **并发只在 SQLite 单测里**（本机无 MySQL）：真锁语义由 CI 的「并发集成（MySQL 8.0）」
  job 覆盖；本机那几条 MySQL 用例是 **skip**，"本地全绿"**不含**它们。
* ⛔ **不声称任何 D1 / AC 通过**：本切片只到"后端能用接口走通 ＋ 已自动化验证"。

## 8. S7-2 实施记录（2026-09-18，**后端**）

**做了什么**

* **补录入口** `POST /tasks/{task_id}/evidence`：在**原任务**上追加一条证据，
  返回**重算后**的齐备度（补录的唯一目的就是让缺件清单变短）。
* **派生读模型** `GET /assignments/{assignment_id}/evidence-gaps`：缺什么
  ＝ `required_evidence` − `evidence_refs` 的类别；含 `handover` 汇总。
* **§2 落成字段**：证据条目新增 `occurred_at`（**业务发生时间**）与 `source`（来源）；
  `recorded_at` / `recorded_by`（记录时间与记录人）**由服务端写**，调用方自带 ⇒ 400。
* **权限矩阵 92 → 94**；`__init__.py` 无需改（两条都挂在既有 `tasks_api` 上）。
* 用例 `tests/test_entrust_task_evidence.py`（19 例）。

**凭什么判定**

* ⛔ **不另造工作流 / 不建通用等待引擎**（边界 1）：缺件条件不是新实体，
  它就是任务自己的 `waiting` ＋ `wait_reason`；补救出口不是新流程，就是在**本任务**上补齐。
  ⇒ 没有新 guard 值、没有新权限常量、没有新表。
* ⛔ **不发明"交接成果"**（合同 S4 段原话）：`handover` 没有独立实体，
  它就是 `task_type = handover` 的任务；**没有交接任务时 `satisfied` 是 `null`**。
* ⭐ **业务发生时间不被默认成记录时间**：不给就**缺着**（未知保持未知）。
  这一条是 §2 的判据本身 —— 两者相等时无法区分"真的同年同月同日同时"与"我们悄悄填了现在"。
* ⭐ **完成从"替换"改为"合并"**：补录两条 → 完成只提交第三条 ⇒ **三条都在**。
