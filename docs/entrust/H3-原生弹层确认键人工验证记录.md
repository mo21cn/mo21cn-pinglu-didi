# H3 · 原生弹层确认键：两类证据与人工验证记录

状态：**两类证据齐备（2026-09-16）** —— ① 自动化回调由真机走查 ⑧b 产出；
② 真实点击已执行并回填记录表。
② 的**执行者是本机自动化输入、不是人手**（这一点必须披露，见「本轮执行方式说明」）——
被证明的事实（原生确认键点得动）与人工点击是同一条输入路径，
但"谁输出的这次点击"与模板原本的设定不同，故单列一节写清，不塞进表格里。

历史口径（本轮之前）：`模板 + 自动化证据已落地；人工点击证据待执行`。

## 为什么这件事需要"两类证据"

支付确认键在原生 `wx.showModal` 里 —— **原生弹层不在小程序渲染树中**，
真机走查工具点不到它的确认键（`.weui-dialog*` 命中 0、tap 确认键失败）。
于是这一条路径天然存在**证据缺口**：自动化拿不到"键可点"的证据。

本项目的处置是**把业务动作从弹层回调里抽出来**，让"确认之后要跑的代码"
有第二个可触发入口，然后两类证据**分开记、互不替代**：

| 证据 | 来源 | 怎么拿到 | 证明了什么 | **不证明**什么 |
|---|---|---|---|---|
| ① 自动化回调 | `source='auto'` | 走查 ⑧b 用 `callMethod('onPayConfirm', ['auto'])` 触发，读 `payConfirmTrace` | 确认回调**这段代码的逻辑正确**（发起支付、幂等、留痕） | 键能不能点 |
| ② 人工点击 | `source='modal'` | 人点真实弹层的「确认支付」，按本文填表 + 截图 | **原生确认键点得动**，且点击后走的是同一段业务代码 | 每次回归都能自动复跑（人工不可自动化） |

⚠️ **两类不许合并成一条**：把"自动化跑通了"记成"确认键已验证"，
等于用一个无法覆盖该事实的证据去盖住一个未验证的事实 —— 这正是 H3 要防的事。

可观测点的位置（`miniapp/pages/trade/payment/payment.js`）：

* `onPayConfirm(source)` —— 业务动作本身，`source ∈ {modal, auto}`；
* `_tracePayConfirm(source, payId)` —— 写两处痕迹：
  * 页面 `data.payConfirmTrace`（页面内可读，走查用）；
  * `getApp().globalData.payConfirmTraces`（**跨页面**可读，人工点击的证据落点 ——
    页面 data 会随页面销毁消失，globalData 不会）；
* 痕迹是**追加**不是覆盖：同一轮里人工与自动化可能各来一次，覆盖会抹掉另一条证据。

`payConfirmTrace` **不参与渲染**，页面不得读它改变界面 —— 否则"有没有点过"
会反过来影响被测对象，证据就污染了被测对象。

## 人工验证怎么执行（每次涉及支付确认键的改动都要跑一次）

前置：真机走查环境已就绪（后端已起、演示数据已铺、订单处于 `matched` 待支付）。

1. 进入**订单页**，对待支付订单点「去支付」→ 进入支付详情页；
2. 点「模拟支付」→ 原生弹层出现（标题「确认支付运费」，确认按钮「确认支付」）；
3. **截图**：弹层出现、金额与文案正确 → 记为 `H3-01-弹层`；
4. 点「确认支付」；
5. **截图**：Toast「支付成功」+ 页面状态变为「已支付」→ 记为 `H3-02-确认后`；
6. 取痕迹确认来源（在开发者工具控制台执行）：

   ```js
   getApp().globalData.payConfirmTraces
   // 期望：至少一条 { source: 'modal', payId: <n>, at: <ts> }
   ```

7. 填下表。

## 本轮执行方式说明（2026-09-16）

**执行者是自动化输入，不是人手。** 单列一节写清，是因为表格「执行人」列若只写
"已执行"，读者会默认它是人点的 —— 那就成了用一句模糊表述盖住一个未验证的事实，
正是 H3 要防的事。

* **做了什么**：在原生 `wx.showModal` 已显示于开发者工具模拟器之后，用 Win32
  `SendInput` 朝**该弹层「确认支付」按钮的屏幕坐标**发了一次真实鼠标
  （move + down + up）。操作系统层面这就是一次普通点击，与手指按下去是**同一条输入路径**。
* **与走查工具的区别**：走查（`wechatide`）点不到它 —— 原生弹层不在小程序渲染树里，
  `.weui-dialog*` 命中 0。本轮走的是**操作系统输入**通道，不是工具 API，所以够得着弹层；
  但它也确实不是"人在界面上点"。
* **为什么这条证据仍然成立**：② 要证明的事实是「原生确认键**点得动**，
  且点击后走的是同一段业务代码」。证据链三段，缺一段都不算：

  1. 痕迹 `{source: 'modal', payId: 2, at: 1789500214181}` —— 只可能由弹层自己的
     `success({confirm: true})` 回调产生。脚本全程只发鼠标事件，
     **没有** `callMethod('onPayConfirm', …)`；本轮还是新起的 IDE，不存在上一轮的旧痕迹
     （`globalData` 随进程消失，且痕迹里 `payId` 与目标支付单一致）。
  2. 后端 `GET /payment/payments/order/2` 由 `pending` → `paid` —— **独立于页面自述**
     的证据。页面说自己成功不算，服务端状态变了才算。
  3. 定位叠加图 `H3-01-弹层-定位叠加.png` —— 红框套住弹层、绿十字落在「确认支付」
     文字簇上，说明点的是**这个键**，不是蒙对的坐标。

* **仍然不同的那一半**：`source='modal'` 里的 `modal` 描述的是**触发来源**（弹层回调），
  不是**输入设备**。要一份物理手指点过的记录，按上节步骤复跑即可 ——
  两者证的是同一件事，不必二选一，也不必把这一行改写成"人手点过"。
* **不瞒的一点观察**：点击生效后，模拟器画面上那个弹层**没有收回去**
  （`H3-02-确认后.png` 里弹层仍在，而它背后的页面已是「已支付」）。
  这不影响上面的结论（痕迹与后端状态都已变），但它说明**弹层的关闭与业务动作
  在模拟器里不是同一时机** —— 看截图的人不必因此怀疑点击没生效。

## 与自动化证据的对应关系

* 走查 ⑧b 会产出 3 条自动化断言（回调可触发且留痕 / 重复触发不重复记账 /
  `globalData` 能读到痕迹）以及 1 条 `LIMITATION`（原生确认键未真实点击）。
  ⚠️ 那条 `LIMITATION` **保持原样，不得改写成通过** —— 它描述的是**走查工具**的能力边界
  （工具点不到原生弹层），这个边界没有因为本轮而消失：下次跑走查，⑧b 在弹层点击这一格
  依然记 `LIMITATION`。本记录表补的是**另一条通道**的证据，不是把那一格涂绿。
* 本表 `modal` 行已于 2026-09-16 填上 ⇒ H3 两类证据齐备，汇报口径升级为
  「支付后界面与**原生确认点击**均已验证（点击由自动化输入产生，见「本轮执行方式说明」）」。
  升级前的口径是「支付后界面已验证，**原生确认点击未验证**」—— 保留在此以便追溯。
* 汇报时 `NOT_RUN` / `LIMITATION` 一律**双句写法**（状态 + 缺什么才有证据），
  见技能 `miniapp-device-walkthrough`「结果分档」一节 —— 单句会被读成"这项过了"。
