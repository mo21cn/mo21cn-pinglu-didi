## 1. 它验证什么、不验证什么

`LLM_MOCK=true` 的规则模板只保证**输出结构与真实模式同构**，它证明不了真实模型
**好不好用**。CI 继续由 fixture 覆盖（无 Key、无网络依赖），本验证包是**CI 之外**
的独立质量测量。

- ✅ 验证：货源解析（`agent/service.py::parse_cargo`）在真实模型上的**逐字段准确率**、
  **是否编造**、**置信度有没有区分度**、**延迟**与**多轮一致性**。
- ❌ 不验证：撮合／支付／状态机等确定性内核（架构红线：它们不经 LLM）；
  也不验证 Agent 作业（ag01/ag02）的信封质量 —— 那需要 DB 夹具，列为下一步。
- ❌ **不代表 PRD 验收通过**：本包产出的是"测量结果"，不是"合格证"。

## 2. 位置与用法

```
backend/scripts/llm_key_doctor.py        # Key 体检（只读）：分清「账户有资源」与「这把 Key 能花到那笔资源」
backend/scripts/h7a_samples.json         # 样本 + 参考答案（机器判分，不需要人工逐条看）
backend/scripts/h7a_model_quality.py     # 跑分脚本（真发请求、会产生费用）
```

Key 走 `backend/.env.local`（`.gitignore` 已排除，**禁止入库**），
因为 config 的 `env_file` 把 `.env.local` 放在最高优先级。

```bash
cd backend
# 0) 先体检：不花调用费，只读三件事（Key 是否被站点认可 / 套餐剩多少 / 能不能真调通）
.venv/Scripts/python.exe scripts/llm_key_doctor.py
# 1) 再看会花多少
.venv/Scripts/python.exe scripts/h7a_model_quality.py --dry-run
# 2) 真跑
.venv/Scripts/python.exe scripts/h7a_model_quality.py --runs 2 --out ../artifacts/h7a.json
```

**第 0 步不是可选的礼貌步骤**：2026-09-16 首次真跑 24 次全被 402 挡下，根因查了很久
（见 §5.1）—— 先花两秒体检，能省掉整轮排查。

退出码三态：`0` = 达标 / `1` = 未达标 / `2` = **没跑成（NOT_RUN）**。
`2` 与 `1` 必须分开 —— "没验成"不能倒推成"不达标"，也不能被读成"跑过了"。

## 3. 样本（12 条）

`h7a_samples.json` 的覆盖点，每条都对应一类真实风险：

| 样本 | 考察点 |
| --- | --- |
| S01 | 完整信息（基线） |
| S02 | 缺目的港 + 缺价格 → **必须置 null** |
| S03 | 缺重量 |
| S04 | 集装箱 + 万元口语（"两万五" → 25000） |
| S05 | 液货枚举（tanker） |
| S06 | 中文大写数字（"八十吨" → 80） |
| S07 | **相对日期（"下周三"）** —— 它是 §5.2 那条主缺陷的探针 |
| S08 | 完全无关输入 → 全 null（**不编造**） |
| S09 | 信息不足（"我想发点货"）→ 全 null |
| S10 | 域外港口（上海/广州不在 13 个枚举内）→ 正确行为是置 null，**不得自创代码** |
| S11 | 中文数字（"三百五十吨" / "四万二"） |
| S12 | 长句 + 干扰（先提"贵港→南宁"的老线路，真实线路是"崇左→贺州"） |

## 4. 评分规则与阈值（**跑之前定死，跑完不许改**）

判分写在 `h7a_model_quality.py::THRESHOLDS`：

| 指标 | 阈值 | 为什么是这个数 |
| --- | --- | --- |
| 逐字段准确率 | ≥ 85% | 12 样本 × 7 字段 = 84 次判定；低于此值解析结果需要人工逐单复核，产品上不划算 |
| 编造次数 | = 0 | 系统提示词写死「信息缺失时置 null，不要编造」，属硬要求，不折算成分数 |
| 置信度校准 | > 0.10 | 答对字段的平均置信度 − 答错字段的；差值为负说明置信度没有区分度，`needs_review` 就是摆设 |
| 调用失败 | = 0 | 输出不可解析 = 该样本完全不可用 |

字段级判定口径：港口/货类**精确匹配**（枚举内）；重量/价格**0.5% 相对容差**；
货名用**关键词包含**（避免"散装水泥"/"水泥"的差异造成假失败）；
**null 与非 null 不一致即判错**，期望为 null 却给出值额外记一次「编造」。

## 5. 真实验证结果（2026-09-16）

**结论：已真实跑通 —— `rc=1`，4 项达标 / 1 项未达标；未达标根因是提示词缺一个输入，不是模型质量。**

第一次真发请求连跑三轮，每轮被一个不同的东西拦住；前两个修掉后，第三轮才是**可信的**测量：

| 轮次 | 退出码 | 拦在哪 | 处置 |
| --- | --- | --- | --- |
| 第 1 轮 | `2` NOT_RUN | 24 次**全部** HTTP 402（Key 与计费方式不匹配） | 换订阅 Key，见 §5.3 |
| 第 2 轮 | `2` NOT_RUN | 24 次里 22 次 `bad_response`（推理模型把思维链内联进 `content`） | 网关剥推理块 + 取围栏内 JSON，见 §6.5 |
| 第 3 轮 | `1` 未达标 | **测出来了**，见 §5.1 | —— |

### 5.1 第三轮实测（12 样本 × 2 轮 = 24 次调用）

| 指标 | 实测 | 阈值 | 判定 |
| --- | --- | --- | --- |
| 字段准确率 | **87.50%**（147/168） | ≥ 85% | ✅ |
| 编造次数 | **0** | = 0 | ✅ |
| 调用失败 | **0** | = 0 | ✅ |
| 置信度校准 | **−0.167** | > 0.10 | ❌ |
| 延迟 | mean 6007ms / p95 9094ms | —— | 记录 |
| 多轮一致 | 2/12 | —— | 记录（按设计无阈值） |

逐字段：`cargo_name` / `cargo_type` / `weight_t` / `origin_port` / `offer_price`
均 **24/24 = 100%**，`dest_port` 23/24 = 96%，**`expect_date` 只有 4/24 = 17%**。

⇒ **`calibration` 与 `expect_date` 是同一个根因**，不是两个独立缺陷：
模型给出**错误年份**时 `field_confidence` 仍报 `1.0`，"答对字段的平均置信度 − 答错字段的"
就被拉成负数。**`calibration` 是 `expect_date` 的影子指标**（见 §5.2）。
三项硬要求（不编造、可解析、准确率）都过了；漂移的是**它不知道今天是几号**。

### 5.2 `expect_date` 17% 的根因：提示词要求按"今天"推算，却从不告诉它今天

`app/modules/agent/service.py::SYSTEM_PROMPT` 写着：

> `"expect_date": string|null,  // 期望装货日期 "YYYY-MM-DD"（口语"下周三"等按今天推算）`

而 `SYSTEM_PROMPT` 是**一个不含任何日期的模块常量**。实测后果分两类：

| 类型 | 样本 | 现象 |
| --- | --- | --- |
| 只说"X月Y日"，年份要靠"今年"补 | S01–S06、S10–S12 | 年份瞎猜：给了 2024 / 2025 / 2027，**错** |
| 相对日期 | S07「下周三」 | 给 `null`（无从推算） |

**这不是"模型不聪明"，而是它缺一个它无法推断的输入**。评分基准本身也假定模型知道年份
（`h7a_model_quality.py::_expected_date` 用 `f"{today.year}-10-08"` 生成参考答案）。

> **产品影响（比 H7a 分数更重要）**：`service.py::_sanitize` 对日期做
> `parsed if parsed >= today else None` —— 猜成过去年份的日期会被**静默清成 null**
> 并标 `needs_review`。也就是说货主打「10月8号装货」，拿到的草稿里**装货日期是空的**。
>
> 修法：把当天日期注入 system prompt。注意 `SYSTEM_PROMPT` 里含字面 `{}`（JSON 示例），
> **不能用 `str.format`**，要用 `.replace()` 占位符；`h7a_model_quality.py` 的取用点要同步改。
> **本轮未改** —— 这是生产提示词的行为变更，需 HO 明确授权后单独一次提交。

### 5.3 第一轮 402 的根因：不是「没买订阅」，是「这把 Key 挂不到那笔资源」（已解决 · 留档）

首版把这行记成「账户余额不足 ⇒ **充值后重跑**」。**方向是错的** —— 账户本来就有
**Token Plan Plus 月度订阅**。三行实查证据（`scripts/llm_key_doctor.py`，只读）：

| 检查 | 结果 | 说明 |
| --- | --- | --- |
| `GET /models` | **200**，8 个模型 | Key 被站点认可，不是无效 Key |
| `GET /token_plan/remains` | **200**，`general` **周窗口剩余 99%** | **账号的套餐额度几乎是满的** |
| `POST /chat/completions` | **402 / 1008** | 可真调用说"资源不足" |

三者并存只有一个解释。按 MiniMax 官方（Token Plan 概要 / 常见问题）：

> 订阅 Key 用于 Token Plan 订阅套餐和已购积分；**订阅 Key 与普通按量计费 API Key
> 相互独立，不能混用**。每位用户在所属的每个团队中都有一把专属订阅 Key。

即平台是**两套凭证、两个钱包**：

| 凭证 | 形态 | 花的是 | 从哪取 |
| --- | --- | --- | --- |
| **订阅 Key** | `sk-cp-`（旁证） | Token Plan 套餐额度 / 已购积分 | 账户管理 / Token Plan |
| **按量计费 API Key** | `sk-api-`（旁证） | 开放平台**账户余额**（wallet） | 接口密钥页 |

当时手上那把是 **`sk-api-` 形态（按量计费）**，调 `/chat/completions` 就从**账户余额**扣；
余额为 0 ⇒ 402，**套餐里剩的 99% 与它无关**。
⇒ 一句话：**「账户有钱」与「这把 Key 能花到那笔钱」是两件事**。
把 402 读成"该充值"会让人去充一笔不需要充的钱。

> **形态判读的依据级别**：官方明确规定"两套 Key 互不通用"，但**未公布前缀对照表**；
> `sk-api-` / `sk-cp-` 的对应关系来自社区实践，属**旁证**。
> 最终判据是控制台上「这把 Key 是从哪一页创建的」。
> 另：`GET /v1/account/balance` 返 **403 `api key is not an admin key`**，
> 说明按量计费那把是普通（非 admin）Key。

### 5.4 处置与验证（2026-09-16 已执行）

1. 复制**订阅 Key**（`sk-cp-` 形态）替换 `backend/.env.local` 的 `LLM_API_KEY`；
2. `scripts/llm_key_doctor.py` 四步全绿 —— **`✅ 端到端可调用`**；
3. **正面证据**：`GET /token_plan/remains` 的 5h 剩余从 **100% → 99%**，
   说明这次调用**确实扣的是套餐额度**。这比"没报错"强 —— 它证明钱真的花到了那笔资源上。

⚠️ **轮换 Key 时踩到的一个陷阱（已修）**：备份出来的 `backend/.env.local.bak-<ts>`
**当时不在 `.gitignore` 覆盖范围内**（`.env.local` 覆盖了，`.bak-…` 没覆盖），
于是**装着旧 Key 的备份文件变成一个未跟踪文件**（`git status` 里是 `??`），
谁顺手 `git add -A` 就把它提交上去了。⇒ 已补 `.env*.bak` / `.env*.bak-*` /
`.env.local.backup*` 三条规则，并把该备份移出仓库到工作区 `secrets-backup/`。

## 6. 本轮顺带发现并已修的缺陷

它们不是 H7a 的目标，但都是"第一次真发请求"才暴露出来的：

1. **HTTP 402 被归类成 `bad_request`**（`app/modules/agent/llm.py`）。
   报出来是"请求被拒绝"，掩盖了"该充值"这个**真正要做的动作**。
   ⇒ 新增 `quota` 分类，且**不可重试**（重试不会让账户有钱），
   见 `RETRYABLE_KINDS` 与 `tests/test_entrust_agent.py::test_quota_error_is_not_retryable`。
   **顺带**：402 的用户可见文案也改了 —— 原来只说"需充值"，但查清 §5.3 后可知
   402 有两种成因（账户余额为 0 / **Key 与计费方式不匹配**），文案须同时指向，
   否则会把人推去充一笔不需要充的钱。
2. **`.env.local` 会污染测试环境**（conftest 只防了微信，没防 LLM）。
   本机为调试真模型配上 `LLM_MOCK=false` 后，
   `test_claim_next_consumes_attempt_and_execute_succeeds` 由 `succeeded` 变 `failed`
   —— 真因是本机改了配置，不是代码坏了，但现象与"并发守卫写错"同形。
   ⇒ conftest 补 `force_llm_mock` autouse（与既有 `force_wechat_mock` 同一套约定）。
3. **`scripts/h7a_model_quality.py` 缺 sys.path 自举** ⇒ 本文件 §2 那条运行命令
   **实际跑不起来**（`ModuleNotFoundError: No module named 'app'`）。
   同目录 `seed_entrust_demo.py` / `seed_entrust_orgpicker.py` 早有同样的补法，本脚本漏了
   —— 教训：**"验证包写完了"与"验证包能按文档跑一遍"是两件事**，
   后者要在干净 shell 里真敲一次才知道。
   ⇒ 已在脚本头部补 `sys.path.insert` 并逐行标 `# noqa: E402`。
4. **代码注释与结论漂移**：`_report` 里仍写着"HTTP 402，本客户端当前归类为 bad_request"，
   而 402 早已经改成 `quota`；同时 `_report` 的"常见原因"仍只说"余额不足"。
   ⇒ 与 §5.3 同批订正。判据变了，读代码的人**总是后到** —— 注释必须跟着改。
5. **`chat_json` 读不懂推理模型的输出** —— **本包最值钱的一条**（`app/modules/agent/llm.py`）。
   MiniMax-M2.7 是**推理模型**：它把思维链直接内联进 `message.content`
   （`<think>…</think>`），答案跟在其后；并且**无视** `response_format={"type":"json_object"}`。
   网关却拿整段去 `json.loads` ⇒ **必然**在 char 0 崩，24 次调用全记 `bad_response`。
   修法：解析前剥推理块（取**最后一个** `</think>` 之后），并从中取第一个完整的顶层
   JSON 对象。
   * **不用**供应商的 `reasoning_split=true`（实测有效）：那是专有参数，
     而"content 夹推理块"在 OpenAI 兼容生态里是普遍现象（DeepSeek-R1 系同形），
     客户端剥一次覆盖全部供应商，网关保持中立；剥下来的推理原文进 `LLMResult.reasoning`
     留档（不参与判分），免得"我们主动要它思考，却把思考直接丢掉"。
6. **只记 `kind` 不记 `message`，等于没记**（`scripts/h7a_model_quality.py`）。
   重跑时 S10 报 `bad_response`，结果文件里只有 `{"id":"S10","run":1,"kind":"bad_response"}`
   —— 光看这个**查不出任何原因**，只能另写探针复现才看到"答案是 markdown 围栏里的 JSON"。
   ⇒ `_call` 改为同时返回错误原文，`errors` 条目加 `message` 并当场打印。
   **错误分类用来路由，错误原文用来定位**，两者缺一不可。

### 6.1 一条方法论教训：`bad_response` 的"围栏"兜底，我判断错了一次

剥推理块之后，我在**同一份真实载荷**上实测了四种组合、都拿到裸 JSON，于是判断
"markdown 围栏只是理论边界情况，没观测到就不做兜底"。重跑 H7a 立刻被 S10 打回来 ——
它的输出是 `</think>` + ```` ```json … ``` ````。

而且**它不稳定**：复现时同一载荷走 `chat_json` 两次都成功（拿到裸 JSON），
绕开网关直发却两次都出围栏。⇒ 教训不是"要多加兜底"，而是：

> **"没观测到"不等于"不会发生"，尤其当样本量是 4 次、而线上是每单一次。**
> 判断该不该做兜底时，依据应当是**目标格式的稳定性**，而不是**我这几次恰好看到了什么**。
