## 1. 结论先行

「已完成历史委托」夹具做不出来的原因**不是缺一条命令**，而是**委托状态机没有终态**：
`claimed` 是死状态（无出边）。⇒ 要做，先扩展状态机 —— 本文档要定死的就是这件事。

## 2. 现状（2026-09-17 实测，附行号）

| 项 | 现状 | 出处 |
| --- | --- | --- |
| 状态取值域 | `draft` / `submitted` / `claimed` / `cancelled` | `assignments.py:44-47` |
| 活跃集 | `ACTIVE_STATUSES = (draft, submitted, claimed)` | `assignments.py:49` |

**只能停在那里**。补一条"结案命令"也**无处可去** —— 这正是阻塞理由要订正的原因。

## 3. PRD 要求（逐条给依据，不是本文档编的）

| PRD 口径（原文要点） | 要求 |
| --- | --- |
| `Assignment`: `draft`, `submitted`, `active`, `completed`, `cancelled`; **separate derived stage and financial closure status** | 有 `completed` 终态；**另有派生的 stage 与独立的财务结案状态** |
| Closure requires completed/cancelled-with-disposition tasks, required delivery evidence, resolved blocking exceptions, approved settlement and explicit disposition of outstanding balances | 结案有**五条硬前置** |
| Open balances keep a visible financial-open state unless a documented authorized credit arrangement permits operational closure | 未结余额保持**可见的"财务未结"** |
| Operational completion and financial closure remain distinguishable | **运营完成 ≠ 财务结案**，必须可区分 |
| Critical unresolved cases block the relevant execution/closure actions；非关键残留只能按 explicit disposition rule 关闭 | 关键未决案件**阻塞**结案；不得 generic skip |
| Reopen a permitted task with a reason and retain the complete history | 允许**重开**，带理由、**保留完整历史** |

## 4. 差距（三条）

1. **缺终态**：实现无 `completed`（PRD 有）。
2. **缺财务维度**：实现只有单一 `status`（PRD 要求运营 / 财务两个维度可区分）。
3. **`claimed` 是死状态**：连取消都不行，与 PRD「经理可在各阶段介入」的灵活性不一致。

## 5. 提议的状态与迁移口径

### 5.1 命名映射（先消歧，避免"两侧都空"的假绿）

PRD 用 `active`、实现用 `claimed`，二者指**同一阶段**（已受理、有认领经理）。
⇒ 建议**保留实现名 `claimed`**，并在接口与前端文档里**显式登记 `active ≡ claimed`**。

理由：改名要同时动表注释、服务常量、前端镜像表、接口文档，代价大且极易留下半改状态；
**把映射写清楚**比改名可控（与 DR-0008 / DR-0017 那类"口径先对齐"的处置一致）。
⚠️ 该映射一旦在前端再现，**必须登记 CI 逐格比对**（规范 3.5）—— 否则就是静默失效。

### 5.2 状态集与迁移图（提议）

```
draft ──submit──> submitted ──claim──> claimed ──complete──> completed
  │                   │                                          │
  └──────cancel───────┘                                ──reopen──> claimed
                                                          （带理由 + 留痕）
```

- 新增终态 **`completed`**、命令 **`complete`**、时间戳 **`completed_at`**；
- 新增重开 **`completed → claimed`**（带理由 + 事件留痕）；
- ⛔ **不新增** `claimed →cancel→ cancelled`（**Q1 裁定**：DEMO-1 不做通用取消）；
- ⛔ **不新增** `completed →cancel→ cancelled`（**Q2 裁定**）；
- ⚠️ **重开不自动获得取消资格**（Q2）：回到 `claimed` 后，取消这条边**依然不存在** ⇒
  重开只能再走 `complete`，或走"已发生事实的独立处置规则"（该规则不在本设计范围）。

### 5.3 两个维度（关键设计）

| 维度 | 字段 | 取值 | 性质 |
| --- | --- | --- | --- |
| 运营状态 | `status` | `draft / submitted / claimed / completed / cancelled` | 命令驱动 |
| 财务结案 | `financial_status` | `not_started` / `open`（有未结余额） / `settled` | **由业务事实派生**（费用／结算／收付／处置记录），**不接受直接 PATCH** |

⚠️ **`closed_with_credit` 已从取值域中移除**（HO 0917 Q3 裁定）。原草案把它列为第四个取值，
HO 指出：**授信意味着"允许延期付款"，不意味着"钱已结清"** —— 把它做成财务状态会让
"钱没到账"在界面上显示成"财务已关闭"，这正是 PRD「运营完成 ≠ 财务结案」要防的那件事。

⇒ 正确落法（三件事分开记）：

| 事实 | 落在哪 |
| --- | --- |
| 运营已完成 | `status = completed` |
| 钱是否已结清 | `financial_status`（派生；有未结余额 ⇒ **`open`，不是已结**） |
| 允许延期付款的书面依据 | **另记**：授信依据 + 批准事实（独立记录，不改 `financial_status`） |

DEMO-1 主路径**先只做余额结清**，完整授信业务不在本轮范围。

PRD 要求「separate derived stage and financial closure status」与「运营与财务可区分」
⇒ **不塞进一个字段**。一个委托允许 `status=completed` 且 `financial_status=open`
（活干完了、钱没结清）—— 这正是 PRD 要表达的那件事。

### 5.4 结案前置（硬门槛，来自 PRD 结案规则）

`complete` 必须**全部满足**才允许；任一不满足即 409，并**逐条报出缺哪条**：

1. **任务**：全部 `completed`，或按 disposition `cancelled`；
2. **交付证据**：要求的证据齐备（缺就是缺，不得"先过再说"）；
3. **异常**：无未解决的**阻塞性（critical）**案件；非关键残留须有显式 disposition；
4. **结算**：已批准；
5. **余额**：未结余额有显式处置 ⇒ `financial_status = settled`。
   ⛔ **授信不再是结案路径**（HO 0917 Q3）：原草案写的"`closed_with_credit` 且带依据"已作废 ——
   授信只说明"允许延期付款"，不构成余额已处置。正确落法是
   **`status=completed` ＋ `financial_status=open`（钱没到账就仍显示未结）＋ 授信依据另记**。

⚠️ 前置检查**不得**留"管理员可跳过"的后门（PRD：Required hard checks cannot be bypassed
by chat, generic "complete", or administrator UI）。

⚠️ **HO 0917 另外点名"不可省略"的四条**（实现切片必须同时交，不是加分项）：

| # | 约束 | 为什么不可省 |
| --- | --- | --- |
| 1 | **客户确认** | 委托是替客户办事，运营方单方面宣布完成会让"完成"失去对客效力 |
| 2 | **幂等** | 重复提交 `complete` 不得产生第二条完成事件、不得重复扣减余额 |
| 3 | **MySQL 并发保护** | 沿用 `revision` + `expected_revision`（现状 `ent_assignment.py:14-18`）；两个写者同时结案必须有一个拿到 409，**不得后者静默覆盖前者** |
| 4 | **五类前置逐条报出** | 不满足时 409 且**逐条列出缺哪条**（现状设计 §5.4 首段），只回"不可结案"会让调用方无法自助 |

### 5.5 Q1–Q4 的 HO 裁定结果（2026-09-17，**已裁，不再是待决**）

| # | 问题 | **裁定** | 理由（HO 原文要点） |
| --- | --- | --- | --- |
| **Q1** | `claimed` 是否可 `cancel`？ | **否 —— DEMO-1 暂不新增通用取消** | 已发生采购、履约、费用后的终止**需要独立处置规则**，不是加一条状态边即可 |
| **Q2** | `completed` 之后能否 `cancel`？ | **否**。只允许有权限、有理由的**纠错重开**（`completed → claimed`）；**重开不自动获得取消资格** | 完成后直接取消语义矛盾；重开是纠错，不是"回到可以随便取消的状态" |
| **Q3** | `financial_status` 派生还是可写？ | **派生**（由费用/结算/收付/处置事实），**不允许直接 PATCH 一个状态就宣称结清**；授信**另记**、不改财务状态 | 授信＝允许延期付款，≠ 钱已结清 |
| **Q4** | 本设计是否进 S4？ | **是，必须进**。交付：完成状态 + **真实结案命令** + **受控重开** + 结案前置检查 + 并发保护 | 本就是**既有合同范围**，不再等待"是否做"的二次批准 |

⚠️ **Q1/Q2 的"否"不等于"委托永远不能终止"** —— 它说的是：**终止不是一条状态边能表达的**，
需要一套独立的处置规则（已发生事实怎么收尾）。那套规则**不在本文档范围**，
DEMO-1 期间 `claimed` 的委托仍无取消出口（与现状一致，**不是新引入的缺陷**）。

### 5.6 迁移口径（**Q4 已裁为"进"** ⇒ 实现切片按此执行）

- **新增迁移条目**，**不改已发布条目**（规范 3.4）；
- 新增列：`completed_at DATETIME NULL`、`financial_status VARCHAR(16) NOT NULL DEFAULT 'not_started'`；
  - ⚠️ `financial_status` 取值域是 **`not_started` / `open` / `settled` 三个**（§5.3 已移除
    `closed_with_credit`）；授信**不加列、不改这个状态**，走独立记录；
- 索引：既有 `(owner_user_id, status)` / `(org_id, status)`；"历史委托"列表建议加 `(status, completed_at)`；
- `status` 列注释同步为五个取值；
- **数据迁移**：既有 `claimed` 行**保持 `claimed`**（HO：旧数据**不推测完成**），
  `financial_status` 一律 `not_started`；
- 幂等、可重跑（按迁移执行器既有约定）；
- ⚠️ **`_CANCELLABLE` 保持 `(draft, submitted)` 不变**（Q1 裁定）⇒ 迁移**不扩大**可取消集。
