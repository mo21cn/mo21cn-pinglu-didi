# DR-0004：工具链版本锁定（`ruff` 精确版本）

- 日期：2026-09-13
- 提出人：`chore/ci-gates`（开启 `ruff format --check` 门禁时发现）
- 决策人：HO
- 状态：**已采纳**
- 关联：PR #50（`chore/ci-gates`）；规范四「CI 门禁」——禁止对必需检查设 `continue-on-error`；`AGENTS.md` 硬约束

## 背景

`backend/requirements.txt` 中工具链依赖为区间约束：

```
ruff>=0.6,<1.0
mypy>=1.11,<2.0
```

`ruff` 至今仍是 `0.x`。按语义化版本约定，`0.x` 的**次版本升级允许不兼容变更**，而 `ruff format` 的排版风格恰恰在次版本间持续调整（换行策略、字符串归一、魔法尾逗号等）。这造成一个具体而高频的故障：

1. CI 每次运行都 `pip install -r requirements.txt`，装的是**当时最新的** ruff；
2. 开发机上的 ruff 是**某一次安装的**版本；
3. 两者不一致时，`ruff format --check` 在 CI 变红，而本地是绿的（或反之）。

后果不只是"CI 红了很烦"：

- **误判**：门禁变红会被当成"这次改动引入了格式问题"，开发者会去做无意义的手动排版，甚至回滚正确代码。
- **诱发违规**：反复的假红会诱导用 `--no-verify`、给检查加 `continue-on-error`、或删掉门禁来"解决"——这三条都是规范四明令禁止的。**一个会随机变红的门禁，比没有门禁更糟**，因为它会训练团队绕过门禁。

`chore/ci-gates` 已用 **ruff 0.16.7** 完成一次性全量格式化（独立 `style` 提交，61 文件）。这个版本就是当前全部代码的格式基准，必须固化下来。

## 候选方案

| 方案 | 描述 | 优点 | 缺点 | 风险 |
| --- | --- | --- | --- | --- |
| A | 精确锁定 `ruff==0.16.7` | CI 与本地永远同版本；门禁结果确定；升级变成一次显式、可评审的动作 | 需要人工发起升级；长期不升会落后于新规则 | 落后可通过定期升级 PR 消解；升级成本极低（重跑格式化即一个 `style` 提交） |
| B | 维持区间 `>=0.6,<1.0` | 自动获得最新规则 | 门禁结果随上游发布漂移；故障时间与发布时间耦合，排查成本高 | 会在最不合适的时候（赶发布、赶验收）变红 |
| C | 收紧上界 `>=0.6,<0.17` | 比 B 稳定 | 仍允许 0.6～0.16 之间的风格漂移；上界到期后问题原样复现 | 只是延后问题，并未消除 |

## 决策

选择：**方案 A —— `ruff==0.16.7` 精确锁定**。

理由：

1. **门禁的价值来自确定性**。`ruff format --check` 是规范四要求的必需检查，不允许 `continue-on-error`。那么它必须给出可复现的结果，否则门禁本身失去意义。
2. **升级是显式动作而非隐式漂移**。锁版本后，升级 = 一张独立 PR（改一行 + 重跑全量格式化 + 单独 `style` 提交），可以安排在任何方便的时间点，不会在某次无关的 feature 分支上突然炸掉。
3. **0.16.7 已是事实基准**。全量格式化就是用这个版本做的，锁定它意味着**不需要再做任何额外改动**，存量代码即刻与门禁一致。

**`mypy` 仍保持区间 `>=1.11,<2.0`**，这是有意保留的差别：

- `mypy` 升级带来的新增报错，绝大多数是**真实的类型问题**，CI 变红是有价值信号，应当被看见并修掉；
- `mypy` 不像 formatter 那样存在"风格漂移"——同一个代码库在相邻版本间不会因为排版口味变化而整体变红；
- 因此 `mypy` 区间约束的收益（自动获得更严格检查）大于成本。若将来出现确凿的假阳性漂移，再单独立 DR 处理。

## 影响

- 后端：
  - `backend/requirements.txt`：`ruff>=0.6,<1.0` → `ruff==0.16.7`。
  - 开发机需保证本地 ruff 与锁定版本一致，否则本地绿灯但 CI 红灯（见"验证方式"）。
- 前端：无影响。
- 数据库迁移：无影响。
- 功能开关：无影响。
- 对旧流程的影响：无。仅约束开发工具链版本，不触碰运行时依赖（fastapi / sqlalchemy / pydantic 等均保持区间）。
- 需要同步修改的文档：
  - `AGENTS.md`：补"本地 ruff 版本必须与 `requirements.txt` 锁定版本一致"的硬约束。
  - `.github/workflows/ci.yml`：格式门禁步骤的注释由"若需固定格式化风格请锁定 ruff 版本（见 DR-0004）"改为指向已锁定的事实。
  - `docs/entrust/00-基线对齐报告.md`：DR-0004 标记已采纳。

## 回退方式

- **代码回退**：把 `requirements.txt` 改回 `ruff>=0.6,<1.0` 即可，一行改动，无其他耦合。
- **数据兼容性**：无。工具链依赖不参与运行时，也不进生产镜像的运行时路径。
- **外部能力**：无。不依赖任何外部服务或 Key。

**注意**：回退后 `ruff format --check` 将重新变得不确定。回退本决策等于接受 DR-0004 背景中描述的故障模式，需要在回退说明中写明这一点。

## 验证方式

| 命令 | 预期结果 |
| --- | --- |
| `pip install -r requirements.txt` | 安装到 ruff 0.16.7 |
| `ruff --version` | 输出 `ruff 0.16.7`（本地与 CI 一致） |
| `ruff format --check app tests` | 退出码 0，无任何待格式化文件 |
| `ruff check app tests` | 退出码 0 |
| CI job `backend` | `Lint（ruff check）` 与 `格式门禁` 两步均绿 |

**升级流程（后续需要升 ruff 时）**：

1. 独立分支改 `requirements.txt` 的版本号；
2. `ruff format app tests` 全量重跑，**单独成一个 `style` 提交**（与版本改动分开，便于 review 时区分"格式变化"与"依赖变化"）；
3. 提交 PR 说明升级理由与新版本带来的规则变化。

未执行项及原因：无。本机已用 0.16.7 完成 lint / format / mypy / pytest 全量验证，CI 由 GitHub Actions 在推送后自动执行。
