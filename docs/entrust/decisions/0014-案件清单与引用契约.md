## 0. 结论速览

DR-0013 §4 把 UI-04 的 `exceptions` 队列定为「**可点击的只读案件清单**（点进去到 UI-08）」，
但**没有写这份清单的数据从哪来**。落到实现时发现三个缺口同时存在：

1. `GET /exceptions` 的 `assignment_id` 是**必填** —— 只有「单委托」视角，没有组织视角；
2. `AssignmentOut` 里**没有任何**异常或阻断字段，`assignments.py` 也不碰案件 ——
   组合级页面拿不到「哪些委托有案件」；
3. `ExceptionCaseOut` / `DetailOut` 里**没有能力字段** —— 界面无法知道「当前用户能不能处置这一宗」。

本记录按 HO 裁决把这三处**一次补齐**，并冻结四件契约：

| # | 冻结对象 | 一句话 |
| --- | --- | --- |
| 1 | `GET /exceptions` **双视图参数契约** | 保留单委托用法；新增 `view=org`，两视图**参数分别校验**，**不允许无范围全表查询** |
| 2 | `ExceptionCaseListItem` | UI-04 一行一宗案件，**直接打开 UI-08**；**委托计数不得替代清单** |
| 3 | `CaseRef` | UI-05 的 `exceptions` 槽引用，**独立形状，不复用 `artifact_refs`** |
| 4 | `ExceptionCaseCapabilities`（`capabilities.can_*`） | UI-08 的按钮可用性；**与写命令共用权限与状态判定**；A2 未实现动作**恒不可用** |

**顺序**：本记录先定契约，**再**推进 UI-08（4a）与 UI-05 引用（4b）——
不等详情页做完才决定引用形状。

## 1. 背景：为什么不能靠「前端逐单拉取后拼接」

组合工作台（UI-04）的语义是**跨委托**的。若前端拿组织内的委托列表逐单调
`GET /exceptions?assignment_id=N` 再拼接，会产生四个后果：

1. **授权判定被搬到前端** —— 拼接的前提是「这单我能不能看」，而可见性判定必须且在服务端；
2. **计数与分页失去意义** —— 逐单拉取后拼接的 `total` 是前端算的，页码也不是服务端的页码；
3. **N+1 请求** —— 组织内委托数量直接变成请求数；
4. **跨组织泄漏面** —— 一旦某次请求的 `assignment_id` 来自不可信上下文，拼接结果会混入他组织数据。

因此 HO 裁决明确：**授权、scope 筛选在分页和计数前生效；禁止前端逐单拉取后拼接**，
并且**委托计数不能替代清单**（计数只能说明「有」，不能让人点到那一宗）。

## 3. 决策与契约

### 3.1 `GET /exceptions` 双视图参数契约

```
GET /api/v1/entrust/exceptions
```

| 参数 | 默认视图（单委托，既有） | `view=org`（新增） |
| --- | --- | --- |
| `view` | 缺省或空串 | **只接受 `org`**；其他取值 → `400` |
| `assignment_id` | **必填** `ge=1` | **禁止出现** → `400` |
| `org_id` | **禁止出现** → `400` | **必填** `ge=1` |
| `scope` | **禁止出现** → `400` | 可选，`unclosed`（默认）/ `all` |
| `status` | 可选（既有） | **禁止出现** → `400`（用 `scope` 表达开闭） |
| `kind` | 可选（既有） | 可选（同取值域） |
| `page` / `size` | 既有 | 既有（`size` 上限 100） |

三条硬约束：

1. **参数分别校验**：默认视图不接受 `org_id` / `scope`；`view=org` 不接受 `assignment_id` / `status`。
   混用一律 `400`（**不**静默忽略 —— 静默忽略会让「我筛了却筛不掉」变成一个查不出的 bug）。
2. **不允许无范围全表查询**：默认视图缺 `assignment_id` → `422`；`view=org` 缺 `org_id` → `422`。
   **明确拒绝**「不传 `org_id` 就返回我所属全部组织」的用法 —— 那正是跨组织拼接。
3. **作用域是单个组织**：`org_id` 只接受**一个整数**（不是列表）。响应中不得出现
   `org_id != 查询 org_id` 的记录，`total` 也必须在**同一 `WHERE`** 下计算。

响应模型：

| 视图 | 模型 | 说明 |
| --- | --- | --- |
| 默认 | `ExceptionCaseListOut`（既有） | `items: list[ExceptionCaseOut]`，**形状不变** |
| `view=org` | `ExceptionCaseOrgListOut`（新增） | `{ total, page, size, org_id, items: list[ExceptionCaseListItem] }` |

- `scope=unclosed`（默认）：`status != 'closed'`；`scope=all`：不加开闭过滤。
- 排序：`ORDER BY id DESC`，与既有单委托视图**同一口径**（不引入第二个排序规则）。
- **授权先于分页与计数**：先经 `authz` 判定，再执行查询。判定链见 §3.5。

### 3.2 `ExceptionCaseListItem`（UI-04 清单项）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `case_id` | `int` | 案件主键（与 `ExceptionCaseOut.case_id` 同名同义） |
| `assignment_id` | `int` | 归属委托 —— 界面要能说清「是哪张单的」 |
| `kind` | `str` | `exception` / `change_request` |
| `title` | `str` | 一行标题 |
| `status` | `str` | 状态取值域同 DR-0013 §3.4 |
| `impact_kind` | `str` | 影响类型 |
| `blocking` | `bool` | **由 `is_blocking` 唯一判据算出**（§3.6） |
| `due_at` | `str \| None` | 可选；未知保持未知 |
| `updated_at` | `str` | 排序与「最后更新」展示 |
| `affected_count` | `int` | 受影响项条数（分页后对当前页批量求长，不做 N+1） |

**刻意不含**：`org_id`（视图已限定单组织，回传无信息量）、`severity`、`cause`、
`decision` / `resolution` / `closure` / `events` / `affected` 明细。

> **为什么不含 `severity`**：C3 的用意是堵住「按严重度决定流程」的联想。清单里给了它，
> 界面迟早会拿它排序或加重；而清单**已经有**表达轻重的正确字段 —— `blocking`（流程约束）
> 与 `impact_kind`（影响类型）。严重度属详情页的业务判断，留在 UI-08。

### 3.3 `CaseRef`（UI-05 `exceptions` 槽的引用）

```
CaseRef = { case_id: int, kind: str, title: str, status: str, blocking: bool }
```

**与 `artifact_refs` 平行但独立** —— 这是 HO 的明确要求，理由不是「风格统一」：

| | `artifact_refs` | `CaseRef` |
| --- | --- | --- |
| 键 | `artifact_id` / `artifact_type` / `label` / `revision_no` | `case_id` / `kind` / `title` / `status` / `blocking` |
| 「版本」语义 | **精确版本**（`revision_no`，工作台与对话引用同一对 `(artifact_id, revision_no)`，PRD 第 187 行） | **无**。案件的 `revision_no` 是乐观锁版本号，不是「看哪一版」 |
| 消费者 | 成果页（`artifact_id` 进深链） | 案件页（`case_id` 进深链） |

⇒ **禁止**为了复用前端的渲染分支，把案件伪造成 `artifact_refs` 的形状
（例如 `{artifact_id: case_id}`）。字段名不同是**刻意的防线**：
一旦共用键名，前端就会用一个渲染分支吃两种数据，而两边的语义差异
（有版本 / 无版本）会在某次改动里静默错位。前端按**槽位 `key`** 选择渲染分支。

**深链参数命名**：UI-08 的 `routes.js` 深链参数为 `case_id`（与 `CaseRef.case_id` 同名），
页面 `onLoad` 用 `case_id` 直接请求 `GET /exceptions/{exception_id}`。
API 路径里的 `exception_id` 是**既有**命名（不改），二者是**同一个值** ——
这处不一致由本文档显式记录，避免被当成 bug「顺手统一」而牵动已发布路径。

### 3.4 `ExceptionCaseCapabilities`（UI-08 的能力字段）

挂在 `ExceptionCaseDetailOut`（`GET /exceptions/{id}`）上，**不挂**在 `ExceptionCaseOut` 上：

- 理由：capabilities 是**调用者相关**的（不是案件数据），挂进共享模型会污染白名单投影，
  并让列表项也带一份「我能做什么」；
- 写端点（登记 / 决定 / 关闭 / 重开）仍返回纯数据的 `ExceptionCaseOut`，界面写完后重新拉详情刷新能力。

| 字段 | 判定（**必须与写命令同源**） |
| --- | --- |
| `can_add_link` | 有写权限 **且** 案件未关闭 |
| `can_remove_link` | 有写权限 **且** 案件未关闭 **且** `affected` 非空 |
| `can_decide` | 有写权限 **且** 案件未关闭 **且** 当前状态下存在允许的决定转移 |
| `can_close` | 有写权限 **且** `allowed_closure_dispositions(kind, status)` 非空 |
| `can_reopen` | 有写权限 **且** `status == closed` |
| `can_apply_change` | **恒 `false`** —— 「应用变更」属 A2，本片未实现 |

> **`can_decide` 为什么要额外排除「已关闭」**（实现期细化，用例
> `test_can_decide_is_false_on_closed_case_even_though_transition_exists` 钉住）：
> 状态机里 `closed → open` **是**合法转移，只按「存在允许的转移」判会让
> 已关闭案件的能力位亮起「记录决定」。但那条转移归 `reopen` **专有命令**所有 ——
> 它写 `reopened` 事件，而走 `decide` 会写成 `status_changed`，**审计形态不同**。
> 界面同时亮出「记录决定」与「重开」，只会把人引到审计不一致的那条路上。

三条实现纪律：

1. **不自建第二份权限判据**。写权限判定只有 `_assert_can_write` 一处实现，
   `can_write_case(...)` **包住它**并把结果折叠成布尔给 capabilities 用。
   方向是「包」而不是「抽出来再让 `_assert_can_write` 调它」：后者要求
   `_assert_can_write` 先拿到布尔、再自行判断该抛 404 还是 403，
   于是成员资格会被判第二遍 —— 那才是第二份实现。原因区分因此仍完整保留。
2. **不硬编码状态名**。「状态维」一律取 `allowed_transitions(kind, status)` 与
   `allowed_closure_dispositions(kind, status)` 的结果；DR-0013 §3.4 的状态机改了就跟着变。
3. **服务端只是如实投影**。界面据 `can_*` 隐藏按钮**不是**权限控制 ——
   写端仍独立复核权限、证据、幂等与版本（`can_*` 与写端不一致时，**以写端为准**；
   界面收到 403/409 要提示，不能静默）。

### 3.5 授权与作用域（继承既有单一入口，不另建一层）

`view=org` 的判定链，顺序不可调换（与 `authz.py` 模块文档同一口径）：

1. 解析调用者上下文 `resolve_context(user_id)`；
2. **组织成员资格**：`org_id ∉ context.org_ids` → **404**（不区分「不存在」与「无权知晓」）；
3. **动作权限**：`context.can(PERM_VIEW, org_id=org_id)` 为假 → **404**；
4. 通过后执行查询，`WHERE org_id = :org_id [AND status != 'closed']`。

**两个维度不可混用**（DR-0008 的硬约束）：

- 读（本视图）用 **`org_id=` 维度** —— 与该组织对委托单的读可见性口径一致
  （`authz.assert_can_view_assignment`）；
- 写（capabilities 与写命令）用 **`owner_user_id=` 维度** —— 权限必须由**该货主**的生效授权提供。

⇒ **甲组织的权限不能与乙货主的授权拼接放行**。例如 U 在甲组织是 `manager`（有
`entrust:task:dispatch`），但乙货主只给甲组织授了 `entrust:view`：U 能**看**乙的委托案件，
却**不能**处置 —— `can_*` 全 `false`，写请求 `403`。

> **「只读用户」指的是授权内容，不是组织角色**（实现期发现，用例
> `test_capabilities_false_when_the_grant_lacks_dispatch` 钉住）：组织角色为 `member`
> **不等于**只读 —— 若该货主在授权里给了 `entrust:task:dispatch`，这位成员照样能处置。
> 写权限的判据只有一条，落在货主授权上。验收 3 与验收 4 因此是**同一个**判据的两种取值，
> 而不是两条独立规则；用例把两种角色放在同一个场景里一起断言，避免日后有人
> 重新引入「按角色判能力」。

### 3.6 阻断判据（复用，不复制）

`ExceptionCaseListItem.blocking` 与既有全部阻断路径**共用 `is_blocking`** 一个函数
（DR-0013 §3.3）。**不**把判据翻译成 SQL：`rejected` 在两种 `kind` 下语义相反，
翻译等于写出第二份实现，而两份实现迟早出现「执行门禁认阻断、清单不认」。

候选集在 Python 侧过滤（`_blocking_only`）—— 与案件数同量级，不构成性能问题。

### 3.7 顺序

本记录即「先定的接口契约」。4a（UI-08 只读页）与 4b（UI-05 引用可点）在其后推进，
**无需等待详情页完成才决定引用形状**（`CaseRef` 已在 §3.3 冻结）。

## 4. 影响

- **后端**

## 5. 回退方式

**代码回退**：

- `GET /exceptions` 的 `view=org` 分支独立，移除即回到只有单委托用法（默认分支未动）；
- `capabilities` 是**附加字段**，移除不影响案件数据；界面据旧的「本地猜测」退化，
  但写端权限不受影响（服务端始终是执行点）；
