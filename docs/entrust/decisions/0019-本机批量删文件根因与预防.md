# DR-0019：本机「工作区批量删文件」故障的根因定档与预防措施

- 日期：2026-09-19
- 提出人：开发代理（应 HO 指令：暂停项目先彻查「工作文件夹不停自动删文件」）
- 决策人：HO
- 状态：**已采纳**（HO 2026-09-19 指令：「本次核查批量删除文件根因的预防措施写入文档」）
- 关联：DR-0009（走查工具链）、技能 `git-pr-squash-flow`；本记录不改动任何产品行为

## 背景

开发过程中反复出现「**工作区里一批已跟踪文件被物理删除**」，7 天内 6 起：

| 日期 | 触发操作 | 被删的已跟踪文件 |
| --- | --- | --- |
| 09-13 | `git checkout develop` ＋ `git merge --ff-only` | 91 |
| 09-14 | `git merge develop`（只改 4 个文档） | 38 |
| 09-14 | 同类（另一处记录） | 91 |
| 09-17 | 切 `S3-contract-derive` | 223 |
| 09-17 | 切 `S3-capacity-confirm` | 161 |
| 09-17 | `git rebase --onto`（并附带 HEAD 被 detach） | 173 |
| 另 | `PUT /pulls/{n}/merge` 带 `--delete-branch` | 「上百个」 |

另有更危险的两种变体：`refs/heads/<子目录>` 整目录被清 ⇒ **HEAD 变 unborn**；
`~/.workbuddy/.../envs/default` 的 `Lib/site-packages` 整目录消失（装的包突然 `ModuleNotFoundError`）。

**为什么必须现在定档**：长期把它当成「玄学故障」会导致两种坏后果 ——
① 为了躲它而放弃「一个切片一个分支」的正常工作方式；② 把真实的删除误判成"环境噪声"而漏救。

### 侦察结论（2026-09-19，证据一次性列清）

**排除项（都做了实测，不是推理）**

| 嫌疑 | 结论 |
| --- | --- |
| 360 残留 / 第三方文件系统过滤驱动 | ❌ E: 卷只挂 `applockerfltr`/`bfs`/`Wof`/`FileInfo`，**全部微软签名**；全机 **0 个第三方内核驱动** |
| 杀软 | ❌ `SecurityCenter2` 的 AV 列表为空，Defender 未安装 |
| 恶意进程 | ❌ 对象访问审计（Security 4663，带进程名）在内 20 分钟只抓到 `git.exe` 删自己的 `.git/index.lock`；30 个金丝雀文件全部存活 |
| git 钩子 | ❌ `.husky/_/` 的 `post-checkout`/`post-merge` 只是 39 字节存根，`pre-commit` 只做 grep |
| 项目脚本 | ❌ 全仓无 `git clean` / `rm -rf` / `shutil.rmtree` |
| 其他本机 Agent | ❌ AutoClaw / MiniMax / Claude Cowork / OpenClaw 的配置里**零处**引用本仓库 |

**已复现的最小触发**（本机 `E:\pinglu-didi`，一次即中）

```
git checkout -b <临时分支>
git rm --pathspec-from-file=<40 个 docs/entrust/*.md> --pathspec-file-nul
git diff --name-only --diff-filter=D      # → 32 个【没被 rm 的】docs/** 文件已从工作区消失
```

- **被删的是「整棵 `docs/` 子树」里与本次操作无关的已跟踪文件**，不是随机文件；09-14 那 91 个也**全在 `docs/**`**。
- 删除发生在 `git rm` / `git commit` / `git checkout` 这类**写工作区**的步骤里，与"是否切分支"无关；
  **只动 1 个文件的小改写不触发**。
- 因此两条历史判断被推翻：①「360 卸干净就会好」——不成立；②「是 git 删完但写回被打断」——**不成立**
  （git 不会删自己没改写的文件，而实测被删的正是"没被触碰的文件"）。

⇒ **定档：真实缺陷、约每天 1 次、触发面是"过量写工作区"、作用面是 `docs/` 子树；
但删除集有界且全部可从 refs 恢复**（6 起 100% 恢复、零内容丢失）。
残余风险只在一个位置：**故障删完之后若执行 `git add -A && git commit`，删除会被当成有意改动提交进去**。

## 候选方案

| 方案 | 描述 | 优点 | 缺点 | 风险 |
| --- | --- | --- | --- | --- |
| A | 只靠纪律：每次 git 写操作后人工只读复核 ` D`，发现就 `checkout HEAD --` 取回 | 零代码 | 依赖"人记得"，且**故障发生在提交前**时来不及 | 中：一次漏做就可能把删除提交进 PR |
| B | **自动护栏**：在 git 钩子里检测 ` D`（工作区缺失、索引仍在）≥5 个即自动从 HEAD 恢复 | 把"记得复核"变成"机器必做"；覆盖 pre-commit/pre-push（提交与推送前就拦住） | 本机专属、需维护；钩子文件不入库 | 低：阈值 + 只恢复 ` D`，不动 `D ` |
| C | 放弃 git 写操作，改用纯 API 路径 | 完全绕开触发面 | 日常工作不可行（提交/切分支/合并都要用） | 高：不现实 |

## 决策

选择：**B ＋ 保留 A 的纪律**。

理由：
1. 触发面是"写工作区"，**无法从流程上完全消除**（提交、切分支、合并都要写工作区）；
2. 被删集合**有界且可从 HEAD 恢复** ⇒ 自动化恢复是低风险高收益；
3. 覆盖点选在 **pre-commit / pre-push / post-commit / post-checkout / post-merge / post-rewrite** ——
   前两者正好拦住"把删除提交/推出去"这条唯一会真丢内容的路径；
4. 阈值取 ≥5 个 ` D`：故障每次 38–223 个，而人工"有意删 1–2 个文件"不会被误回滚；
5. 只自动恢复 ` D`（工作区缺失、索引仍在）；`D `（索引级删除）**只记日志并在 stderr 点名**，
   因为索引级删除也可能是有意的（例如本章复现里那 40 个 `git rm`）。

落点：`E:\pinglu-didi\.husky\_\_rollback_guard.sh`，由 `.husky/_/` 下的 6 个钩子调用。
⚠️ **它在 `.husky/_/` 内，而该目录被 `.husky/_/.gitignore` 的 `*` 排除** ⇒ 本机专属，
不出现在 `git status` / diff / 任何 PR 里（**有意为之**：这是机器级 workaround，不是仓库资产）。
日志：`E:\PL-Ship-Broker\.workbuddy\_rollback_guard.log`。

### 接线两个坑（都让护栏静默失效，各自都踩过一次）

1. husky 存根是 `. "$(dirname "$0")/h"`，而 `h` 内部有 **`exit 0`**
   ⇒ **追加在它后面的行永远不会执行**。护栏调用必须放在**它前面**，且用
   `sh <脚本> <hook名> || true`（子进程隔离，不受 `h` 的 `exit` / `cd` 影响）。
2. **`git` 是 Windows 程序、打不开 MSYS 路径**：`mktemp` 给 `/tmp/...`，
   于是 `--pathspec-from-file=/tmp/...` 报 `fatal: could not open ... for reading`；
   而 stderr 被重定向掉 ⇒ **静默恢复 0 个文件**。清单必须落在 **Windows 风格路径**（`E:/...`）。

## 影响

- 后端：无（不改产品代码）
- 前端：无
- 数据库迁移：无
- 功能开关：无（`ENTRUST_ENABLED` 等一概不动）
- 对旧流程的影响：**无**。护栏只在"工作区缺失 ≥5 个已跟踪文件"时动作；
  正常提交、正常切分支、有意的单文件删除都不触发。
  ⚠️ 唯一的语义变化：**本机**上"故意删掉 5 个以上已跟踪文件后立刻 `git commit`"会被护栏拦回工作区 ——
  这在本仓的工作流里没有正当用法（批量删除应通过正常提交去做，那时索引级删除是 `D ` 而非 ` D`）。
- 需要同步修改的文档：本记录；`docs/entrust/01-决策记录模板.md` 的登记表；技能 `git-pr-squash-flow`（本机实证节）。

## 验证方式

1. **复现**（证明故障仍存在，也证明护栏有必要）：
   `git checkout -b <临时分支>` → `git rm --pathspec-from-file=<40 个 docs/entrust/*.md> --pathspec-file-nul`
   → `git diff --name-only --diff-filter=D` 应为 **32** 个**未参与 `git rm`** 的 `docs/**` 文件。
2. **护栏生效**：上一步之后 `git commit`，日志 `_rollback_guard.log` 应出现
   `AUTO-RESTORED worktree_missing=32 remaining=0`。
3. **收尾判据**（三条合看）：`git ls-files` 数量回到 444；`git status --porcelain` 行数为 0；
   `git rev-parse refs/heads/develop` 与 `refs/rorigin/develop` 相等。
4. **未执行项**：① 护栏**不覆盖** ref 被删（`refs/heads/<子目录>` 整目录消失、HEAD 变 unborn）——
   那条仍靠"删分支前先 `symbolic-ref` 再 `update-ref -d` 并逐条比对 ref 名"，
   见技能坑 24/44/51；② 未验证 `post-rewrite` 在真实 rebase 下的行为（本机 `rebase` 不可用，见坑 13b）。

## 追加（2026-09-19 晚）：**untracked 文件会被永久删除** —— 密钥事故与护栏扩展

**事故**：核实模型 Key 时发现 `backend/.env.local`（**被 gitignore、内含可用订阅 Key**）**已缺失**；
E: 与 C: 回收站里**都没有它的 `$I` 元数据**（E: 4364 条、C: 0 条）⇒ 与本故障机制一致：
**本故障用的是普通 `unlink()`，不经过回收站**（也正因如此，WorkBuddy 的 safe-delete shim 拦不到它）。
Key 最终从一份**无关的 recon 快照**（`E://PL-Ship-Broker//.workbuddy//_b_recon3.txt`，2026-09-16）
里找回，与 `memory/2026-09-16.md` 记的指纹（`sk-cp-…`／125 字符）**逐字一致**；
还原后 `backend/scripts/llm_key_doctor.py` **四步全绿**（`/models` 200、套餐 5h 剩余 100%、
`chat/completions` 200）。

**为什么原来的护栏救不了**：它只从 **HEAD** 恢复 **tracked** 文件（`git diff --diff-filter=D`）。
untracked 文件不进 `git diff` ⇒ **既不会被发现、也无法恢复** ⇒ 静默且永久丢失。
密钥、本地覆盖配置（`.env.local`）、未入库的临时资产都属于这一类。

**护栏扩展**（`E://pinglu-didi//.husky//_//_rollback_guard.sh`，本机专属、不入库）：

- ⭐ **不用人工维护清单** —— 判据是**派生的**：扫描 `.`／`backend`／`miniapp` 下的 `.env*`，
  凡**被 gitignore** 的都要有受保护副本（tracked 的由 HEAD 恢复，不需要副本）；
  副本名按路径编码（`/` → `_`），恢复目标无需清单即可还原；
  非 `.env*` 命名的新密钥留了逃生口：路径逐行写进 `secrets-backup/_extra.list`；
- 每次钩子运行时：文件**在** ⇒ 若与受保护副本不同则刷新副本；文件**不在** ⇒ 从副本**自动恢复**并高声报错；
- 日志只记 **长度 ＋ POSIX `cksum`**，⛔ **不落任何密钥材料**（形如 `key_len=125 key_cksum=…`）。

**实测（注入验证，两条判据都成立）**：把 `.env.local` 移走 ⇒ 钩子报
`SECRET-RESTORED backend/.env.local <- …bak-latest` ⇒ 恢复后与副本**逐字节一致**（`cmp -s` 通过）。
受保护副本在 `E://PL-Ship-Broker//.workbuddy//secrets-backup//`（git 之外、且不在工作区内）。

⚠️ **仍未覆盖**：① 副本与被保护文件**同机** —— 整盘/整机级损坏仍会一起失去；
② **非 `.env*` 命名**的新密钥不会被自动扫到（逃生口见上）；**同名文件若含 `_`** 会让路径编码有歧义；
③ 本故障的**触发条件仍不可预测**（本次与 git 工作区改写同时发生，但因果关系未证实）。
