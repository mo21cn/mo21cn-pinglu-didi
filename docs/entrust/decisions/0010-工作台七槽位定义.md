# DR-0010：委托工作台「七个业务槽位」的枚举口径

- 日期：2026-09-13
- 提出人：开发（委托支线 S2 前端切片前置侦察）
- 决策人：HO
- 状态：提议
- 关联：UI-05（单张委托工作台，R1 主战场）、UI-04（三队列）、UI-02（侧栏专业入口）；R11（无 AI 能力的槽位不得出现空 Agent 入口）；AC-02、AC-21

## 背景

交付计划的 UI-05 行统一描述为「**7 个业务槽位 = 7 类聚合的投影**」，并给出每槽要显示
「当前成果／未决问题／下一责任方／最后更新」，以及 R11 的约束「**无 AI 能力的槽位不显示 Agent 操作，只给完整人工操作**」。
但**七个槽位具体是哪七个，在所有文档与设计稿里都没有枚举**：

- `MVP开发与交付计划_…v1.5.1.md`：只写「7 个业务槽位」，数据来源列写的是 5 项
  （委托 / 任务 / 成果 / 采购 / 附件）—— **5 个数据来源 ≠ 7 个槽位**，口径不闭合；
- `Entrusted_Shipping_Agent_IM_PRD_v1.0.md`：全文检索「槽位」**无命中**；
- 设计稿 `wt/L3/design/prototypes/dual-role-wireframes-v2.png`（等 5 张）：是既有「平陆滴滴打船」双身份原型
  （身份选择 / 货主端 / 船东端 / 发布货物 / 发布空船 / 我的订单），**不含委托工作台**；
- `平陆运河/工作流逻辑示意.jpg`：是 Agent IM 的交互范式参考（侧栏 → Agent 列表 → 独立对话 → 结构化工作台），
  **不含槽位划分**。

UI-05 是本支线工作量最大的一页，槽位划分直接决定：页面结构、每槽的后端投影接口、以及「哪个槽位该出现 Agent 入口」
（=专业能力 2／5 的落点）。**此项不定义，UI-05 无法开工**；若先按某种猜测开工，后面极可能整体返工。

## 候选方案

| 方案 | 描述 | 优点 | 缺点 | 风险 |
| --- | --- | --- | --- | --- |
| **A（建议）** | 按**业务对象/生命阶段**切：① 委托受理 ② 方案与报价 ③ 合同与单证 ④ 履约与交接 ⑤ 费用与结算 ⑥ 附件与凭证 ⑦ 异常与变更 | 与「四段式派生阶段条（受理-方案-履约-结算）」天然对齐；槽位**独立于 AI 能力存在**，正好承接 R11；⑥⑦ 作为贯穿项覆盖文档已明确要求的「异常／变更记录与影响标记」 | 与「5 个数据来源」不是一一对应，需在计划里补一句映射说明 | 低 |
| B | 按**AI 专业槽位**切：AG-01…AG-05 五个专业 + 附件 + 异常变更 | 与「专业能力覆盖 2／5」直接对应 | **与 R11 自相矛盾**：若槽位由专业定义，「无 AI 能力的槽位」就成了空概念 | 中高 |
| C | 先按 A 开工，待 HO 确认后微调 | 不阻塞进度 | 槽位是页面骨架，返工成本高于等待 | 中 |

## 决策

选择：**方案 A**（待 HO 确认后定稿；若 HO 另有划分，以 HO 版本为准并同步修订本记录）。

理由：

1. **R11 隐含了「槽位先于 AI 存在」**——「无 AI 能力的槽位」必须是一个先有业务含义、再挂（或不挂）专业能力的容器，
   因此 B 在逻辑上不成立；
2. 方案 A 的 ①→⑤ 与计划已确定的四段式派生阶段条一一落位，阶段条可由槽位状态**派生**（而不是另建一套状态），
   符合「**派生阶段条**」的字面要求；
3. 文档示例「下一步：确认装卸费承担方」正好落在 ⑤费用与结算；「内含简版异常／变更记录与影响标记」正好落在 ⑦；
   两条已知约束都被覆盖，不是凭空凑数；
4. 5 个数据来源到 7 槽位的映射为：委托→①、任务→②④⑦、成果→②③⑤、采购→②⑤、附件→⑥，**每个来源都有落点**。

## 影响

- **后端**：需要 7 类**聚合投影**只读接口（每槽一条，或一条聚合返回 7 段）；这是新增只读查询，不改既有接口语义。
  「下一责任方」与「未决问题」的判定规则需在此一并定稿（属 AC-02/AC-21 的表现层）。
- **前端**：UI-05 页面骨架 = 7 槽位；每槽的「查看／编辑／打开」动作只有 ⑤②③ 有真实落点，
  其余先跳「后续开放」占位（与 UI-02 侧栏同一口径）。
- **数据库迁移**：**无**（只读投影，不新增表）。
- **功能开关**：沿用 `ENTRUST_ENABLED`；关闭时整页 404，不留空槽位。
- **对旧流程的影响**：**无**。委托工作台是新增页面，不触碰既有货主/船东/港口三端页面与接口。
- **需要同步修改的文档**：`MVP开发与交付计划…v1.5.1.md` 的 UI-05 行（补七槽位枚举与「数据来源→槽位」映射）、
  UI-05 的验收子项（每槽的「当前成果／未决问题／下一责任方／最后更新」需逐槽可见）。

## 回退方式

- **代码回退**：槽位划分先在**前端配置表**（一维数组：key / 标题 / 数据来源 / 是否开放 / 动作）落地，
  后端只提供通用投影接口。改变划分＝改配置表，**不牵动数据库、不牵动状态机**。
- **数据兼容性**：无新增持久化结构，无兼容问题。
- **外部能力**：无外部依赖。

## 验证方式

1. 前端配置表内 7 条槽位与本文档枚举**逐字一致**（可作为静态契约断言进 CI）。
2. 每槽 4 个字段（当前成果／未决问题／下一责任方／最后更新）均可由后端投影返回，未知保持 `null` 且界面显示
   「待补充」而**不是空白或 0**（沿用「未知就是未知」约束）。
3. 专业能力 2／5 的落点可被断言：**恰好 2 个槽位**出现 Agent 入口，其余 5 个槽位只有人工动作
   （R11 的回归用例）。

未执行项及原因：本记录为**提议**，槽位划分待 HO 确认；在确认前 UI-05 不开工，
故上述 3 条验证均记为 **`not-run`**，不得按通过处理。
