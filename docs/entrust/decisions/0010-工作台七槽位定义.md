## 1. 原记录（提议稿，保留备查）

### 1.1 原背景

交付计划的 UI-05 行统一描述为「**7 个业务槽位 = 7 类聚合的投影**」，并给出每槽要显示
「当前成果／未决问题／下一责任方／最后更新」，以及 R11 的约束「**无 AI 能力的槽位不显示 Agent 操作，只给完整人工操作**」。
但**七个槽位具体是哪七个，在所有文档与设计稿里都没有枚举**：

- `MVP开发与交付计划_…v1.5.1.md`：只写「7 个业务槽位」，数据来源列写的是 5 项
  （委托 / 任务 / 成果 / 采购 / 附件）—— **5 个数据来源 ≠ 7 个槽位**，口径不闭合；
- `Entrusted_Shipping_Agent_IM_PRD_v1.0.md`：全文检索「槽位」**无命中**；
- 设计稿 `wt/L3/design/prototypes/dual-role-wireframes-v2.png`（等 5 张）：是既有「平陆滴滴打船」双身份原型
  （身份选择 / 货主端 / 船东端 / 发布货物 / 发布空船 / 我的订单），**不含委托工作台**；
- `平陆运河/工作流逻辑示意.jpg`：是 Agent IM 的交互范式参考（侧栏 → Agent 列表 → 独立对话 → 结构化工作台），
  **不含槽位划分**。

UI-05 是本支线工作量最大的一页，槽位划分直接决定：页面结构、每槽的后端投影接口、以及「哪个槽位该出现 Agent 入口」
（=专业能力 2／5 的落点）。**此项不定义，UI-05 无法开工**；若先按某种猜测开工，后面极可能整体返工。

## 2. 修订说明：原「未定义」判断不成立

### 2.1 直接原因：检索口径错误

- 原判据是「`Entrusted_Shipping_Agent_IM_PRD_v1.0.md`：全文检索『槽位』**无命中**」。
- **该文件是英文文档**，对应词是 `slots`（**§4.3 标题即 `Assignment workbench slots`**）。用中文词检索英文文档，
  无命中是**必然**，不能推出「没定义」。
- 交付计划 UI-05 行本身也只写「7 个业务槽位」，未列名；「数据来源」列写 5 项——这才是真正的口径缺口：
  **5 个数据来源 ≠ 7 个槽位**，缺的是一句映射说明，**不是一份新定义**。

### 2.2 结构性原因：权威材料不在仓库内

原记录引用的 `Entrusted_Shipping_Agent_IM_PRD_v1.0.md` **当时不在仓库中**（`docs/entrust/` 只有基线报告与决策模板）。
开发只能引用「附件」，无法引用「文件 + 章节」，于是「找不到」被误记成「不存在」。
⇒ ENT-017 已把权威 PRD、交付计划 v1.5.1 与 HO 处置意见正文一并入库 `docs/entrust/`。

### 2.3 教训（并入流程约定）

> **判定「需求未定义」前必须同时做到两件事**：① 用**文档实际语言**检索（本文件的正文是英文）；
> ② 检索范围覆盖**仓库内与仓库外**两部分材料。
> 只做其中一件，得出的「未定义」结论都是不可靠的。

## 3. 定案（自本次修订起生效）

### 3.1 七槽位：顺序与稳定 key 固定

| 序 | 稳定 key | 槽位名称 | 主要内容 |
| --- | --- | --- | --- |
| 1 | `overview` | 委托概况 | 客户、服务主体、货物、路线、时间、负责人、缺项 |
| 2 | `plan_tasks` | 方案与任务 | 方案版本、运输段、任务、前置条件 |
| 3 | `procurement` | 采购与报价 | 船东／供应商报价、比价、采购确认 |
| 4 | `customer_contracts` | 对客方案与合同 | 对客报价、客户接受、合同及签署证据 |
| 5 | `execution` | 履约与交接 | 运输与作业事件、数量、交接凭证 |
| 6 | `exceptions` | 异常与变更 | 异常案件、影响检查、处理与确认记录 |
| 7 | `settlement` | 费用与结案 | 应收应付、争议费用、结算与结案条件 |

顺序即上表，**不得重排**；`key` 进前端配置表，顺序与 key 由静态契约断言守住。
**不采用原方案 A**（其把「采购与报价」与「对客方案」合并、又把附件独立占一槽）。

### 3.2 槽位 ≠ 表 ≠ 成果类型 ≠ 接口

- 一个槽位可以读**多个**业务对象；同一个附件可以关联**多个**成果。
- 接口口径：**一条单委托工作台聚合查询**返回七槽位摘要（每槽四字段 + 计数），详情按需加载。
  **不**为每槽各建一套 CRUD、表或成果类型。
- 后端负责**权限、状态、可执行动作**；前端负责展示与跳转。

### 3.3 槽位 ↔ 数据落点映射（补上原记录缺的那句）

| 槽位 | 主要数据落点 |
| --- | --- |
| `overview` | 委托本体 + 客户 + 服务主体 + 货物 + 路线 + 时间 + 负责人 |
| `plan_tasks` | 方案版本、运输段、任务、前置条件 |
| `procurement` | 供应商/船东报价、比价、采购确认、**内部成本** |
| `customer_contracts` | 对客报价、客户接受、合同版本、签署证据 |
| `execution` | 里程碑、数量/状况记录、交接凭证、对账差异 |
| `exceptions` | 异常案件、阻断影响、变更提案、决策与已应用版本 |
| `settlement` | 应收、应付、附加费、争议、结算与结案清单 |

> 内部成本只进 `procurement`，且**不得**出现在客户侧投影（白名单投影口径不变）。

**与交付计划的衔接**：计划 UI-05 行「数据来源」列写的 5 项（委托/任务/成果/采购/附件）**由本表取代**——
槽位是投影的**呈现单位**，数据来源是**取数单位**，两者本就不是一一对应。
计划正文为 HO 已批准版本，本次**不改其原文**，以本记录为权威口径。

### 3.4 附件 = 共享证据能力，**不占槽位之一**

- 提供**统一材料入口**（上传/查看/关联），材料关联到各槽位的任务与成果。
- 原方案 A 把附件独立占一槽、并把「采购与报价」「对客方案」合并——**一并废弃**：
  合并会削弱「内部采购」与「对客承诺」的分离，而分离是本支线的核心约束。

### 3.5 四个派生字段的推导规则

| 字段 | 口径 |
| --- | --- |
| 当前成果 | 有效业务版本；多个成果时显示摘要与数量 |
| 未决问题 | 缺项、待确认、失效成果、阻断条件、未关闭异常 |
| 下一责任方 | 下一项可执行／待响应任务的责任人或责任角色 |
| 最后更新 | **相关业务记录的最近更新时间**，不是页面刷新时间 |

「确认装卸费承担方」按上下文落到**采购**或**对客方案**相关任务，**不因含「费用」二字就一律归到 `settlement`**。

### 3.6 空值四态（禁止一律显示「待补充」）

| 态 | 含义 |
| --- | --- |
| 暂无记录 | 该槽业务上确实还没产生记录 |
| 尚未分配 | 有需求但还没有责任人 |
| 不适用 | 本单业务上不需要（如无附加费） |
| 信息缺失 | 应有但缺失／未同步 |

### 3.7 Agent 入口判据（**删除**「恰好两个槽位有 Agent 入口」）

- 按钮是否出现 = `该动作已有实现` ∧ `专业能力已启用` ∧ `用户有权限` ∧ `当前上下文满足要求`。
- 一个专业可服务多个槽位（「方案与采购 Agent」同时服务 `plan_tasks` 与 `procurement`）。
- 验收断言改为：**每个出现的入口都对应真实动作与正确作用域**；而不是数槽位个数。
- ⇒ 原记录 §1.3 的第 3 条验证（「恰好 2 个槽位出现 Agent 入口」）**作废**。

### 3.8 首版人工落点要求

- 可以分 PR 实现，但**首版验收时范围内槽位必须有可用人工操作**（编辑、记录、确认）。
- 「跳到后续开放」**不能**作为验收完成；开发中暂缺的能力必须显式标注为未完成项。
- 没有 AI 的槽位仍应能人工编辑、记录、确认。

#### 3.8.1 「本期未开放」的撤下条件（[DR-0013](0013-异常与变更案件.md) §7.3）

`exceptions` 槽位当前以 `available=false` + `not_open_reason` 呈现，**不是**「暂无记录」。
撤下该标记需要**同一提交内**同时满足：

| # | 条件 |
| --- | --- |
| 1 | 三张表由**版本化迁移**创建，`--status`／`--verify` 幂等通过 |
| 2 | 两套状态机（`exception` / `change_request`）与阻断判据有**服务端**实现与用例 |
| 3 | 槽位四字段由**真实投影**返回；无记录时按空值四态呈现，**不是空数组糊过去** |
| 4 | 至少有**一个可用的人工落点**（登记案件 + 记录决定 + 关闭），能在真载荷走查中走通 |
| 5 | 客户投影白名单有用例 |

**五条同时满足前，标记不得撤下** —— 撤下就等于把「能力还没做」说成「这单没有异常」。

## 4. 影响

> ⚠️ **修正指引（2026-09-14，[DR-0012](0012-成果归属.md)）**：本节原文中的「**不加表、不加迁移**」（连同 §5 的「无新增持久化结构」）
> **已被 DR-0012 修正**。原文**保留备查**，但**不再作为有效结论**。
>
> * **证伪的前提**：该结论建立在「*成果可按单张委托读取*」之上，而这个前提**从未被验证**。
>   实测：`ent_artifact` 原先只挂 `entrustment_id`，而 `ent_entrustment` 是 **(org_id, entrust_user_id)** 的
>   **组织级授权**，与具体委托单无关；`ent_assignment` 也没有反向指针 ⇒ **成果与委托单之间没有任何关联键**，
>   同一货主在同一组织下的多张委托会**互相串成果**。
> * **冲突的权威条文**：PRD **第 187 行**（对话与工作台引用同一 artifact ID 与版本）、PRD **第 405 行**
>   （工作台是 authoritative records 的 assignment projection）、本记录 **§3.3**（成果是各槽位的主要数据落点）。
> * **处置**：采纳 DR-0012 **方案 A** —— 追加一条 additive 迁移，为 `ent_artifact` 补**可空** `assignment_id` + 索引；
>   历史行保持 **NULL**，**不按 (货主, 组织) 猜测回填**。
> * **本节仍然有效的部分**：七槽位口径、聚合查询的**形态**（一条只读查询返回七槽位摘要）、前端骨架、
>   功能开关、以及「对旧流程无影响（AC-01）」的判断 —— 均不变。

- **后端**：需要**一条**单委托工作台聚合只读查询（返回七槽位摘要），不改既有接口语义、不加表、不加迁移。
  「下一责任方」「未决问题」的判定规则按 §3.5 定稿（属 AC-02/AC-21 的表现层）。
- **前端**：UI-05 页面骨架 = 七槽位（顺序与 key 见 §3.1）；每槽的「查看／编辑／打开」动作在首版范围内必须有真实落点。
- **数据库迁移**：**无**（只读投影，不新增表）。
- **功能开关**：沿用 `ENTRUST_ENABLED`；关闭时整页不可用，不留空槽位。
- **对旧流程的影响（AC-01）**：**无**。委托工作台是新增页面，不触碰既有货主/船东/港口三端页面与接口。
- **需要同步修改的文档**：本记录；修订开发方案 §2；UI-05 的验收子项。
  交付计划正文的 UI-05 行**不改原文**，口径以本记录 §3.1、§3.3 为准。

## 5. 回退方式

- **代码回退**：槽位划分先在**前端配置表**（一维数组：`key` / 标题 / 数据来源 / 是否开放 / 动作）落地，
  后端只提供通用投影接口。改变划分＝改配置表，**不牵动数据库、不牵动状态机**。
- **数据兼容性**：无新增持久化结构，无兼容问题。
- **外部能力**：无外部依赖。
- **回退本决策的后果**：等于回到「七槽位无权威枚举」的状态，UI-05 重新不可开工。
  必须写明这一点，不得静默回退。

**本片显式保留的未完成项**：`exceptions` 槽位按 §3.8 以 `available=false` +

说成「这单没有异常」。该标记在后续切片做出真实数据模型前不得撤下。

### 6.2 真载荷走查补上（ENT-022，2026-09-14）

§6.1 里 #2 留下的缺口——「**仍缺**：用真后端载荷驱动前端投影的端到端（本仓库尚无委托
演示种子）」——在本片关闭。在此之前，前端投影只被「同形 fixture + 跨语言静态断言」覆盖：
后端把 `state` 的**语义**改掉时静态断言不会红，界面会静默显示「不适用」「无未决问题」
这类**错误的业务结论**（字面量没变，译法错了）。

落地的三件事：

* `backend/scripts/seed_entrust_demo.py`（新增，幂等）铺出**有内容的**委托：两张委托
  （`claimed` / `submitted`）、7 项任务（覆盖全部 `task_type`）、5 份成果（其中
  `settlement_draft` **刻意缺必填字段**，用来在真数据上验「信息缺失」≠「暂无记录」）、
  1 条 `assignment_id IS NULL` 的历史成果（验 `unassigned_artifact_total` 如实报数）。
  身份复用既有 `seed-shipper` / `seed-owner`，因此 e2e 的三角色 token 开箱可用；
* `scripts/verify_frontend_e2e.js` 新增第 ⑬⑭ 段：用**真接口载荷**驱动「委托队列」与
  「单委托工作台」两页，并对**七个槽位逐槽**核对「后端 `state` ↔ 界面文案」；
  另有一条硬断言——无委托载荷时**显式失败**，而不是让两页退化成"看 404 分支"后静默全绿；
* CI 的 `frontend-e2e` job **显式**加 `ENTRUST_ENABLED=true` 并串入该种子。刻意不改
  `.env.development`：本 job 要验的就是委托页面，把结论挂在"某个文件的默认值"上，
  那个值一改就会静默少验一半。

### 6.3 第二片「成果的编辑 / 确认」后的逐条状态（ENT-023，2026-09-14）

（如 `settlement_draft.receivable_lines`）在编辑态显示成**单行输入框**。
这是**已知缺口、不是本片兜底**；修法（给注册表补字段类型声明）作为**独立切片**待排。

其数据模型见 [DR-0013](0013-异常与变更案件.md)（**已采纳**，HO 2026-09-14 裁决，有条件采纳方案 A），撤下条件见 §3.8.1。
