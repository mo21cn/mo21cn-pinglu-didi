# DR-0020：真机走查就绪闸门的**档位修正**与「窗口标识 / 超时性质」的可观测性

- 日期：2026-09-19
- 提出人：开发代理（应 HO 2026-09-19 指令：「下一步执行 1-2-3-4-5」之第 4 条）
- 决策人：HO
- 状态：**已采纳**（HO 2026-09-19 指令）
- 关联：DR-0009（走查工具链换轨，**本记录部分修正其 §8.4 / §8.5⑨ 的档位描述**）、PR #169
- 本记录不改动任何业务行为，只改**走查工具链的读数与处置口径**

## 背景

DR-0009 §8.5⑨ 留下了就绪闸门失败的四档处置，并登记了一条「**未完全定位**：为什么某些
新起实例的 automator 不注册，还没有找到判据」。2026-09-19 拿到了新证据，其中**两条
修正掉了原有口径**，据此又新增两项此前只能靠猜的可观测维度。

### 修正一：档②「automation runtime 未注册 ⇒ 要人工点允许」**不成立**（至少不是必然）

HO 2026-09-19 实测：**没有点「允许」、也没有点开发者工具里的 miniapp，工具自己跑起来了**
（即不依赖人工点击）。同轮 runner 读数（`--prepare-ide --keepalive 3600`）：

```
[  12.9s] pageStack=[]  (开窗 5.3s / 取栈  7.7s)  回执 ok=False errorType=MCP_TOOL_ERROR
                                                   message=cant find runtimeid by projectpath E:\pinglu-didi\miniapp
[  40.1s] pageStack=[]  (开窗 6.3s / 取栈 15.8s)  回执 ok=True                      ← 约 40s 后注册成功
[  60.4s] pageStack=[]  (开窗 4.0s / 取栈 11.6s)  回执 ok=False ... timeout waiting for automator response
   ⋮（同型共 17 次，取栈耗时 11.5 ~ 13.2s，全程整超时）
[ 372.6s] ✗ 连续 17 次命中「automation runtime 未注册」⋯且已等够 360s ⇒ 早退
```

⇒ 「automator 不可用」**至少有两种截然不同的形态**，此前被合并成同一档：

| 回执 | 含义 | 正确处置 |
| --- | --- | --- |
| `cant find runtimeid by projectpath` | 真的**还没注册**（冷启动） | **等**，约 40s 自愈；⛔ 别清场、别重起 |
| `timeout waiting for automator response` | 注册已过，但**取栈不应答** | 通道 / 目标窗口问题（见修正三） |

把两者都叫「档②」会让处置指向「去点一次允许」这个**不必要**的动作 —— 本轮实测里
**没人点过允许，闸门后来也通过了**（见下方"决定性一轮"）。

**判据仍应是回执里的 `taskType=auth / status=pending`**，而不是"我看它卡住了"。

### 修正二：界面的「网络异常请稍后重试」与闸门失败**无关**

本轮曾据此提出一条链条：**网络异常 → 插件反复重下 → automator 不可用**。
查 IDE 自己的日志后（`…\微信开发者工具\User Data\<hash>\WeappLog\logs\*.log`）**被推翻**：

- 全日志**没有任何网络类错误**，唯一一条 ERROR 是 `[PROJECT-LITE][exports.markDevLaunchEnd]`；
- 项目在**正常加载**：`[PROJECT-LITE][W.loadPage]` ＋ `[onInstanceLoaded]` ＋
  `[_webviewCreatedHandler]` 连续出现；
- **MCP 调用能进 IDE**：`[MAIN][H.reportToolCall] [mcp-log] tool_call`，
  且每 ~15s 一条 `[mcp-log] session_init` ⇒ **通道本身是活的**；
- 本会话 `env | grep -i proxy` **为空** ⇒ 「剥掉沙箱代理」那一步实际是 **no-op**。

⇒ 界面上那个闪跳与闸门失败**没有因果关系**，⛔ 不要再往代理 / 网络方向猜。

### 修正三：**纯时序假设被证伪**（⛔ 不许靠加预算或反复重跑来刷绿灯）

| 观测 | 值 |
| --- | --- |
| 成功那两次的**取栈耗时** | **1.8s / 7.7s**（快） |
| 失败的全部 | **11.6 ~ 13.2s**（整超时） |
| 晚到 t=165.6s、t=376s 的探测 | **照样超时**（也在 t=376s 拿到过非空栈） |

⇒ 是**通道可用性 / 目标窗口**问题，不是"等得不够久"。
另外注意：成功那次 `ok=true` 时**页面栈也可能是空的** ⇒ `ok` 与"栈非空"必须分开看。

### 决定性一轮（本记录的触发事件）

修掉 `--prepare-ide` 的落点 bug（见下）后重跑，闸门**通过了**，日志里第一次出现：

```
TIMEOUT after 90s: open_project_window
✅ 模拟器已就绪
```

⇒ **`open_project_window` 可以整超时 90 秒，而紧接着的取栈仍然成功拿回非空栈**。
开窗超时**不是致命项**，不该据此 abort（现行 `wait_ready` 的判据只看 `pageStack`，是对的，
本节把它写进决策以免后人"顺手"改掉）。

### 本轮新增的**可观测性**（本记录的主要落点）

两条此前只能猜的东西，现在能读：

1. **窗口标识 `winId`**：`open_project_window` 的成功回执实测形如
   `{"result": {"success": true, "type": "reuse", "winId": "s0"}}`
   （⚠️ 两个字段在 **`result`** 里、**不在顶层** —— 这一点 v1 读错了，见「第二轮实测」；
   DR-0009 §8.5⑨ 记的是去掉外层后的形状），而**取栈不带窗口参数**
   ⇒ 「每轮都重开窗、取栈却指向旧窗口」这个假设**一直无法证伪**。
   现在 `type` / `winId` 进日志，`winId` 在轮次间变化时**点名告警**。
2. **超时性质**：`channel_error`（**IDE 自己**回错，本机 ≈11.5s 内部超时）与
   `our_timeout`（**我们**等到预算用尽）在日志里此前**同形**——这是"看不出慢在哪"的直接原因。
   现在 `kind=` ＋ `elapsed=` 并列打印。

## 候选方案

| 方案 | 内容 | 取舍 |
| --- | --- | --- |
| A | 只改文档（把档位描述改对） | 成本最低，但下次仍然"看不出为什么空" |
| B | 只加可观测性（不改文档） | 文档里的过期档位会继续误导处置 |
| **C** | **文档 + 可观测性并重，且⛔ 不改就绪判据** | **采纳** |

## 决策

1. **不改就绪判据**：仍为「能开窗 ＋ `pageStack` 非空」。⛔ **不**引入"等够 N 秒即算通过"
   这类宽松化，也⛔ **不**加预算去"等出"一个绿灯。
2. **就绪闸门的档位以本记录为准**（替换 DR-0009 §8.5⑨ 中"档②＝点允许"的表述）：

   | 档 | 回执特征 | 处置 |
   | --- | --- | --- |
   | ① | — | **先**只读探测**现成**实例，能用就 `--skip-ide` 复用（**首选**） |
   | ② | `cant find runtimeid by projectpath` | **等**（约 40s 自愈）；⛔ 别清场、别重起 |
   | ③ | `source=auth` / `taskType=auth` + `status=pending` | 才要人工在 IDE 窗口点一次「允许」 |
   | ④ | `timeout waiting for automator response` 且持续 | **通道 / 目标窗口**问题：按 ①② 处置，⛔ 别加预算、别刷绿灯 |
   | ⑤ | `kind=our_timeout` | **我们**的预算不够 ⇒ 可以调大探测预算后再试 |

3. **可观测性落点**：
   - `scripts/wechatide_client.py`：新增 `classify_page_stack()`（四分类）、
     `window_info()`；`page_stack_probe()` 注入 `__elapsed__` / `__kind__`。
   - `scripts/run_walkthrough_devtools.py`：`_brief()` 打印 `kind=` / `elapsed=`；
     `wait_ready()` 每轮打印 `窗=<type>/<winId>`，`winId` 漂移时点名，预算用尽时**按 kind 分档**给处置。
   - **只加键、只加打印**，默认值全部不变 ⇒ 不指定时行为与从前一致。
4. ⛔ **不声称闸门已修好**：本记录只把"为什么空"变成**可读**，
   **没有**消除那个 ≈11.5s 的 IDE 内部超时。

## 影响

- **文件**：`scripts/wechatide_client.py`、`scripts/run_walkthrough_devtools.py`
  （两者都在 CI 的根脚本 lint 清单内，见 `ci.yml`）。
- **不涉及** `backend/`、不涉及任何业务行为、权限或迁移。
- **日志新增字段**：`kind=` / `elapsed=` / `窗=<type>/<winId>`。
  本仓库无"按固定列数解析走查日志"的脚本，故不构成破坏；下游若有人写死列数需同步。
- **未交付物**：`wechatide_client.py` 是**本仓库内**的封装（不在 IDE 安装目录），
  所以本改动随仓库版本走，不影响 IDE 自身。

## 回退方式

`git revert <本笔提交>`。三项观测全部是**只加键 / 只加打印**，
删除后 `page_stack_probe` 仍返回 `(stack, receipt)` 两元组，调用方无需改动。

## 验证方式

1. **单元级（含正控）**：`classify_page_stack()` 四类各一条，必须包含
   `ok=true` 且栈非空 ⇒ `ok` 的正控（⛔ 不许只有"都是错"的负例 —— 那是真空通过）。
2. **静态**：`ruff check` / `ruff format --check`（按 `ci.yml` 原文，根脚本清单含这两个文件）＋ `py_compile`。
3. **本机门禁**：`python -X utf8 scripts/verify_local_gates.py` ⇒ `{"total":16,"failed":0}`。
4. **真机侧（下一轮）**：走查日志里必须能**同时**看到
   `窗=<type>/<winId>` 与 `kind=` / `elapsed=` 三个读数；若 `winId` 漂移，
   同一轮里应出现那条点名告警。

## 第二轮实测（2026-09-19 下午）：**winId 漂移被证伪**，并修掉一个「恒空读数」

用 `E:\_diag\probe_channel.py`（只读：`status` → `open_window` → `pageStack`，dump **完整回执**）
对**同一个实例**连跑两轮，两轮**完全一致**：

```json
--- check_wechatide_status (9.75s) ---
{"ok": true, "result": {"success": true, "loginExpired": false, "tokenRequired": false}}

--- open_project_window (4.35s / 5.29s) ---
{"ok": true, "tool": "open_project_window",
 "result": {"success": true, "type": "reuse", "winId": "s0"}}

--- automation_runtime_info(pageStack) (11.90s / 11.63s) ---
{"ok": false, "errorType": "MCP_TOOL_ERROR", "message": "timeout waiting for automator response",
 "source": "mcp_business", "reason": "mcp_business_fail",
 "detail": {"rawResult": {"success": false, "error": "timeout waiting for automator response"}}}
```

**结论一（任务："把 winId 漂移证实或证伪"）⇒ 证伪。**
窗口**没有漂移**：`type=reuse`、`winId=s0` 两轮恒定；通道与登录也都正常
（`ok=true`、`loginExpired=false`、`tokenRequired=false`）。
⇒ 「每轮重开窗 ⇒ 开窗与取栈落在不同窗口」**不成立**，卡点只剩**取栈那一步的
≈11.6s IDE 内部超时**（与本文「修正三」一致）。

**结论二 ⇒ 抓出本文自身的读数 bug（已修）。**
`type` 与 `winId` 在回执的 **`result`** 里，而 v1 的 `window_id()` 与 `wait_ready()` 的 `窗=`
读的是**顶层** ⇒ **恒为空**（日志里表现为 `窗=None/None`）。这是一个
「**看起来有观测、实际永远读不到**」的**假读数** —— 与 54 ⑤ 那次 `None→None` 判 PASS 的
**真空通过**同型。修法：

- `window_id()` → `window_info()`，读 `result.type` / `result.winId`；
- `wait_ready()` 的 `窗=` 同步改为读 `result`；
- **CI 侧新增** `backend/tests/test_walkthrough_channel_classify.py`：夹具换成**这次实测到的
  真实回执形状**，并加一条**反向断言**「同样两个字段放在**顶层**时必须读到**空**」，
  锁死读取位置；另有一条断言「消息里都含 `timeout`，但 `our_timeout` 与 `channel_error`
  必须分类不同」—— 直接守护本文「修正三」的判定。
  ⛔ 从此不许再用**臆想**的回执形状做夹具。

## 未覆盖项（登记，不假装已覆盖）

- **为什么取栈会整超时 ≈11.5s** —— ⛔ **仍未定位**。
  本轮只把它与 `our_timeout` **区分开**，没有消除它。
- ~~`winId` 漂移 ⇒ 取栈取错窗口~~ ⇒ **已证伪**（见上「第二轮实测」：`type=reuse`、
  `winId=s0` 两轮恒定）。⛔ 不得再把它当成待解释的原因。
- ⭐ **「读数键写错位置」是一个反复出现的失效模式（本轮已是第 2 例）**：
  54 ⑤ 读了快照内部的 `quantity_before`（实为 `old_quantity_text`）、
  本条读了顶层的 `winId`（实为 `result.winId`）—— **两例的判据当时都能过**，
  因为判据看的是别的东西（"条数"／"有没有打印"）。
  ⇒ 纪律：**任何新读数都要有一条"读到真值"的正向断言**，
  **夹具必须取自实测回执**；能加"读错即失败"的守护就加。
- **人工点击是否**是某条路径上的必要步骤 —— 本轮只证伪了"必然需要"，
  未排除"某些实例上仍然需要"（判据：回执 `taskType=auth / status=pending`）。
