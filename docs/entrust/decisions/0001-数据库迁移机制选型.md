# DR-0001：数据库迁移机制选型（Alembic vs 轻量自建执行器）

- 日期：2026-09-13
- 提出人：S0 基线盘点（F1：仓库无迁移机制，`main.py` 用 `create_all`）
- 决策人：HO
- 状态：**已采纳**
- 关联：PRD 9.2（数据库与持久化）；验收 AC-22（迁移可追溯）；规范六「数据库、配置与依赖」；PR #（见提交后回填）

## 背景

仓库当前没有任何数据库迁移机制：`backend/app/main.py` 的启动钩子里直接 `Base.metadata.create_all(bind=engine)`。这带来三个具体问题：

1. **结构变更不可追溯** —— 加字段、改索引、建表都没有版本记录，无法回答"生产库现在是什么状态"。
2. **多环境靠人肉对齐** —— 开发/测试默认 SQLite（`pinglu_didi_dev.db` / `pinglu_didi_test.db`），生产 MySQL。方言不同，靠 `create_all` 无法保证三端一致。
3. **回退无依据** —— 规范六要求"代码回退与数据库回退分别说明"，没有迁移记录就无从谈起。

委托支线 R1 要新增组织成员、委托授权、成果版本、幂等记录、作业表等多张表，**S1 的所有模型变更都被这条阻塞**，必须现在定。

## 候选方案

| 方案 | 描述 | 优点 | 缺点 | 风险 |
| --- | --- | --- | --- | --- |
| A | 引入 Alembic（`alembic.ini` + `env.py` + 版本链，autogenerate 生成迁移） | 生态最成熟；自动生成差异；版本图支持分支合并；与 SQLAlchemy 深度集成 | 新增依赖与目录概念；`autogenerate` 结果需逐条人工审查；团队需理解版本链/哈希/head 等概念 | 本项目**未深度使用 SQLAlchemy ORM**（业务多走原生 SQL 与手写查询），autogenerate 的收益大打折扣，学习成本照付 |
| B | 轻量自建执行器：`migrations/` 下每表一个 `.py`（手写 SQL + checks），根目录 `migrate.py` 执行，库内 `_migration_history` 表记录执行历史 | 零新依赖（纯 Python + SQLAlchemy 已有能力）；文件结构一眼看懂；新人零学习成本；SQL 完全可控、可 Review；天然适配 SQLite/MySQL 双方言 | 无自动差异生成，需手写 SQL；无自动 downgrade；版本为线性 id，不支持分支合并 | 手写 SQL 写错方言会当场失败（靠 checks 与 CI 冒烟兜住）；线性历史要求"id 只增不改"，需靠评审纪律保证 |

## 决策

选择：**方案 B（轻量自建迁移执行器）**，作为 Alembic 的替代。

理由：

1. **收益匹配度** —— Alembic 的核心卖点是 autogenerate，而它依赖 ORM 元数据差异比对。本项目业务层大量原生 SQL，ORM 只用于建表与少量 CRUD，autogenerate 省不下多少事，却要付全部学习成本。
2. **零新依赖** —— 规范六要求"每次模型变更提供版本化迁移"。在没有额外依赖的前提下满足该要求，比引入新依赖再满足它更符合"最小改动"。
3. **可控性优先** —— 委托支线涉及金额、权限、作业状态，DDL 必须逐条人工确认。手写 SQL + `checks` 校验 + Code Review 的组合，比"自动生成再审查"更不容易漏。
4. **双方言是硬需求** —— 开发/测试 SQLite、生产 MySQL。原方案示例中 SQL 为 MySQL 方言，本支线需要扩展为**按方言提供 SQL**（见"影响 - 数据库迁移"）。

**保留的 Alembic 思想**：迁移文件版本化、执行历史持久化、迁移与业务代码同仓同评审。这三条是本方案的价值来源，不是可选项。

## 影响

- 后端：
  - 新增 `backend/migrate.py`（执行器 CLI）与 `backend/migrations/`（迁移文件包）。
  - `main.py` 启动钩子的 `create_all` **继续保留**，但排除迁移管理的表（见下）。
  - `tests/conftest.py` 需为迁移管理的表提供独立建表路径。
- 前端：无影响。
- 数据库迁移：
  - **命名空间约定**：委托支线新增表统一使用 `ent_` 前缀；`ent_` 表一律由迁移文件创建，**不进 `create_all`**。既有表（users / ships / cargos / orders / payments / ports 等）维持 `create_all` 现状，本次不动，避免一次性迁移全库带来的风险。
  - **方言字典**：迁移条目的 `sql` 可以是字符串（全方言通用），也可以是 `{"mysql": ..., "sqlite": ...}` 字典，执行器按 `engine.dialect.name` 选择。缺少对应方言即报错，不允许静默跳过。
  - **历史表**：`_migration_history`（module / migration_id / description / executed_at），`UNIQUE(module, migration_id)` 保证不重复执行。
  - **id 只增不改**：已上线条目的 SQL 严禁修改，新需求追加新 id。
  - **无自动 downgrade**：需要回退时追加一条反向迁移（如 `id: 2` 写 `DROP COLUMN`），不假设"撤销上一次执行"是安全的。
  - **非事务性**：MySQL DDL 隐式提交，一条迁移失败即停止并报错，由人工介入，执行器不做回滚。
- 功能开关：无。迁移执行与否不影响 `ENTRUST_ENABLED`。
- 对旧流程的影响：
  - **既有 8 个模块的建表路径不变**，`create_all` 仍覆盖既有表，AC-01 基线回归不受影响。
  - 新增 `ent_` 表从第一天起就走迁移，避免"先 `create_all` 后迁移"的中间态。
- 需要同步修改的文档：
  - 新增 `docs/06-database-migration.md`（本方案的使用说明与纪律）。
  - `docs/entrust/00-基线对齐报告.md` 第 7 节 D1 标记已决策。
  - `AGENTS.md` 写入"改表结构必须走迁移"的硬约束。

## 回退方式

- **代码回退**：`git revert` 移除 `migrate.py` 与 `migrations/`；`main.py` 的 `create_all` 排除逻辑一并回退。无外部依赖需要卸载。
- **数据兼容性**：`_migration_history` 表是新增表，移除后不影响业务表。`ent_` 前缀的业务表若已上线，代码回退**不会**删除表，需人工确认后单独处理。
- **外部能力**：无。执行器仅依赖已在 `requirements.txt` 中的 SQLAlchemy。

## 验证方式

| 命令 | 预期结果 |
| --- | --- |
| `python migrate.py --status`（全新库） | 列出全部待执行条目，已执行 0 |
| `python migrate.py` | 按 module、id 顺序执行，逐条打印，退出码 0 |
| `python migrate.py --status`（再次） | 待执行 0，已执行 = 条目总数 |
| `python migrate.py --verify` | 执行 + 复跑全部 checks + 断言无待执行；不满足则退出码非 0 |
| `pytest tests/test_migrate.py` | 通过：SQLite 上建表成功、重复执行幂等、方言解析正确、条目 id 唯一且递增 |
| CI job `db-migration` | 连续两次 `python migrate.py --verify` 均通过（第二次证明幂等） |

未执行项及原因：

- **MySQL 上的实际执行**未跑 —— 本机与 CI 默认无 MySQL 实例，属 D2（MySQL 集成测试环境）范围，未决。迁移文件中 MySQL 分支的 SQL 目前只经过人工评审，未经真实执行验证。在这条补齐之前，AC-22 中"生产方言可执行"这一子项应记为 `not-run`，不得记为通过。
