## 1. 原记录（提议稿，保留备查）

### 1.1 原背景

风险 R1 的原始表述是「`app.json` 已 17 页 / tabBar 5 项，`navigateTo` 页面栈上限 10 层，
深链与返回策略须显式设计」。2026-09-13 实测现状：

| 事实 | 值 |
| --- | --- |
| `app.json` 页面 | 17（四件套 0 缺失） |
| tabBar | 5 项（`custom: true`，用 `custom-tab-bar` 组件） |
| 导航调用分布 | `navigateTo` 20 / `switchTab` 11 / `navigateBack` 7 / `reLaunch` 3 / `redirectTo` 1 |
| 当前最长声明链 | `pages/trade/match/match` = 4 层（`mine` → `assistant` → `cargo` → `match`） |
| `navigateTo` 指向 tabBar 页的 bug | **0 处**（已由 `verify_miniapp.js` 第 6 项守住） |

所以 R1 **不是一个已存在的 bug**，而是「**新增页面不需要声明任何东西就能进 `app.json`**」这一结构性缺口：

1. **栈深不可见**：`navigateTo` 撞 10 层上限时**不报错**，只表现为「点了没反应」
   （`utils/agent-entry.js` 里那句 `fail` 兜底就是为它写的）。委托支线还要再加
   UI-01～UI-05，若某条链叠到第 10 层，很难反推是哪条链、哪次改动造成的。
2. **深链无契约**：`pages/entrust/detail/detail` 深链进来若缺 `assignment_id`，
   页面会进错误态而不是被拦下；哪些页可以深链、必须带什么参数，代码里没有单点可查。
3. **既有门禁不覆盖这两点**：`verify_miniapp.js` 只查「路由可达」与「tabBar 该用哪个 API」，
   既不计算链深，也不校验深链参数。

### 1.2 原候选方案

| 方案 | 描述 | 优点 | 缺点 | 风险 |
| --- | --- | --- | --- | --- |
| A | 只写一份《路由与深链约定》文档 | 零改动 | 文档不拦人；新增页面照旧无需声明 | 高：等于把 R1 留给下一个人 |

## 3. 定案（修正版 B）

### 3.1 分开建模「页面层级」与「导航边」

修订前的问题：`parents` 同时表示**界面层级**（用于算链深）与**所有来路**（用于校验导航边）。
于是产品上合理的工作台↔会话双向切换，在链深计算里变成环 → `Infinity`。

修订后：

```js
// ① 导航边：唯一真相。所有真实可达的调用关系，每条带策略。
const NAV_EDGES = [
  { from: 'pages/entrust/workbench/workbench', to: 'pages/assistant/assistant',
    strategy: 'push' },
  { from: 'pages/assistant/assistant', to: 'pages/entrust/workbench/workbench',
    strategy: 'reuse', reason: '从工作台进入会话后返回工作台应复用而非再压一层' }
]

// ② 层级：只表达「静态上可以从哪一层以 push 进来」，用于 chainDepth()。
//    **由 NAV_EDGES 中 strategy==='push' 的边派生**，不手工维护 ⇒ 不存在两份数据打架。
//    ROUTES[p].parents 字段名保留（调用方不变），语义收窄为「层级」。
```

- `chainDepth()` 只看 **`push` 与 `replace`** 两类有向边：`push` 权重 `+1`，
  `replace` 权重 `0`（替换当前页、不增层）。`reuse` / `back` 的往返**不参与链深**，
  因此也不构成环。
- 导航边校验改看 `NAV_EDGES`，与层级解耦。

### 3.2 边的策略枚举

| 策略 | 语义 | 是否增加栈深 |
| --- | --- | --- |
| `push` | 正常进入下一级（`wx.navigateTo`） | **+1** |
| `replace` | 明确允许替换的同级页面（`wx.redirectTo`） | 0（替换） |
| `back` | 返回栈中已有页面（`wx.navigateBack`） | 0（出栈） |
| `reuse` | 目标已在栈中且上下文相同，复用并刷新 | 0 |
| `reset` | `wx.reLaunch`，重置栈 | 归 1 |
| `switchTab` | tabBar 页（`wx.switchTab`） | 归 1 |

### 3.3 环的判定规则（关键修订）

- **`push` 图必须无环**：`A --push--> B --push--> A` 才可能持续压栈，判为**错误**。
- **经 `back` / `reuse` / `replace` 的往返不算环**：正常工作台↔会话切换**必须被允许**。
- `kind`（`tab` / `root` / `detail`）**不再被当成自动清栈**：清不清栈由**实际调用的导航操作**决定，不由页面类别决定。

### 3.4 运行期导航策略链（**替代**「接近上限就 `redirectTo`」）

按序处理，命中即停：

1. **目标已在栈中且业务上下文相同** → 返回／复用，并**刷新目标成果**；
2. **正常进入下一级、预算允许**（`depth < STACK_BUDGET`） → 正常压栈；
3. **声明为可替换的同级页面** → 保存必要上下文后替换；
4. **涉及未保存编辑** → 先保存或提示处理，**不静默卸载**；
5. **仍无法安全进入** → 给出明确提示 + 「返回工作台」操作。

**明确禁止**：把 `redirectTo` 作为所有页面的通用默认动作。替换必须**由声明允许**，而不是由深度自动触发。

#### 3.4.1 实现期确认的三条细化（ENT-019 接入时暴露，已按此实现）

接入两个委托页时发现，只按上面的字面顺序实现会让**已声明的语义执行不出来**。三条细化：

| # | 细化 | 为什么必须这样 |
| --- | --- | --- |
| ① | `reset` **优先于复用**（在「目标已在栈中」之前判定） | `reset` 的语义是「清空栈重来」。若先过复用分支，冷启动深链进工作台（栈：`index → mine → workbench`）时 `go('/pages/index/index')` 会退化成 `navigateBack(2)` —— 落点看起来一样，但**栈没清、身份链路没重走**；栈里只有工作台时又会退化成 push，压出第二个首页 |
| ② | `reset` 优先于预算判定（不能落到 push） | 修 ① 之前，`strategy:'reset'` 在 `resolveNavigation()` 里没有任何分支承接，一路落到第 4 步被当成 **push** 执行成 `wx.navigateTo`。`go()` 的 `switch` 当时也缺 `case 'reset'` |
| ③ | 「未保存编辑」只在**声明式替换**与**预算耗尽**两处拦截 | 第 2 步（压栈）排在「未保存编辑」之前是**刻意的**：`push` 不卸载当前页，编辑还在栈里、没丢。真正会丢编辑的是 `replace`、`reset` / `switchTab`、以及栈满后的兜底。若对"往下走一层"也弹窗，用户会被训练成一律点确定 —— 那比不提示更糟 |

配套：`confirm-unsaved` 的返回值带 **`afterConfirm`**（= 用户答复「放弃编辑」后该执行的那个计划）。
预算耗尽时 `afterConfirm` 是一个 **blocked** 计划而不是 push —— 因为**放弃编辑也进不去**，
页面必须如实说出来（`pages/entrust/workbench/confirmLeave()` 已按此实现），不能假装「存下来就能进」。

> 与 HO 五步的字面对应关系：HO ① ≡ 复用、② ≡ 压栈、③ ≡ 声明式替换、④ ≡ 未保存编辑、⑤ ≡ 明确失败 + 兜底。
> 细化 ① 是**顺序**调整（reset 提前），细化 ③ 是**澄清**第 2 步与第 4 步的先后（HO 的字面顺序本就如此）。

### 3.5 上下文复用键

页面复用**不能只比较路径**：同一个成果详情页可能分别显示两张委托。复用键为：

```
页面路径 + 委托 ID + 必要的任务／成果／会话 ID
```

键不等 → 不复用，走压栈（或声明为 `replace`）。

### 3.6 目标页入口守卫（深链校验必须落在目标页）

`go()` 内部校验之外，**冷启动或外部进入**时目标页仍需在 `onLoad` 执行入口守卫，检查：

1. 参数是否合法（**非空** + 类型／枚举）；
2. 是否登录及有访问权；
3. 成果、任务、会话**是否归属所给委托**；
4. 是否需要选择组织或恢复上下文。

两点口径，避免过度拦截：

- 「缺少上次选择的组织」**可以进入选择流程**，并非必须禁止该页深链；
- `deepLink = deny` **不能**代替服务端授权（前端拦截只是体验，授权必须在服务端）。

### 3.7 预算口径

- 保留 `STACK_BUDGET = 8` 作为**项目预算（策略）**，`MAX_STACK = 10` 是平台硬限。
- 但**预算必须真的被运行期用到**（修订前 `STACK_BUDGET` 运行期零引用，见 §2.2 ⑤）：
  运行期在 `depth >= STACK_BUDGET` 时进入 §3.4 的策略链，而不是直接压栈。
- 承认：把临时页面留在声明之外、再预留两层，**并不能保证**实际栈安全；
  所以**策略链 + 入口守卫 + 行为测试三者必须同时存在**，不能只留声明。

## 7. 已知盲区（更新）

1. **工具函数来源的导航边无法静态解析**：`utils/agent-entry.js` 的 `openSmartEntry()`
   跳 `pages/assistant/assistant`，但它的**调用方页面**需要跨文件解析才知道。
   脚本把这类边记为 `[工具来源]` 跳过并打印，**不计入链深证据**。
   → 约定：新增页面若调用 `openSmartEntry()`，请把该页面补进 `assistant` 的 push 边。
2. **`replace` 边的链深权重为 0**（替换当前页、不增层）：约束是 `depth(to) ≥ depth(from)`。
   初版把 `redirectTo` 当 `push`、按 `+1` 计（方向是**高估**，不漏报但会早报）；
   修订后按真实语义计 `0` —— 否则 `cargo --redirectTo--> match` 这种刻意保持栈浅的
   替换会让 `match` 的声明链深**虚高一层**。
   **代价**：某个来源直接写 `wx.redirectTo` 却没在 `NAV_EDGES` 声明时，它既不算进链深，
   也会被门禁的「未声明边」点名报出——即"漏声明"会红，而不是被静默低估。
3. **未校验「声明的 `parents`／`NAV_EDGES` 是否有真实调用边」**：`reuse` / `back` 边无法由静态扫描证明，
   只能声明。多声明只会高估约束，不设为错误（避免为通过门禁而漏声明）。
   （ENT-019 起 `push` / `replace` 边若被声明**且**该页面在 `MIGRATED_PAGES` 内，
   就必须有 `go()` 或 `wx.*` 的真实调用证据；未接入的页面仍只声明。）
4. **`MIGRATED_PAGES` 名单是人工维护的**：它只保证"名单里的页面确实走 `go()`"，
   不能保证"该进名单的页面都进了"。判断口径是「新增的委托页面从首个切片起必须进」，
   旧页面按触及范围迁移 —— 这是流程约定，门禁只能核对名单自身不撒谎。
5. **真机栈深未验证**：本决策不承诺「10 层上限在真机上就是这样」，只承诺「声明链深不超过 8」且有运行期策略链。
   真机验证仍**未执行**（见 §6.1 末两行）。
