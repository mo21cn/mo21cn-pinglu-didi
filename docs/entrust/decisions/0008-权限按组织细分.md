# DR-0008：权限判定按组织细分，`can()` 必须指定作用域

- 日期：2026-09-13
- 提出人：`fix/entrust-org-scoped-permissions`（开发组织选择器时侦察发现）
- 决策人：HO
- 状态：**已采纳**
- 关联：计划 §5.2 S1 §权限；AC-10（权限矩阵）；AC-01（基线回归）；DR-0007；`AGENTS.md` 3.1「权限校验始终后端执行」

## 背景

`access.resolve_context()` 把用户在各个组织的成员角色权限**取并集**：

```python
for row in rows:                      # 用户在哪些组织里
    permissions |= ORG_ROLE_PERMISSIONS.get(row["member_role"], ...)
```

而 `AccessContext.can(permission)` 允许**不传任何作用域**，此时就用这个并集判定。

于是产生一个真实的跨组织越权（2026-09-13 用真实数据复现）：

| 事实 | 值 |
| --- | --- |
| 用户 U 在组织 A 的角色 | `manager`（含 `entrust:assignment:claim`） |
| 用户 U 在组织 B 的角色 | `member`（**只读**，仅 `entrust:view`） |
| 组织 B 有一张 `submitted` 的委托单 | — |
| `U.can(PERM_ASSIGN_CLAIM)` | `True` ← 来自 A 的角色 |
| `claim_assignment(该委托单, actor=U)` | **成功**，`claimed_by = U` |

即：**只读成员在自己的组织内完成了写动作**。

影响面盘点（`grep '\.can\('` 全量）：

- 用非 `PERM_VIEW` 权限且**未限定作用域**的判定：**仅 `claim_assignment` 一处**（本条修复点）。
- 其余非 `PERM_VIEW` 判定（`agent_api`、`authz.assert_can_write_entrustment`、
  `attachments_api`、`extraction_api`）都传了 `owner_user_id`，受"授权必须来自该货主"约束。
- 大量 `PERM_VIEW` 判定用的是并集，但 `owner` / `admin` / `manager` / `member`
  **四种角色都含 `PERM_VIEW`**，并集与按组织判定结果相同，故无行为差异。

**但根因不是那一行**：只要"不带作用域的判定"还是可写出来的，这类漏洞会随每个新端点复发。
触发条件已经具备 —— 用户属于多个组织，是委托发货的正常业务形态（一个经理服务多家货主组织）。

## 候选方案

| 方案 | 描述 | 优点 | 缺点 | 风险 |
| --- | --- | --- | --- | --- |
| A | 只改 `claim_assignment` 一行（改成按组织判定） | 改动最小 | 模型本身仍缺"按组织"这一维；下一个端点会再犯 | **高**：已知的复发模式，等于把它留给下一个人 |
| **B** | 引入按组织细分的权限，且**让"无作用域判定"成为错误** | 整类漏洞不可能再写出；约束交给运行时而不是"记得传参数" | 需要改 10 处调用点（都在同一模块内） | 低：每处都有现成的组织字段可用；测试全量覆盖 |
| C | 把 `permissions` 并集直接删掉 | 最彻底 | 破坏诊断与兼容；`assert_can` 的既有签名需大改 | 中：收益低于 B，改动面更大 |

## 决策

选择：**方案 B。**

1. `AccessContext` 新增 `org_permissions: Mapping[int, frozenset[str]]` ——
   某组织内的权限 = 该组织的成员角色权限 ∪ **授予该组织**的授权权限。
2. `can(permission, *, org_id=None, owner_user_id=None)`：
   - **两者都不给 → `ValueError`**（不给"默默用并集"的机会）；
   - 只给 `org_id` → 按组织判定；
   - 只给 `owner_user_id` → 按货主授权判定；
   - 两个都给 → **AND**（更严；调用方能给两个维度时就该给两个）。
3. `Delegation` 新增 `org_id`：授权是"授予某个组织"的，缺了它无法回答"这条授权给谁"。
4. `permissions`（并集）保留，但明确标注**仅供诊断**，不再是任何判定的依据。
5. `assert_can()` / `require_permission()` 同步：透传两个作用域，或直接由 `can()` 报错拦截。

理由：本项目的既有立场是"把约束做成结构，而不是做成纪律"（同 ENT-010 的权限矩阵、
DR-0004 的版本锁定）。一个"记着别忘传参数"的约定，迟早会在某个赶工的新端点上失守。

**`permissions_in_org(org_id)`** 同时是组织选择器的数据来源 ——
界面要能显示"我在这个组织能做什么"，这需要按组织可读的权限，而不是并集。

## 影响

- 后端（仅委托支线 `app/modules/entrust/`）：
  - `access.py`：`AccessContext` 新增字段与方法；`Delegation` 新增 `org_id`；
    `resolve_context` 构建 `org_permissions`；`_active_delegations` 查询补 `org_id`；
    `assert_can` 增加 `org_id` 参数。
  - `assignments.py`：`claim_assignment` 改用按组织判定（**越权修复点**）。
  - `authz.py` / `router.py` / `tasks.py` / `agent_api.py`：10 处 `can(...)` 补组织维度。
  - `dependencies.py`：`require_permission` 增加 `org_id`。
- 数据库迁移：**无**。只读模型的解释方式变了，表结构不变。
- 功能开关：无。
- 对旧流程的影响（AC-01）：**无**。本模块是叠加层，不触碰 `User.current_role`
  与既有 router；无组织身份的用户解析结果仍为空集。
- 需要同步修改的文档：本决策记录；交付计划的 §8 风险表（记为已修）。

## 回退方式

- **代码回退**：把 `can()` 的"必须指定作用域"检查去掉、并把调用点改回不带作用域即可。
- **数据库回退**：不适用（无表结构变更）。
- **外部能力**：无。

**注意**：回退本决策等于重新接受背景里描述的跨组织越权。回退说明里必须写明这一点，
不能只写"恢复原状"。

未执行项及原因：无。

**遗留**：按货主维度（`owner_user_id`）的判定本身是**跨组织**的 —— 只要该货主把权限
授权给了用户所在的任一组织即成立。这是有意的（授权归货主所有，与它落在哪个组织无关），
但若将来业务要求"授权只在指定组织内可用"，需要把该维度也收紧（两个作用域都传即可，
`can()` 已支持 AND 语义）。
