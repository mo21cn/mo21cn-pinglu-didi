## 1. 背景

### 1.1 现状：它是一条**独立通道**，不是空值四态

后端 `workbench.py` 当前把该槽声明为：

```
key="exceptions"
not_open_reason="本期未开放：异常与变更尚无数据模型，不作为「暂无记录」呈现"
```

投影时走 `available=False` + `unavailable_reason`，**刻意不套用空值四态**（DR-0010 §3.8）。
理由成立：套四态会把「这个能力还没做」说成「这单没有异常」——后者是一个**业务结论**，而前者是**工程状态**，两者不能混。

前端与静态门禁都已按此断言：「未开放槽不得给字段行、必须给理由」。

### 1.2 前提更正：PRD **有**字段级要求 —— 我此前的判断是错的

> v1 讨论中我给出的前提是「PRD 只在工作区层面定义它（第 180 行），**没有任何字段级要求**，所以模型必须由我们自己定」。
> **这个判断是错的。** 本节更正它，理由按本支线规矩（`01-决策记录模板.md` 填写要求 4、5）必须留痕，不得静默修正。

**错因**：只读了 §4.3 那张槽位表（第 180 行「Open cases, blocking impacts, proposed changes, decisions and applied revisions」），
没往下读 §5.5、§6.1、§9。**权威定义在这个文档里是分散的**：

| 对象 | 定义落在哪 | 内容 |
| --- | --- | --- |
| 槽位**内容** | §4.3 第 180 行 | Open cases / blocking impacts / proposed changes / decisions / applied revisions |
| 字段**清单** | **§5.5 第 255 行** | owner、severity、affected tasks/artifacts、proposed actions、due time、decision、resolution evidence、closure |
| **状态机** | **§6.1 第 277 行** | `open` / `in_review` / `approved` / `rejected` / `applied` / `closed`（as applicable to type） |
| 阻断**语义** | **§5.4 第 224 行** | informational / review-required / execution-blocking；**只有 execution-blocking 阻止动作** |
| **变更传播** | **§6.2 第 285 行** | 事实变更 → 下游草稿/结果标 `needs_revalidation` + 显示原因 + 复核任务；**不重写已接受/已签/已执行历史** |
| 对象**投影** | **§7 第 381 行** | Affected records、owner、decision、implementation and resolution evidence |
| **API 能力** | **§9 第 406 行** | Record/correct events、open/resolve cases、approve/apply changes |
| **页面契约** | **§4.1 UI-08 第 155 行** | Cause、affected records、proposed resolution、approvals、implementation evidence、closure；**且可从工作台与对话进入** |
| 结案**条件** | §5.6 第 263 行 | 结案要求 **resolved blocking exceptions** |
| 客户**入口** | §3 第 116 行 / §4.1 UI-07 第 154 行 | 客户可**提交变更请求**（change requests） |

**教训升级**（补进 DR-0010 §2.3 已有那条）：判定某对象「需求未定义」之前，不能只看它作为**槽位／页面**出现的那一段，
必须**遍历该对象在文档中的所有出现**（本对象对应英文词 `exception` / `change` / `blocking`）。
一次全词检索就能避免这次误判 —— 这与 DR-0010 §2.1（用中文词检索英文文档）是同一类错误，只是层级更隐蔽：
**上次错在检索词的语言，这次错在检索结果的处理 —— 命中了就够，不该只看命中片段。**

**这个更正改变什么**：模型**不是**「由我们自己定」，而是**按权威条文填**。
`severity` / `owner` / `due time` / `decision` / `resolution evidence` / `closure` 是**必须项**；
状态机是**照抄六个值**；`blocking` 必须落在 §5.4 的三档依赖语义上。

### 1.3 为什么必须现在决定

1. **它是本支线最后一个「未开放」槽位**，而 PRD 第 183 行要求「每个槽位都有有意义的人工动作」。
   不决定，UI-05 就永远差一个槽位，AC-20（结案）也永远缺一半判据。
2. **AC-20 的主口径依赖它**：PRD 第 263 行「结案要求 resolved blocking exceptions」——
   没有异常对象，「阻断异常阻止结案」这条**无法验证**，AC-20 只能停在「部分 pass」。
3. **AC-12（变更传播）需要它作为受影响集合的来源**：PRD 第 285 行的 `needs_revalidation` 机制需要知道「哪些成果受影响」，
   而 §5.5 第 255 行的 `affected tasks/artifacts` 正是这个集合的权威出处。
4. **不决定的代价是可知的**：留「未开放」意味着 PRD 第 183 行在 exceptions 上**暂时不满足**，
   这必须**显式登记**（§7.2），不能靠沉默。

## 3. 决策（方案 A）与边界

### 3.1 数据模型（A1）：三张表

> **为什么是三张而不是两张**：HO 第 4 条明确「若公共审计机制不足，允许增加最小案件事件表，**不受『两张表』限制**」，
> 并把它与「重开的状态更新与审计必须同事务」绑在一起。本支线目前**没有**公共审计机制，
> 而「状态改了但没留痕」在案件这类对象上是不可接受的 ⇒ 采用第三张表，范围**只到案件**（不做通用审计平台）。

#### 3.1.1 `ent_exception` —— 案件本体

每一列的出处都必须可追。

| 列 | 类型 | 空 | 出处 | 说明 |
| --- | --- | --- | --- | --- |
| `id` | 整数 PK | 否 | — | |
| `org_id` | 整数 | **否** | PRD 第 385 行 | 作用域。**由服务端从 `assignment.org_id` 派生**（§3.1.4） |
| `assignment_id` | 整数 | **否** | PRD 第 381 行 + DR-0012 | **归属**。异常必属于某张委托单（新表，无历史数据，故 NOT NULL） |
| `kind` | 字符串(16) | 否 | PRD 第 277 行「as applicable to type」 | `exception` / `change_request` |
| `title` | 字符串(200) | 否 | §4.1 UI-08「Cause」 | 一句话摘要 |
| `cause` | 文本 | 是 | §4.1 UI-08「Cause」 | 原因 |
| `severity` | 字符串(16) | **否** | **§5.5 第 255 行「severity」** | `low`/`medium`/`high`/`critical`（**HO 已裁决四档**）。**不参与任何 allow/deny 计算**（§3.3） |
| `impact_kind` | 字符串(24) | **否** | **§5.4 第 224 行** | `informational`/`review-required`/`execution-blocking`（**照抄 PRD 取值域**）。**阻断的唯一判据** |
| `status` | 字符串(16) | 否 | **§6.1 第 277 行** | 六值照抄；合法转移**按 kind 分别**定义（§3.4） |
| `owner_user_id` | 整数 | 是 | §5.5「owner」 | 责任人（可空＝尚未分配） |
| `raised_by_user_id` | 整数 | **否** | HO 第 4 条「补齐提出人」 | **提出人** |
| `source` | 字符串(24) | **否** | HO 第 4 条「补齐来源」 | `manual` / `chat` / `customer` / `agent_proposal`（A1 只产生前三者） |
| `due_at` | 时间 | 是 | §5.5「due time」 | |
| `proposed_action` | 文本 | 是 | §5.5「proposed actions」 | 提议的处置 |
| `decision_note` | 文本 | 是 | §5.5「decision」 | 决定内容 |
| `decided_by` / `decided_at` | 整数／时间 | 是 | §7 第 381 行「decision」 | 决定人与时间（审计四要素） |
| `basis_revision_id` | 整数 | 是 | HO 第 4 条「决定依据版本」+ 第 7 条「精确版本」 | **决定所依据的受影响成果版本**（`ent_artifact_revision.id`）。`approved` 后必填 |
| `resolution_note` | 文本 | 是 | **§5.5「resolution evidence」** | 处置说明（**证据**） |
| `closure_disposition` | 字符串(32) | 是 | **§5.5 第 255 行**「explicit disposition rule, not a generic skip」 | `resolved`/`accepted_residual`/`cancelled`/`duplicate`/`superseded`；**关闭时必填**（§3.5） |
| `closed_by` / `closed_at` | 整数／时间 | 是 | §5.5「closure」 | |
| `revision_no` | 整数 | 否，默认 1 | **§6.2 第 283 行**「Every mutable aggregate has a revision counter」 | **案件自身**的乐观锁；命令带 `expected_revision` |
| `raised_at` | 时间 | **否** | §5.5 + §7 第 385 行 | **业务发生时间** |
| `created_at` / `updated_at` | 时间 | 否 | 既有约定 | **录入时间**；与 `raised_at` 分开 |

索引（PRD 第 385 行）：`(assignment_id, status)`、`(org_id, status)`、`(due_at)`。

> ⚠️ `basis_revision_id` 与 `revision_no` **不是一回事**：前者是「决定依据的**成果**版本」（业务），
> 后者是「案件记录自身的乐观锁」（并发）。两个都要，混用会让 §3.7 的版本校验失效。

#### 3.1.2 `ent_exception_link` —— 受影响项（§5.5「affected tasks/artifacts」、§7「affected records」）

| 列 | 类型 | 空 | 出处 | 说明 |
| --- | --- | --- | --- | --- |
| `id` | 整数 PK | 否 | — | |
| `exception_id` | 整数 | 否 | — | |
| `target_kind` | 字符串(16) | 否 | §5.5「affected tasks/artifacts」 | `task` / `artifact` |
| `target_id` | 整数 | 否 | 同上 | **必须校验归属与权限**（§3.1.4） |
| `applied_revision_id` | 整数 | 是 | **§4.3 第 180 行「applied revisions」** | 该受影响**成果**被应用到的**精确版本**；A2 期写入，**写入即「阻断被真实解除」的证据** |
| `created_at` | 时间 | 否 | — | |

**唯一约束** `(exception_id, target_kind, target_id)`：同一受影响项不得重复登记（PRD 第 253 行「prevent double counting」的同类要求）。

> `applied_revision_id` 是**引用**而不是自由文本，理由是 PRD 第 187 行：
> 「对话与工作台引用**同一个 artifact ID 与版本**」。写进备注里的版本号无法被机器核对，等于没引用。

#### 3.1.3 `ent_exception_event` —— 最小案件事件表（HO 第 4 条）

**每次状态变更、决定、关闭、重开都追加一条**；与状态更新**同事务**（§3.6）。

| 列 | 类型 | 空 | 说明 |
| --- | --- | --- | --- |
| `id` | 整数 PK | 否 | |
| `exception_id` | 整数 | 否 | |
| `seq` | 整数 | 否 | 同一案件内从 1 递增；`(exception_id, seq)` **唯一** |
| `event_kind` | 字符串(24) | 否 | `created` / `status_changed` / `decided` / `link_added` / `link_removed` / `applied` / `applied_rejected` / `closed` / `reopened` |
| `from_status` / `to_status` | 字符串(16) | 是 | `status_changed` / `closed` / `reopened` 必填 |
| `actor_user_id` | 整数 | **否** | 谁做的 |
| `note` | 文本 | 是 | 说明；**重开的 reason 落这里**（必填） |
| `evidence_ref` | 文本 | 是 | **证据引用**（HO 第 4 条）；`closed` 必填 |
| `basis_revision_id` | 整数 | 是 | **决定依据版本**（HO 第 4 条）；`decided` / `applied` 必填 |
| `payload_json` | 文本 | 是 | 附加结构化信息（link 目标、新 revision id 列表等） |
| `created_at` | 时间 | 否 | |

`seq` 在事务内取 `COALESCE(MAX(seq), 0) + 1`，受案件行锁保护；`(exception_id, seq)` 唯一约束是并发下的最后一道防线（冲突 → 整笔回滚）。

#### 3.1.4 归属与作用域（HO 第 1 条）

| 规则 | 落法 |
| --- | --- |
| **不新增 `entrustment_id`** | 异常从属 `assignment`；`assignment` 已带 `org_id` 与归属经理。再加一列会造出两个作用域，与 DR-0012 §3.1 的正交纪律相悖 |
| `assignment_id` **必填** | NOT NULL；创建时校验 assignment 存在且调用者是该委托的归属经理（`authz.py` 单一入口） |
| `org_id` **由服务端派生** | 从 `assignment.org_id` 取值。请求体若带 `org_id`，必须与之一致，否则 **403** —— 不接受客户端指定作用域。与 AC-02 入口隔离同源：本地作用域判断可被篡改 |
| **每条 link 都校验** | `target` 所属 `assignment_id` 必须 == 案件的 `assignment_id`；调用者对该 target 必须有权限。**跨委托链接 → 403** |
| **证据同样校验** | `evidence_ref` 引用的对象同样校验归属与权限；不允许引用别的委托的证据 |
| 读取侧同样过滤 | 列表／详情／工作台一律按归属 + `authz.py` 过滤，**不做「先返回再隐藏」** |

### 3.2 边界①：投影用**两套独立白名单**（HO 第 7 条）

> ⚠️ **v1 的主张被 HO 推翻并记录在此**：v1 说「复用 `project_for_customer` 同一函数，不新建第二套白名单」。
> v2 改为**独立白名单**。理由：案件与成果的可见性集合本来不同 —— 案件有「客户自提变更请求」这一窄口，
> 成果有 `CUSTOMER_VISIBLE_TYPES` 那一套。硬塞进同一函数，会让「异常一律不得对客」这条约束退化成
> 函数内的一个特殊分支；后续任何一次「顺手放宽」都会**同时**放宽两边。

`exceptions.py` 提供两个投影函数、两个白名单常量，共守同一纪律（**allow-list、先剔除再返回**），各有一条「白名单之外一律不出现」的用例。

| 投影 | 用途 | 产出 |
| --- | --- | --- |
| `project_case_internal()` | 工作台槽位 / UI-08 | §4.3 四类内容（open cases / blocking impacts / proposed changes / applied revisions）+ §7 的 owner / decision / implementation & resolution evidence |
| `project_case_for_customer()` | 客户可见面 | **只**暴露客户**自己提出**（`kind='change_request'` 且 `source='customer'`）的单据的 `title` / `status` / `raised_at` / 对客可见的成果引用 |

**对客投影必须剔除**：任何 `exception` 的字段、`owner_user_id`、`severity`、`impact_kind`、`decision_note`、
`resolution_note`、`closure_disposition`、`raised_by_user_id`、`source`、内部成果引用、以及 `ent_exception_event` 的**全部**内容。

> 内部成果引用本身也受白名单约束（`ent_artifact` 侧已有 `CUSTOMER_VISIBLE_TYPES`）——**双层白名单**是刻意的冗余。

**客户入口的落位（HO 第 6 条）**：客户提交变更请求的界面属 **UI-07**（客户页，未开工），本裁定**不视为取消 R1 要求** ——
R1 仍要求该能力；本期记为**未覆盖**（§6 未执行项），不假装已有。

### 3.3 边界②：阻断只认 `impact_kind`，`severity` 不参与（HO 第 2 条）

**阻断判据（单一实现，结案检查与执行命令共用）**：

```
blocking(case) := case.impact_kind == 'execution-blocking'
              AND (
                    (case.kind == 'exception'      AND case.status != 'closed')
                 OR (case.kind == 'change_request' AND case.status NOT IN ('closed','rejected'))
              )
```

**一致性约束**：

| 编号 | 约束 | 违反 | 出处/理由 |
| --- | --- | --- | --- |
| **C1** | `severity='critical'` ⇒ `impact_kind='execution-blocking'`（创建与更新都校验）。**单向**：`execution-blocking` 不要求 `critical` | **400** | PRD §5.5「Critical unresolved cases block the relevant execution/closure actions」 |
| **C2** | `impact_kind='execution-blocking'` ⇒ **必须**至少一条 `ent_exception_link` | **400** | PRD §5.4「prevent the **corresponding action**」—— 没有对应动作就没有"the corresponding action" |
| **C3** | `severity` 的变更**不得**隐式改写 `impact_kind`；`impact_kind` 只能由显式命令（显式传字段 + 显式事件）变更 | **400**（隐式改写一律拒） | HO 第 2 条「降低严重度不自动解除阻断」 |

**C3 的效果**：`critical → high`（不动 `impact_kind`）之后 `impact_kind` 仍是 `execution-blocking`，
**阻断依然成立**。要解除阻断只能显式改 `impact_kind`，或把案件处置到终结态。

**为什么不能把 `severity=critical` 当阻断**：那样 `severity` 就成了**权限级开关** ——
改一个展示用字段就能放行或卡住结案与执行。严重度是**业务判断**，阻断是**流程约束**，
两者的变更权限、审计要求、复核人都不同，不能合并（与 DR-0012 §3.1「作用域与归属正交」同一类纪律）。

**阻断作用面（两处，都只用同一判据）**：

1. **已有执行命令** —— `POST /tasks/{task_id}/complete`。
   该端点**已有**前置门禁（`tasks.py::complete_task`：「所需证据未齐 → 409」）。
   本片在**同一处**追加：该任务若被某条 `blocking(case)==true` 的案件 link 命中 → **409**，
   响应**指出案件 id 与原因**（不能只说「有阻断项」）。
2. **结案** —— `费用与结案` 槽对应的结案命令**尚未存在**（S3）。
   **硬约束：结案命令首次上线即须接同一判据**，不允许「先上线、后补门禁」。
   上线后：只要该委托下存在 `blocking(case)==true` 的案件，结案被拒，并**给出是哪几条**。

> **刻意不塞进 `start_task`**：`POST /tasks/{task_id}/start` 有 `_assert_precondition_satisfied`
> （前置任务未完成不能开始）。异常阻断**不**并入那里 —— 前置任务是**任务间依赖**，异常阻断是**案件约束**，
> 两者的失败语义与可解除方式不同（前者靠完成任务，后者靠处置案件）。分开保留，避免两种约束互相掩盖。
> 另注：`ent_workflow_task` 的"前置任务"与 §5.4 的"依赖类型 informational/review-required/execution-blocking"
> **不是同一概念**，本记录不声称它们等价。

### 3.4 边界③：两套状态机，分别定义转移与条件（HO 第 3 条）

PRD 第 277 行给的六个值 `open / in_review / approved / rejected / applied / closed` 带一句 **"as applicable to type"**。
本记录据此把两类案件**分别**定义。

#### `kind='exception'`（真实异常）

> **`rejected` 的语义 = 提交的处置方案被驳回**。真实异常**仍在** ⇒ **不是终态**，阻断**保持**。

```
open       → in_review
           | approved
           | rejected
           | closed   仅 closure_disposition ∈ {cancelled, duplicate, superseded}
in_review  → approved | rejected | open（退回补充）
approved   → applied（须满足 §3.7 前置）
           | rejected（方案被否决）
           | closed   仅 {cancelled, duplicate, superseded}
rejected   → in_review（重新提方案） | open
           | closed   仅 {cancelled, duplicate, superseded}
applied    → closed   仅 {resolved, accepted_residual}
closed     → open（重开，必带 reason；见 §3.6）
```

#### `kind='change_request'`（变更请求）

> **`rejected` 的语义 = 变更请求被否** ⇒ 该变更**不会发生** ⇒ **是终态段，不再阻断**。

```
open       → in_review
           | rejected（不采纳）
           | closed   仅 {cancelled, duplicate, superseded}
in_review  → approved | rejected | open（退回补充）
approved   → applied（须完成实际应用，见 §3.7）
           | rejected
           | closed   仅 {cancelled, superseded}
rejected   → closed   仅 {cancelled, duplicate, superseded}
applied    → closed   仅 {resolved, accepted_residual, superseded}
closed     → open（重开，必带 reason；见 §3.6）
```

**同一个 `rejected` 在两种 kind 下语义不同**，这正是 "as applicable to type" 的落地：
驳回一个**处置方案**不会让真实异常消失；拒绝一个**变更请求**则意味着该变更不会发生。
⇒ 阻断判据按 kind 分别（§3.3），**不共用一句**。

**非法转移**（自环、未列出的组合，如 `closed → applied`、`exception` 的 `rejected → resolved` 关闭）→ **409**，响应带当前状态（PRD §6.1 第 279 行）。

### 3.5 边界④：关闭必须校验处置规则与证据（HO 第 3 条）

| 目标态 | 前置校验 | 违反 |
| --- | --- | --- |
| 任意 `closed` | `closure_disposition` **必填**（缺失 → **400**，不是默认值填充） | 400 |
| `closed` + `resolved` | ① 每条 link 的 `applied_revision_id` **已写入**（确实应用过）；② `resolution_note`（证据）非空 | 409 / 400 |
| `closed` + `accepted_residual` | ① `severity != 'critical'`（critical 按 C1 必须阻断并被解决，不能以残留关闭）；② `decision_note` 与 `resolution_note` 均非空 | 400 |
| `closed` + `cancelled`/`duplicate`/`superseded` | `decision_note` 非空（说清为什么这单本身不该存在） | 400 |

**关键**：`exception` 不允许从 `rejected` 以 `resolved`／`accepted_residual` 关闭 ——
这正是 HO「**不允许通过驳回处置方案解除真实异常**」的落地。

**不提供「一键关闭」**：关闭必须回答「凭什么关」，这正是 §5.5 那句 `not a generic skip` 的意思。

### 3.6 边界⑤：重开与审计**同事务**（HO 第 4 条）

- `closed → open`（重开）**允许**（PRD 第 279 行只禁止非法转移与自动回滚；AC-20 要求「legitimate disposition/reopen retains audit」）。
- **硬约束**：重开命令必须在**同一事务**内同时完成
  (a) **状态更新**（`status='open'`、`revision_no + 1`、清 `closed_by`/`closed_at`/`closure_disposition`），与
  (b) **审计追加**（`ent_exception_event`：`event_kind='reopened'`、`actor_user_id`、`note`=reason、
  `from_status='closed'`、`to_status='open'`、`created_at`）。
  任一失败**整体回滚** —— 不允许「状态改了但没留痕」，也不允许「留痕了但状态没改」。
- 同一规则适用于**所有**状态变更、决定、应用、关闭：**状态与事件同事务**。
- 事件行**只追加**，从不 UPDATE、从不 DELETE；历史依次保留 ⇒ 「重开再关闭的两轮历史完整」可判定。

### 3.7 边界⑥：应用变更的事务边界与精确版本（HO 第 7 条）

**「应用变更」＝对受影响成果走既有 `append_revision` + `confirm_revision`，案件只引用版本。**
**单事务**内按序执行：

1. 取**案件行锁** → 校验 `status='approved'`（且该 kind 允许）与 `expected_revision` 匹配（否则 **409**）；
2. **校验依据版本未变**：对每条 link，受影响成果的**当前版本**必须仍等于案件的 `basis_revision_id`。
   若已变 → **409**，事件记 `applied_rejected`，案件**保持 `approved`**
   —— **旧批准不得直接应用到新内容上**（对应 AC-12 的 `needs_revalidation` 语义），需重新批准；
3. 对每条 link 的成果：`append_revision`（新版本）→ `confirm_revision`（绑定精确版本）→ 写 `link.applied_revision_id`；
4. 案件 `status='applied'`、`revision_no + 1`；
5. 追加 `applied` 事件（`actor_user_id`、`basis_revision_id`、新 revision id 列表）。

**失败即整体回滚** ⇒ 不产生「部分成果已生效」的中间态。
写端点带 `Idempotency-Key`：重试返回首次结果，**不产生重复副作用**（第二次不新建 revision）。

⇒ `applied` **只在**上述事务提交成功后才成立 —— 不允许通过直接改状态字段到达（HO 第 3 条「applied 仅在实际应用完成后成立」）。

### 3.8 横切：回退**不得**绕过已登记阻断（HO 第 7 条）

| 回退类型 | 对阻断的影响 | 约束 |
| --- | --- | --- |
| **代码回退** | 阻断检查随代码消失（这是回退的固有后果） | 案件与事件**数据保留**；重新部署即恢复。**不允许**把「回退代码」当作解除阻断的常规路径 |
| **数据回退**（追加反向迁移） | **不得**用于解除阻断 | 阻断只能通过案件**合法流转到 `closed`** 来解除。以「删案件数据」清阻断一律拒绝 |
| **槽位回退** | `exceptions` 槽切回 `available=False` | 阻断判据与案件记录**保留**；`complete_task` 的阻断检查**不随槽位一起关闭**（它是执行门禁，不是展示） |

### 3.9 复用的公共机制（不另建一套）

| 机制 | 复用方式 | 出处 |
| --- | --- | --- |
| 迁移 | `backend/migrations/ent_exception.py`（三张表），`ent_` 前缀，`sql` 用 mysql/sqlite 方言字典 | DR-0001 |
| 幂等 | 全部写端点带 `Idempotency-Key`，进 `scope_matrix` 的 `idempotent=True` | 开发规范六条公共机制之二；PRD 第 409 行 |
| 案件乐观锁 | `revision_no` + `expected_revision`，过期 **409** | PRD 第 283 行 |
| 成果版本 | 「应用变更」走**既有** `append_revision` + `confirm_revision`，案件只**引用**版本 | PRD 第 180/187 行 |
| 权限 | `assignment_id` 是**归属**不是权限边界；判定仍只有 `authz.py` 一条入口 | DR-0012 §3.1 |
| 人工接管优先 | Agent 提案（`source='agent_proposal'`）**不得**覆盖人工已作的决定；A1 不产生 Agent 提案 | 开发规范；PRD 第 303 行 |
| 作用域 | 新端点**必须**在 `scope_matrix.py` 声明（本片落地时 52 条 → **60 条**，8 条案件端点已登记；后续 60 → 60+N） | ENT-010 / AC-10 |
| 时区与时间 | 存储带时区、显示 Asia/Shanghai；`raised_at`（事件）与 `created_at`（录入）分开 | PRD 第 385 行 |

### 3.10 为什么**不**把它做成一种成果类型

PRD 第 100 行确实把 `exceptions` 列在 artifacts 的宽泛枚举里，容易被读成「加个 `artifact_type` 就行」。**这是错的**：

* PRD 第 381 行把 `Exception / ChangeRequest` 与 `Artifact / ArtifactRevision` **并列为两个不同对象**；
* 成果的状态机是 `draft/in_review/confirmed/superseded`（第 275 行），案件是 `open/.../closed`（第 277 行）—— **两套状态**；
* 成果的语义是「**内容**有版本」，案件的语义是「**案件**有流转」。把案件塞进成果，会让「确认精确版本」
  这个动作同时对内容和流转生效，直接破坏 §6.2 第 283 行「confirmed/released versions are immutable」。

⇒ `registry.py` **不动**。这条要写进 DR 的理由是：否则下一个人会走这条「更省事」的路。

## 5. 回退方式

**代码回退**（与数据库回退**分开说明**，不默认 downgrade 安全）：

* 新增模块与端点独立，停用即不执行；`workbench.py` 的 exceptions 槽**只有一个常量切换**回
  `available=False` + `unavailable_reason`，其余槽位不受影响；
* 前端 UI-08 页与路由登记可单独下线；`routes.js` 移除条目即可，路由静态门禁会随之更新；
* `tasks.py::complete_task` 的阻断分支随代码消失（固有），**案件与事件数据保留**（§3.8）；
* **不修改**任何既有迁移模块，因此代码回退不牵动已发布的 DB 结构。

**数据回退**：

* **无自动 downgrade**。三张表是**新增**，回退后残留不影响旧代码；
* 已登记的案件**保留** —— 它是事实记录，清理它等同于抹掉「曾发生过什么」，且**不得**作为解除阻断的手段（§3.8）；
* 若确需物理删除，**追加一条反向迁移条目**（`id` 只增不改、迁移非事务，按 DR-0001）。

**外部能力**：无外部依赖，无需关闭第三方能力。
