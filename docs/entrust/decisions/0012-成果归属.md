## 1. 背景

### 1.1 直接事实：成果与委托单之间没有关联键

ENT-020 开工侦察时核对模型，得到三条互相印证的事实：

| 事实 | 依据 |
| --- | --- |
| `ent_artifact` 的外键是 **`entrustment_id`**，没有 assignment 维度 | `backend/migrations/ent_artifact.py` |
| `ent_entrustment` 是 **(org_id, entrust_user_id)** 的**组织级授权**，与具体委托单无关 | `backend/migrations/ent_org_access.py` |
| `ent_assignment` 里**没有** `entrustment_id`（反向指针不存在） | `backend/migrations/ent_assignment.py` |

⇒ 成果只能落到 `(owner_user_id, org_id)` 这个**粗维度**上。**同一货主在同一组织下的多张委托会互相串成果**。

这不是实现困难，是**建模缺口**：`entrustment` 这个对象在权威 PRD 里几乎不存在，它是实现侧为承载「组织×货主」授权关系而引入的，于是"成果挂在授权上"就成了当时的自然写法 —— 但**授权 ≠ 委托单**，一个授权覆盖该货主的**所有**委托。

### 1.2 与权威材料直接冲突

| 权威条文 | 要求 | 当前模型能否满足 |
| --- | --- | --- |
| PRD 第 187 行 | 对话与工作台引用**同一个 artifact ID 与版本** | ✘ 工作台无法确定"这一单"的成果是哪几条 |
| PRD 第 405 行 | 工作台是 authoritative records 的 **assignment projection** | ✘ 只能投影到授权，不能投影到单张委托 |
| DR-0010 §3.3 | 成果是各槽位（`procurement`/`customer_contracts`/`execution`/`settlement`）的**主要数据落点** | ✘ 槽位是**单张委托**的呈现单位，取数却取不到单张委托 |

### 1.3 为什么必须现在决定

DR-0010 §4 写着「**不加表、不加迁移**」。这条结论**建立在一个从未被验证的前提上**：*成果可按单张委托读取*。
前提在 1.1 被证伪。按本支线规矩（见 `01-决策记录模板.md` 填写要求 4、5），**前提被证伪就必须修正结论并留痕，不得静默变通**。

若此刻不决定，UI-05 首片只有两种走法，都不能接受：

* 用 `(owner_user_id, org_id)` 聚合 ⇒ 同一客户多张委托互相串成果，**交出一个错误的界面**；
* 不投影成果 ⇒ 首片与 PRD 第 187 行、DR-0010 §3.3 均不符，**交出一个残缺的界面**。

## 2. 候选方案

| 方案 | 描述 | 优点 | 缺点 | 风险 |
| --- | --- | --- | --- | --- |
| **A（采用）** | 给 `ent_artifact` 补**可空** `assignment_id` + 单委托查询索引，追加一条迁移；贯通创建 / Agent 采纳 / 单委托查询 / 权限校验 / 版本引用 | 满足 PRD §4.3 与第 187/405 行；UI-03「跳到精确成果」与 AC-05 同源有了数据前提；纯增量、可单独回退 | 需修正 DR-0010 §4 的结论；历史存量成果**无法归属**（留 NULL 并在界面如实暴露） | 低。加的是可空列，旧代码不感知；风险集中在"归属写错"，由 §3.3 的三条校验挡住 |

## 3. 决策

**选择：方案 A。**

理由（按权重）：

1. **权威材料是唯一真相**：PRD 第 187 行与 §4.3 是硬要求，不是可协商的实现偏好。B 会让首片与它直接不符。
2. **A 是纯增量、可单独回退**：新增可空列不改变任何既有语义，也不触碰 `create_all` 管理的既有表。
3. **B 不计作 UI-05 交付完成**（HO 明示）：B 只能作为**临时骨架**存在，不能借它宣称验收通过。
4. **代价是可知的**：唯一真实代价是"历史存量成果无法归属"——而这个代价**必须保留为可见的未知**，不能被"猜测回填"消掉（见 §3.2）。

### 3.1 `assignment_id` 是「归属」，不是「权限边界」

这是本决策最容易被后续改动破坏的一条，必须写死：

* **权限判定仍然只有一条入口** —— `authz.py`（`assert_can_view_entrustment` / `assert_can_view_assignment` / `assert_can_write_entrustment`）。
* `assignment_id` **只回答"这条成果属于哪一单"**，不参与任何 allow/deny 计算。
* `entrustment_id` **保持 NOT NULL**：组织级授权仍是**权限与展示的作用域边界**。两者是"作用域"与"归属"两个正交概念，不得合并。

### 3.2 历史数据：**不猜测回填**

历史行（本迁移之前创建的成果）`assignment_id` 保持 **NULL**。

**明确拒绝**按 `(owner_user_id, org_id)` 批量回填，理由：那会把"我们猜的"写成与"确实属于某委托"**无法区分的既成事实**；而归属错误在**结案与对账**阶段是灾难性的（对错单、结错账）。按本支线「未知值保持未知」的约定，NULL 是**正确**的表达，不是待清理的脏数据。

存量的出口：`count_unassigned(owner_user_id, org_id)` 只**报数**，供界面显式呈现「归属待确认」；不提供"一键回填"。

### 3.3 归属有效性：三条同时成立，否则拒绝

创建时若声明了 `assignment_id`，服务端（`_resolve_attribution`）逐条校验：

| # | 条件 | 不满足时的语义 |
| --- | --- | --- |
| 1 | 委托单**存在** | 404（不区分"不存在"与"无权知晓"） |
| 2 | **同货主**：`assignment.owner_user_id == entrustment.entrust_user_id` | 400（否则会把 A 货主的成果挂到 B 货主的委托上） |
| 3 | **同组织**：`assignment.org_id == entrustment.org_id`，且**非 NULL** | 400（委托单尚未选定服务经营主体时**不允许**归属：授权是组织级的，挂到一张还没选定主体的委托上等于归属一个还不存在的委托关系） |

**三条规则只有一份实现**：`authz.load_assignment_for_entrustment()`。
Agent 会话创建（`agent_api.create_session`）原先自己写了一遍等价判断，本切片改为复用同一函数 —— **同一业务规则不得有两份实现**，否则两者会各自漂移。

### 3.4 归属由服务端上下文派生，不由客户端声明

`assignment_id` 虽由请求体传入，但它是**声明待校验**而非**直接采纳**：必须过 §3.3 三条并落在调用者可见的授权范围内。客户端**不能**通过传一个任意 ID 把成果挂到别人的委托上。

## 4. 影响

- **后端**：
  - `artifacts.py`：`create_artifact` 增可选 `assignment_id`；新增 `list_by_assignment()`（单委托精确匹配，**不做任何"回退到货主或组织"的放宽**）与 `count_unassigned()`（只报数）；`_row_to_artifact` / 读取列清单带出 `assignment_id`。
  - `artifacts_api.py`：新增 `GET /api/v1/entrust/assignments/{assignment_id}/artifacts`（可见性复用 `get_assignment` 规则，不可见一律 404）；`POST .../artifacts` 接入归属校验；异常映射抽到共享的 `_http.map_access_denied`。
  - `authz.py`：新增 `load_assignment_for_entrustment()`，供成果与会话共用。
  - `agent_api.py`：会话创建改为复用同一校验。
  - `scope_matrix.py`：新增端点须同步声明，矩阵条目 **49 → 50**。
- **前端**：UI-05 首片按**单张委托**读取成果槽位；新页面自首个切片起进入 `MIGRATED_PAGES`（DR-0011 约定）。
- **数据库迁移**：**有，1 条**（`backend/migrations/ent_artifact_assignment.py`）——
  新增可空列 `assignment_id` + 索引 `idx_ent_artifact_assignment(assignment_id, artifact_type)`；
  方言字典（mysql / sqlite）；纯 additive。
  ⚠️ **本条明确修正 DR-0010 §4 的「不加表、不加迁移」**：该结论的前提（成果可按单张委托读取）已被证伪，结论随之失效。
- **功能开关**：沿用 `ENTRUST_ENABLED`，无新增开关。
- **对旧流程的影响（AC-01）**：**无**。新增列可空、旧 INSERT 不指定该列即写 NULL；`entrustment_id` 语义未变；权限结论未变；不触碰货主/船东/港口三端的既有页面与接口。
- **需要同步修改的文档**：本记录；**DR-0010 §4**（加修正指引，原文保留、状态标注）；`02-0010与0011修订开发方案.md`；接口契约与 UI-05 验收子项。

## 5. 回退方式

**代码回退**（与数据库回退**分开说明**，不默认 downgrade 安全）：

* `ent_artifact_assignment.py` 是**独立迁移模块**，停用该模块即不再执行；本切片**未修改**已发布的 `ent_artifact.py`。
* 读写路径上 `assignment_id` 全部是**可选参数**：回退代码后新列仍在表中但被忽略，旧行为（按授权聚合）恢复。
* 服务端新增的 `GET /assignments/{id}/artifacts` 端点可单独下线，不影响既有 8 个成果端点。

**数据回退**：

* **无自动 downgrade**。回退后残留列**不影响**旧代码（旧 INSERT 不指定该列 → NULL）。
* 已写入的 `assignment_id` **保留**，不自动清理 —— 它是事实记录，清理它等同于抹掉归属证据。
* 若确需物理删除列，**追加一条反向迁移条目**（本支线约定：迁移非事务、`id` 只增不改、无自动 downgrade）。

**外部能力**：无外部依赖，无需关闭任何第三方能力。
