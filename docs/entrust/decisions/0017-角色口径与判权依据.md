## 1. 背景（三条事实，逐条对着代码核过）

**事实 ①：`switch-role` 写的是用户行。**
`auth/service.py:127` 的 `switch_role` 直接 `user.current_role = role` —— **落库、用户级**。

**事实 ②：判权读的是用户行，不是 token。**
`auth/dependencies.py:39` 的 `get_current_user` 只从 token 取 `sub`，再
`db.get(User, int(payload["sub"]))` 拿实体；各模块的 `_require_role(user, ...)`
（如 `ship/router.py:38` 的 `if user.current_role != role`）比的是**数据库里的** `user.current_role`。
覆盖点：`agent` 3 处、`cargo` 1 处、`match` 2 处、`order` 5 处、`payment` 1 处、`ship` 4 处。

**事实 ③：token 里签了 `role`，但全仓没有任何一处读它。**
`core/security.py:25` 的 `create_access_token(user_id, openid, role)` 把 `role` 写进 payload；
而检索不到读该 claim 的代码 ⇒ **它是一个死字段，并且具有误导性** ——
看起来像"每会话角色"，实际判权与它无关。

**后果（两个真实场景）**：

* 同一账号在 A 设备切到 `owner` 之后，B 设备（仍登录着、页面停在货主工作台）
  **下一次请求就按 owner 判权** —— 轻则 403，重则拿到另一角色的数据视图；
* 走查/自动化里更直接：为了"进某个落点页"点一下别的身份卡，就把**后续所有 API 的角色**
  改掉了（ENT-043 的 2 条假失败就是这么来的；当时先误判成"请求超时"）。

---

## 2. 候选方案

| 方案 | 描述 | 优点 | 缺点 | 风险 |
| --- | --- | --- | --- | --- |
| **A. 承认「当前角色 = 账号级单值」**（保持现状语义，只做止损） | ① 删掉 token 里的 `role` claim（或改名 `role_snapshot` 并在 `security.py` docstring 写明"仅供参考、**不参与判权**"）；② `switch-role` 的 docstring / 响应 / 前端身份卡文案写明"**这是账号级切换，会影响你在所有设备上的身份**" | 零行为变更；不动 6 个 router；无数据迁移 | 多设备/多会话仍互相干扰；"点一下身份卡就全变了"与 UI 上"身份卡"的隐喻不完全一致 | 低 |
| **C. 改为「每会话独立」** | token 固化签发时的角色；`switch-role` **只签发新 token**、不写 `user.current_role`（可另存 `default_role` 供下次登录用）；`get_current_user` 返回的角色取自 token claim | 多设备互不干扰；claim 名副其实；判权可不查库 | **判定点全量改造**（6 个模块 + 依赖）；**已签发 token 的语义改变**（属行为变更，需按旧接口纪律评估）；要迁移一个"默认角色"字段 | 中高（触点含 `order` / `payment` 旧域核心端点） |

> ⚠️ 两个方案都**不是"顺手改"**：A 动 token 契约（虽只是删一个死字段），C 动 6 个模块的判权依据。
> ⇒ 本条须**先裁决再实现**，不并入其它切片。

---

## 3. 决策

**（待裁决）** —— 本文不改任何实现。

> 倾向（供参考，**非结论**）：**先落 A 的止损，把 C 作为独立切片**。
> 理由：C 的触点包含 `order` / `payment` 等旧域核心端点，需单独回归与灰度；
> 而 A 只需删一个**已经没人读**的字段，却能立刻消除"token 像每会话角色"的误导，
> 并让"切身份是账号级动作"这件事在文案上被明确。

---

## 4. 影响

* **后端**：A —— 仅 `core/security.py` 的 payload 与 docstring；C —— `auth/dependencies.py`
  + 6 个模块的 `_require_role`（约 16 处）。
* **前端**：A —— `utils/auth.js` 的 `enterRole` 文案与"切换会影响所有设备"的提示；
  C —— 切换后要**替换本地 token**（现在是同一个 token 继续用）。
* **数据库迁移**：A 无；C 需新增"默认角色"列（`user.current_role` 可保留为默认值出口）。
* **功能开关**：建议 C 走开关（新老判权并存一段时间），A 不需要。
* **对旧流程的影响**：**A 无行为变更**；C 会改变"已签发 token 的判权结果"，
  需按 AC-01（不破坏既有自主发货/船东/订单/支付/Agent 行为）逐域回归。
* **需要同步修改的文档**：`docs/entrust/decisions/0009` §8.5⑤（缺口登记 → 裁决结果）、
  本记录的"已登记待决事项"行；若选 C，另需在交付计划附录 I 增一行。

---

## 5. 回退方式

* A：删字段是**净减法**，回退即恢复 payload 里的 `role`；无数据影响。
* C：**必须能退回 A 的判权路径**（开关 + 读 `user.current_role` 的旧分支保留一个版本），
  否则一旦发现某个旧域端点行为变化，将无法快速止血；`default_role` 列可空、可回滚。

---

## 6. 验证方式

* **A**：全量后端测试 + 一条断言"token payload 不含 `role`（或含 `role_snapshot`）"；
  走查里"点身份卡后另一会话是否受影响"**仍会受影响** —— 因此**必须**在文案与文档里写明，不能靠测试掩盖。
* **C**：新增用例"两个 token 各自携带不同 role，互不影响"；并回归 6 个模块的角色拒绝路径
  （每个 `_require_role` 至少一正一反）；走查 `--section 25,26,4b,9` 复跑，
  确认 ENT-043 那个"前面的章节切角色、后面章节仍能按需取数"的行为不再依赖清库。
* **未执行项**：本条**尚未实现任何代码**，上述验证均为"裁决后执行"的清单。
