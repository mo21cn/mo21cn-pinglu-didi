# DR-0006 附件文档提取机制

- 状态：**已采纳**（2026-09-13）
- 关联：S1 第 6 条 / AC-17 / AC-18；ENT-013；PRD §3.2 建模红线
- 前置：ENT-009（附件与提取状态字段）、ENT-011（Agent 作业与来源目录）

---

## 背景

S1 第 5 条只建了附件的**状态字段**（`extract_status`），没有提取器。第 6 条要把
「文本 / CSV / 文本型 PDF」读成可用文本，并「扫描件人工录入降级」（AC-17）。
提取结果要能进 Agent 上下文（AG-02 的报价解析），也要能被货主/经理在页面上核对。

约束：
- 项目依赖中**没有任何 PDF / Office 解析库**（requirements 只有 fastapi / pydantic /
  sqlalchemy / pymysql / redis / httpx / numpy / pytest / ruff / mypy）；
- 附件总量上限 20 MiB，类型白名单已定（含 `.pdf` / `.docx` / `.xlsx` / 老式 `.xls` / 图片）；
- 附件是**不可信数据**（AC-18）；上传者可以撒谎声明 MIME；
- 每个 `ent_` 表的时间列在 SQLite 是 TEXT、在 MySQL 是 DATETIME（BASE-002 教训）。

---

## 决策

### 1. 提取器用**纯标准库**实现，不引入 pypdf / openpyxl / python-docx

| 方案 | 结论 |
|---|---|
| 引入 `pypdf` + `openpyxl` + `python-docx` | **否决**：一条为"提取文本"引入的依赖会跟着镜像、CI 缓存、漏洞扫描、版本升级一起长期维护，而它换来的只是**一次近似提取**；三者都是纯 Python，省下的实现量有限 |
| 纯标准库（`zlib` / `zipfile` / `ElementTree`） | **采纳**：`docx`/`xlsx` 本质是 zip+XML；文本型 PDF 用 `zlib` 解 Flate 流后扫描文本操作符即可 |
| 用外部命令（`pdftotext` / LibreOffice） | **否决**：把部署环境变成隐式依赖，且无法在 CI 里隔离 |

代价（已接受）：PDF 提取是**近似的**（不渲染版式），且不支持 CID 字体 ToUnicode 映射。

### 2. PDF / 图片 / 老式 `.xls` 分三种结论，**不假装成功**

| 情形 | 结论 | 下一步 |
|---|---|---|
| `text/*`、`.docx`、`.xlsx`、有文本层的 PDF | `done` | 可引用（带 `truncated` 提示） |
| 扫描件 PDF、图片、文本层解出即噪声（CID 字体） | `needs_transcription` | 人工转录端点补录 |
| 老式 OLE2 二进制（`.xls`/`.doc`）、未知类型 | `unsupported` | 另存为新格式或人工转录 |
| 文件本身坏了（zip 损坏 / XML 非法） | `failed` | 换文件 |

**为什么把"噪声"判成 `needs_transcription` 而不是 `done`**：返回一堆乱码会被下游
当成真数据用（正则抽金额会抽出假数字）。**宁可说"没有文本"，不给出可疑文本。**
若解出的是噪声且内容本身就不是文本（二进制冒充 `text/plain`），则判 `unsupported`
—— 让人去转录一份二进制文件是白费力气。

### 3. 附件声明的 MIME **不参与决定处理路径**（AC-18）

嗅探顺序：**魔数 → 声明 MIME → 扩展名**。PDF 头、PNG/JPEG/WebP 魔数、`PK\x03\x04`
+ 条目名、OLE2 头都优先于 `Content-Type`。嗅探结果与声明不一致时**记 note 但不改变路径**。

理由：若听信声明，上传者就能决定服务端如何解释字节（把任意内容标成 `text/plain`
让它进文本路径）。上传白名单只能拦"声明不合规"，拦不住"声明撒谎"，所以提取层必须自己判。

### 4. 提取文本单独一张表 `ent_attachment_text`（1:1，可重抽覆盖）

- **体积差三个数量级**：2 MiB 的报价 PDF 可能只有 3 千字文本，合进附件表会让
  "列附件"这种高频读拖着正文；
- **生命周期不同**：文件不重传就不变，文本**可重抽**（改提取规则、先失败后成功、人工转录覆盖）；
- **来源必须可分**：机读提取 vs 人工转录的可信度不同（`source`），UI 与 Agent 都要能区分。

### 5. 同步端点，**不写 `pending` / `running` 中间态**

`extract_status` 取值域里保留 `pending` / `running` 是为将来"提取作业化"
（扔进作业表由 worker 领取）预留。当前是同步端点：一次请求内跑完并落终态。
同步执行下写一个 `running` 中间态**外部永远观察不到**，只会让人以为背后有 worker ——
所以本端点不写它，写了才是说谎。这一限制登记在"未覆盖"里。

### 6. 状态与文本**不允许矛盾**：重抽结论变成"没有文本"时撤销旧文本

`extract_status` 与 `ent_attachment_text` 必须一起看。若重抽（改了提取规则/部署了新版本）
得到 `needs_transcription` 而旧文本还留着，就会出现"状态说没文本、接口却能读出内容"
—— UI 与 Agent 会各按一半信息行动。因此非 `done` 结论一律**删除旧文本行**；
删的是**派生数据**（随时可由原文件重抽或由人重建），**原始附件文件永不动**。

### 7. 权限不新增：提取与转录复用上传的 `entrust:quote:create`

两者处理的还是同一份附件，凭空多一个权限只会多一处漂移。可见性判定**复用
`attachments_api.load_visible_attachment`**（与元数据读取、授权下载同一实现），
异常映射复用 `map_attachment_error` —— 同一份规则只有一处实现。

### 8. 提取文本进 Agent 上下文时**比落库更严地截断**

`EXTRACTION_MAX_TEXT_CHARS`（落库上限，默认 200k）> `AGENT_ATTACHMENT_TEXT_CHARS`
（进提示词上限，默认 8k）。提示词还要留给任务、成果、来源目录，不能让一段报价独占。
截断事实随 `text_truncated` 一起进上下文与提示词，让模型知道"这不是全文"。
`attachment_text` 只在 `extract_status = done` 时进入**来源目录**（`build_source_catalog`），
所以"没提取成功却引用 attachment_text"会被判为编造来源。

## 未被本决策覆盖

1. **OCR**：图片与扫描件不尝试 OCR，一律人工转录。若将来要求自动识别，
   需单独决策（必然引入重依赖或外部服务）。
2. **PDF 版式**：不保留表格/分栏/页眉页脚的视觉顺序；CID 字体（无 ToUnicode 映射）
   的 PDF 会被判为 `needs_transcription` 而非尽力猜。
3. **`pending` / `running` 仍未使用**：提取未作业化，大文件同步提取会让请求变长。
4. **`.xlsx` 只取单元格文本**：不保留格式、公式、日期类型（数值按原样文本输出）。
5. **文本不参与客户投影**：提取文本目前只给经理侧与 Agent 用；货主侧读路径的分叉
   在 S3 统一处理。

---

## 后果

- **正面**：零新增依赖；结论可解释（每个状态都有 `detail` 与 `notes`）；
  截断与来源都可追溯；时间列方言有真实 MySQL 用例守护。
- **负面 / 需接受**：PDF 提取精度有限且必须自曝；不支持 OCR；
  老式 `.xls` 明确不支持（用户需另存）；
  同步提取在超大文本文件上会拖长请求（当前上限下可接受）。
