## 2. DR-0010 修订后口径（产品定案，可直接开工）

### 2.1 七槽位（顺序与稳定 key 固定）

| 序 | 稳定 key | 槽位名称 | 主要内容 |
| --- | --- | --- | --- |
| 1 | `overview` | 委托概况 | 客户、服务主体、货物、路线、时间、负责人、缺项 |
| 2 | `plan_tasks` | 方案与任务 | 方案版本、运输段、任务、前置条件 |
| 3 | `procurement` | 采购与报价 | 船东／供应商报价、比价、采购确认 |
| 4 | `customer_contracts` | 对客方案与合同 | 对客报价、客户接受、合同及签署证据 |
| 5 | `execution` | 履约与交接 | 运输与作业事件、数量、交接凭证 |
| 6 | `exceptions` | 异常与变更 | 异常案件、影响检查、处理与确认记录 |
| 7 | `settlement` | 费用与结案 | 应收应付、争议费用、结算与结案条件 |

顺序即上表，不得重排；`key` 进前端配置表，顺序与 key 由静态契约断言守住（§5）。

### 2.2 槽位 ≠ 表 ≠ 成果类型 ≠ 接口

- 一个槽位可以读**多个**业务对象；同一个附件可以关联**多个**成果。
- 接口口径：**先给一条单委托工作台聚合查询**，返回七槽位摘要（每槽四字段 + 计数），详情按需加载。**不要**为每槽各建一套 CRUD。
- 后端负责**权限、状态、可执行动作**；前端负责展示与跳转。

### 2.3 槽位 ↔ 数据落点映射（补上 DR-0010 缺的那句）

| 槽位 | 主要数据落点 |
| --- | --- |
| `overview` | 委托本体 + 客户 + 服务主体 + 货物 + 路线 + 时间 + 负责人 |
| `plan_tasks` | 方案版本、运输段、任务、前置条件 |
| `procurement` | 供应商/船东报价、比价、采购确认、**内部成本** |
| `customer_contracts` | 对客报价、客户接受、合同版本、签署证据 |
| `execution` | 里程碑、数量/状况记录、交接凭证、对账差异 |
| `exceptions` | 异常案件、阻断影响、变更提案、决策与已应用版本 |
| `settlement` | 应收、应付、附加费、争议、结算与结案清单 |

> 内部成本只进 `procurement`，且**不得**出现在客户侧投影（白名单投影口径不变）。

### 2.4 附件 = 共享证据能力，**不占槽位之一**

- 提供**统一材料入口**（上传/查看/关联），材料关联到各槽位的任务与成果。
- 先前 A 方案把附件独立占一槽、并把「采购与报价」「对客方案」合并——**一并废弃**：合并会削弱「内部采购」与「对客承诺」的分离，而分离是本支线的核心约束。

### 2.5 四个派生字段的推导规则（最低规则，直接可写）

| 字段 | 口径 |
| --- | --- |
| 当前成果 | 有效业务版本；多个成果时显示摘要与数量 |
| 未决问题 | 缺项、待确认、失效成果、阻断条件、未关闭异常 |
| 下一责任方 | 下一项可执行／待响应任务的责任人或责任角色 |
| 最后更新 | **相关业务记录的最近更新时间**，不是页面刷新时间 |

注意：`确认装卸费承担方` 按上下文落到**采购**或**对客方案**相关任务，不因含「费用」二字就一律归到 `settlement`。

### 2.6 空值四态（禁止一律显示「待补充」）

| 态 | 含义 |
| --- | --- |
| 暂无记录 | 该槽业务上确实还没产生记录 |
| 尚未分配 | 有需求但还没有责任人 |
| 不适用 | 本单业务上不需要（如无附加费） |
| 信息缺失 | 应有但缺失／未同步 |

### 2.7 Agent 入口判据（**删除**「恰好两个槽位有 Agent 入口」）

- 按钮是否出现 = `该动作已有实现` ∧ `专业能力已启用` ∧ `用户有权限` ∧ `当前上下文满足要求`。
- 一个专业可服务多个槽位（「方案与采购 Agent」同时服务 `plan_tasks` 与 `procurement`）。
- 验收断言改为：**每个出现的入口都对应真实动作与正确作用域**；而不是数槽位个数。
- 相应地，DR-0010 原第 3 条验证（「恰好 2 个槽位出现 Agent 入口」）**作废**。

### 2.8 首版人工落点要求

- 可以分 PR 实现，但**首版验收时范围内槽位必须有可用人工操作**（编辑、记录、确认）。
- 「跳到后续开放」**不能**作为验收完成；开发中暂缺的能力必须显式标注为未完成项。
- 没有 AI 的槽位仍应能人工编辑、记录、确认。

## 3. DR-0011 修订后口径（修正版 B）

### 3.1 分开建模「页面层级」与「导航边」

现状问题：`parents` 同时表示**界面层级**（用于算链深）与**所有来路**（用于校验导航边）。于是产品上合理的工作台↔会话双向切换，在链深计算里变成环 → `Infinity`。

修订后：

```js
// ① 层级：只表达「静态上可以从哪一层进来」，用于 chainDepth()。必须无环。
ROUTES[p].parents = [...]                       // 不改字段名，语义收窄为「层级」

// ② 导航边：所有真实可达的调用关系，每条带策略。
NAV_EDGES = [
  { from: 'pages/entrust/workbench/workbench',
    to:   'pages/assistant/assistant', strategy: 'push' },
  { from: 'pages/assistant/assistant',
    to:   'pages/entrust/workbench/workbench', strategy: 'reuse' }   // 不再造成环
]
```

- `chainDepth()` **只看 `parents`**（或等价地只看 `strategy === 'push'` 的边）。
- 导航边校验改看 `NAV_EDGES`，与层级解耦。

### 3.2 边的策略枚举

| 策略 | 语义 | 是否增加栈深 |
| --- | --- | --- |
| `push` | 正常进入下一级 | **+1** |
| `replace` | 明确允许替换的同级页面 | 0（替换） |
| `back` | 返回栈中已有页面 | 0（出栈） |
| `reuse` | 目标已在栈中且上下文相同，复用并刷新 | 0 |
| `reset` | `switchTab` / `reLaunch`，重置栈 | 归 1 |
| `switchTab` | tabBar 页 | 归 1 |

### 3.3 环的判定规则（关键修订）

- **`push` 图必须无环**：`A --push--> B --push--> A` 才可能持续压栈，判为错误。
- **经 `back` / `reuse` / `replace` 的往返不算环**：正常工作台↔会话切换必须被允许。
- `kind`（`tab`/`root`/`detail`）**不再被当成自动清栈**：清不清栈由**实际调用的导航操作**决定，不由页面类别决定。

### 3.4 运行期导航策略链（替代「接近上限就 redirectTo」）

按序处理，命中即停：

1. **目标已在栈中且业务上下文相同** → 返回／复用，并**刷新目标成果**；
2. **正常进入下一级、预算允许** → 正常压栈；
3. **声明为可替换的同级页面** → 保存必要上下文后替换；
4. **涉及未保存编辑** → 先保存或提示处理，**不静默卸载**；
5. **仍无法安全进入** → 给出明确提示 + 「返回工作台」操作。

**明确禁止**：把 `redirectTo` 作为所有页面的通用默认动作（现状是 `depth >= 9` 就退化 `redirectTo`）。替换必须**由声明允许**，而不是由深度自动触发。

### 3.5 上下文复用键

页面复用**不能只比较路径**：同一个成果详情页可能分别显示两张委托。复用键为：

```
页面路径 + 委托 ID + 必要的任务／成果／会话 ID
```

键不等 → 不复用，走压栈（或声明为 replace）。

### 3.6 目标页入口守卫（深链校验必须落在目标页）

`go()` 内部校验之外，**冷启动或外部进入**时目标页仍需在 `onLoad` 执行入口守卫，检查：

1. 参数是否合法（**非空** + 类型／枚举）；
2. 是否登录及有访问权；
3. 成果、任务、会话**是否归属所给委托**；
4. 是否需要选择组织或恢复上下文。

两点口径，避免过度拦截：

- 「缺少上次选择的组织」**可以进入选择流程**，并非必须禁止该页深链；
- `deepLink = deny` **不能**代替服务端授权（前端拦截只是体验，授权必须在服务端）。

### 3.7 预算口径

- 保留 `STACK_BUDGET = 8` 作为**项目预算（策略）**，`MAX_STACK = 10` 是平台硬限。
- 但**预算必须真的被运行期用到**（现状 `STACK_BUDGET` 运行期零引用，见 §1.4 ⑤）：运行期在 `depth >= STACK_BUDGET` 时进入 §3.4 的策略链，而不是直接压栈。
- 承认：把临时页面留在声明之外、再预留两层，**并不能保证**实际栈安全；所以策略链 + 入口守卫 + 行为测试三者必须同时存在，不能只留声明。

> 引入 `deepLinkOnly` 表达这一区别，避免按字面 required 把内部调用一并拦掉。

> **实现时的又一处微调（ENT-019 记录）**：接入页面时发现 §3.4 的字面顺序在**已声明语义**上执行不出来，

> ③ "未保存编辑"只在**声明式替换**与**预算耗尽**两处拦截（`push` 不卸载当前页，编辑没丢，弹窗只会训练用户盲点确定），
> 并让 `confirm-unsaved` 携带 `afterConfirm`（用户放弃编辑后该执行的那个计划；预算耗尽时它是 blocked，
> 页面必须如实说"进不去"）。三条**不改变 HO 的策略链语义**，只是把它落到能执行的位置。
>
> **ENT-019 的实际验收边界（不得夸大）**：`MIGRATED_PAGES` 只含两个委托页，
> 即运行期治理覆盖 **2/17 页**；A3/A4 在 Node 侧已覆盖（循环 20 次栈深 ≤3、复用键含委托 id），
> **真机走查与栈深实测仍为 `not-run`**。
