## 0. 结论摘要（TL;DR）

- **本计划是对原 PRD 首版范围的调整提案，不是对首版的重新定义。** 原 PRD 把全部 REQUIRED 与 M0～M5 定义为首版要求；其中"先证明报价闭环"是**开发顺序**，并没有把首版范围自动缩减为该闭环。本文档提出的缩减范围命名为 **R1 首个可用增量**，并在 2.4 节列出它与完整首版的差异。
- **为提前验证业务价值、减少同时建设的功能面，建议将完整首版拆为若干可验收增量。**（本文档不对"完整版能否在一个版本内交付"下结论——没有人员投入、工作量拆解与依赖估算，无法作出该结论。）
- **R1 采用"单条纵向闭环 + 两个 Agent 专业"策略**：客户提交委托 → 经理认领 → 上传报价并解析 → 人工修正 → 生成对客报价并定版发布 → 客户按定版确认 → 履约事件记录 → 结算结案。**整条链路必须能在无模型 / 无 API Key 的情况下跑通**（AC-06），AI 只做增强。
- **专业能力覆盖明确为 2／5**：仅开放 AG-01 委托助理、AG-02 方案与采购；其余三个业务槽位提供**完整的人工操作路径**，无 AI 能力的槽位不显示 Agent 操作。通用会话壳可完整交付。
- **UI-06 必须具备基本表单编辑能力**（不是只读）：报价字段可编辑、对客报价可人工组装、合同草稿业务字段可核对修正、保存产生新 revision、聊天卡与工作台同步显示同一 revision。版本对比先用字段变化清单。
- **验收不再按"整项延后"拆批**：24 项 AC 在 R1 完整验证，2 项（AC-12 变更传播、AC-13 依赖语义）部分验证并逐条列出本期子用例与延期子用例。验收表拆为**范围状态**与**执行结果**两个独立字段，`not-run` 只表示未执行验证，不代表功能已批准延期。
- **排期只定义执行顺序**：本文档给出阶段顺序、前置依赖、可并行条件与出口标准，**不给出工期、工作周数或日历排期**。日历排期需在资源假设（工作量、人员／代理可用性、并行条件、环境依赖）确认后另行编制。

### 1.1 需求文档解读：规模与硬约束

需求文档是一份**实现级规格**（Implementation-ready），不是概念稿。

| 维度 | 文档给出的量 | 对计划的影响 |

| 验收项 | AC-01 ～ AC-26 共 26 条 | 拆为"范围状态 + 执行结果"双字段，见 7.1 |

**必须原样继承的硬约束**（会被验收逐条核对，任何环节都不得绕过）：

1. **不夸大能力**：首版不承诺承运、不订外部舱位、不签合同、不付供应商、不报关（第 0 节）。
2. **业务真真相位**：模拟支付返回成功**不能**当作资金已收（5.6）；选中的报价**不等于**已订舱（5.3）；草稿文本**不等于**已签合同（5.4）；内部经理复核**不等于**客户已确认（5.4）。
3. **区分三种来源**：用户上报 / 经理举证 / 集成回执，必须分标签（5.5、7.3）。未经验证的路径与运力必须显式区别于集成确认（AC-26）。
4. **未知就是未知**：未知值保持 null，**绝不允许静默变成 true 或 0**（5.1）。硬性检查不能被聊天、"通用完成"或管理员界面绕过（5.2）。未知的检查不等于通过。
5. **版本与并发**：可变聚合带 revision；已确认/已发布版本不可变；命令带 `expected_revision`，过期返回 409（6.2）。
6. **权限不是 UI 隐藏**：`ENTRUST_ENABLED` 开关与服务端权限相互独立，"UI 隐藏不是访问控制"（9.2）。
7. **每一步都要有证据**：AC-01～AC-26 需给出 pass/fail/not-run + 确切命令 + 有界证据；MySQL 未跑过就要如实写未执行。

## 1. 输入材料分析

### 1.1 需求文档解读：规模与硬约束

需求文档是一份**实现级规格**（Implementation-ready），不是概念稿。

| 维度 | 文档给出的量 | 对计划的影响 |
| --- | --- | --- |
| 界面 | UI-01 ～ UI-08 共 8 个页面/组件 | 按增量分批交付 |
| 工作流 | WF-01 ～ WF-08 共 8 个作业区 | 作业区是"互联区域不是强制线性向导"，可按闭环切 |
| Agent | AG-01 ～ AG-05 五个专业 | 同一模型网关可实现全部五个，但**验证成本**不同 |
| 数据模型 | 16 个逻辑聚合 | **R1 全部保留**（前 12 个完整建模，后 4 个轻量实现）；物理表可合并，逻辑对象与引用关系必须清楚 |
| 验收项 | AC-01 ～ AC-26 共 26 条 | 拆为"范围状态 + 执行结果"双字段，见 7.1 |
| 里程碑 | M0 ～ M5 六个 | R1 覆盖 M0～M3 与 M4 最小子集，M5 为交付加固 |

**必须原样继承的硬约束**（会被验收逐条核对，任何环节都不得绕过）：

1. **不夸大能力**：首版不承诺承运、不订外部舱位、不签合同、不付供应商、不报关（第 0 节）。
2. **业务真真相位**：模拟支付返回成功**不能**当作资金已收（5.6）；选中的报价**不等于**已订舱（5.3）；草稿文本**不等于**已签合同（5.4）；内部经理复核**不等于**客户已确认（5.4）。
3. **区分三种来源**：用户上报 / 经理举证 / 集成回执，必须分标签（5.5、7.3）。未经验证的路径与运力必须显式区别于集成确认（AC-26）。
4. **未知就是未知**：未知值保持 null，**绝不允许静默变成 true 或 0**（5.1）。硬性检查不能被聊天、"通用完成"或管理员界面绕过（5.2）。未知的检查不等于通过。
5. **版本与并发**：可变聚合带 revision；已确认/已发布版本不可变；命令带 `expected_revision`，过期返回 409（6.2）。
6. **权限不是 UI 隐藏**：`ENTRUST_ENABLED` 开关与服务端权限相互独立，"UI 隐藏不是访问控制"（9.2）。
7. **每一步都要有证据**：AC-01～AC-26 需给出 pass/fail/not-run + 确切命令 + 有界证据；MySQL 未跑过就要如实写未执行。

## 2. R1 首个可用增量定义

### 2.1 一句话定义

> **R1 = 让一位货代经理，从客户提交的一单委托出发，用"上传报价 → 解析 → 人工修正 → 出对客报价 → 客户按定版确认 → 记录履约事件 → 结算结案"这一条纵向闭环，把真实业务数据落进真实数据库，全程可无模型跑通，且对话与工作台看到的是同一份对象和同一版号。**

**可验收的最小闭环（12 步）**

1. 客户在货主端创建并提交委托（草稿可先不完整）
2. 经理在工作台认领（原子操作，双认领不覆盖）
3. 经理上传一份纯文本船东报价
4. Agent 解析出结构化字段，**带来源引用**，并列出缺项
5. 经理在 UI-06 表单中人工修正一个费率/费用包含项，保存产生新 revision
6. 工作台与聊天卡同时显示更新后的**同一 revision**（无重复成果）
7. 经理组装对客报价并**发布定版**（生成不可变快照）
8. 客户接受**该精确版本**，内部成本不可见
9. 记录履约里程碑与交接事件，含来源标签
10. 出现一次缺件 → 生成 waiting 任务（不是硬报错）
11. 记录应收/应付与一笔争议附加费，争议排除在确认总额外
12. **经理人发起结案，服务端检查**任务、必要交接材料、阻断异常、结算与未清余额处置条件 → 结案；再以带原因的 reopen 验证历史完整保留

### 2.2 范围裁剪表

| PRD 项 | R1 | 说明 |
| --- | --- | --- |
| REQUIRED：客户旅程 | **部分** | 草稿/提交/查看/接受或拒绝精确版本/差异确认 ✅；变更走**简版记录 + 五类影响标记**（无完整图谱） |
| REQUIRED：经理工作空间 | **部分** | 主助手 + 抽屉 + 专业会话 + 委托工作台 ✅；总览工作台**简化版** ✅；**专业能力覆盖 2／5** |
| REQUIRED：工作流 | **部分** | 任务/前置/负责人/到期/人工完成/reopen ✅；依赖**只支持固定前置条件 + 自依赖与循环检查**，不声明支持通用 Dependency；图形化 DAG 编辑延后 |
| REQUIRED：成果物 | **部分** | 方案（轻量）/报价/对客报价/合同草稿与证据/采购记录/交接/结算 ✅；异常与变更**轻量实现**，不独立成页 |
| REQUIRED：Agent 行为 | **两个专业** | AG-01 委托助理、AG-02 方案与采购 ✅；**AG-03/04/05 延后，对应业务提供完整人工完成路径** |
| REQUIRED：文档 | **完整** | 上传/存储/授权下载 + **文本、CSV、文本型 PDF 提取** + 手工转录降级 ✅（扫描件不做 OCR）|
| REQUIRED：治理 | **完整（不可裁）** | 组织与委托隔离、命令作用域、revision 校验、已接受快照不可变、审计、内外可见性 ✅ |
| REQUIRED：运营 | **完整（不可裁）** | 人工确认记录 + 证据；区分"待请求/已录入确认/已验证集成回执" ✅ |
| OPTIONAL | **不做** | 语音输入、扫描 OCR、推送通道、供应商自助确认链接 |
| DEFERRED | **不做** | 报关、电子签、真实支付与分账、AIS/船闸/港口集成、自动外部采购、全国路径优化、融资与可转让电子提单 |

**不可裁剪清单（R1 的底线）**：治理（权限/隔离/版本/审计）、运营真真相位（三来源标签）、无模型可跑通、空/错/过期/无权限态可操作、**经理人完成真实业务所需的基本编辑与确认入口**。这五项一旦妥协，R1 就失去了"可验收"的属性。

### 2.3 明确不做（Out of Scope）

- ❌ 自动多式联运编排与全国路径优化
- ❌ 真实承运承诺、订舱、外部运力采购
- ❌ 电子签、真实资金流转、与模拟支付服务打通
- ❌ 变更影响传播图谱与独立变更页面（R1 用字段→成果类型映射替代）
- ❌ 图形化依赖编辑器、通用 DAG 语义
- ❌ 高级版本差异界面（R1 用字段变化清单）、智能对账分析、高级运维能力
- ❌ 生产部署、对外真实消息、自动合并主干

### 2.4 R1 边界：可以推迟 vs 必须保留

| 可以推迟 | R1 必须保留 |
| --- | --- |
| 三个后续专业 Agent（AG-03/04/05） | 相应业务的人工完成路径 |
| UI-08 的**完整影响清单**与「应用变更」（A2） | 简版异常／变更记录、确认与影响标记（**已独立成页**，见 3.x UI-08 行） |
| 图形化依赖编辑 | 已开放依赖的基本合法性检查（自依赖、循环） |
| 高级版本差异界面 | 基本编辑、版本保存、确认绑定 |
| 复杂多段优化 | 当前支持运输段的稳定对象与关联 |
| 智能对账分析 | 应收应付正确性、争议处理、结案检查 |
| 高级运维能力 | 当前 worker 的恢复、幂等和人工接管验证 |

> R1 与完整首版的差异即上表：R1 削减的是**专业能力与界面复杂度**，保留的是**经理人完成真实业务所需的基本操作与验证**。

## 3. 技术实现方案（R1 必需部分）

### 3.1 架构落位

- **保持模块化单体**，不引入重型工作流平台（需求 7.5 明确禁止为这个里程碑上重武器）。
- 新增命名空间 **`/api/v1/entrust`**，复用现有模型网关与组件。
- **不修改基线端点语义**去把经理伪装成货主（9）。
- 新增能力清单接口供小程序读取，配合 `ENTRUST_ENABLED` 开关。

```
miniapp/                     — 复用 pages/assistant 壳体；新增 manager/* 工作空间路由
backend/app/modules/entrust/ — 组织/委托/任务/成果/附件/会话/作业/财务
backend/app/modules/entrust/jobs/ — DB 作业表 + worker（至少一次投递 + 幂等副作用）
backend/alembic/             — 若基线无迁移机制则引入最小可用迁移
```

### 3.2 数据模型：16 个逻辑聚合，R1 全部保留

> **修正说明**：本表实际为 **16 个逻辑聚合行**（原 v1.0 误写为 15 个、"12＋3"）。R1 **不按聚合数量削减工作量**——物理表可以合并，逻辑对象和引用关系必须清楚；使用有类型校验的成果载荷也可以，不必为了满足表格而机械建很多表。

**前 12 个（完整建模）**

| 聚合 | 关键字段要点 |
| --- | --- |
| OperatingOrganization / Membership | 组织身份、用户、角色、启用状态；**禁止公开自助提权** |
| Assignment | 服务主体/客户/经理、范围与货物事实、日期、状态、revision、财务状态 |
| AssignmentAccess | 协作权限与显式参与关系（owner/editor/viewer）|
| WorkflowTask / Dependency | 类型、负责人、状态、到期、**固定前置条件**、所需证据、执行代次（lease）|
| Artifact / ArtifactRevision | 通用注册表、kind、可见性、当前版本、基版本、待重新核对标记 |
| Attachment | 归属（组织/委托 或 私有未绑定）、文件名/类型/大小/哈希、存储键、提取状态与来源 |
| Conversation / Message | 作用域、专业、任务绑定、角色/内容、成果引用；**归档 ≠ 业务删除** |
| AgentJob / ActionProposal | 发起人、上下文版本、状态、尝试次数、允许动作、结果与确认绑定 |
| Supplier / SupplierQuoteRevision | 对手方身份、报价条款、范围、有效期、来源、确认状态 |
| Procurement / ResourceReservation | 选中报价/版本、请求与确认证据、容量/时间窗与处置 |
| CustomerOfferRevision / ContractRevision | 结构化客户事实、渲染内容、来源版本、发布/接受/证据状态 |
| AuditEvent / IdempotencyRecord | 操作者与角色、命令、目标/版本、前后引用、结果、原因、关联键 |

**后 4 个（R1 轻量实现，但不能只靠标签和勾选框承担业务含义）**

| 对象 | 第一阶段最低保留内容 |
| --- | --- |
| 运输段 | 稳定 ID、方式、起终点、时间窗、执行方、关联任务与版本依据 |
| 交接记录 | 关联任务、数量与单位、事件时间、来源、证据、更正关系 |
| 异常／变更 | 原因、影响对象、负责人、处理决定、状态与证据 |
| 结算 | 应收／应付行、争议状态、确认版本、收付证据、结案条件 |

**建模红线**：不得把有业务后果的事实只存成不透明的聊天大字段（8）。附件二进制存于公共静态路径之外，20 MiB 上限可配置，文件名安全化，禁止执行上传内容（8）。时间戳统一约定时区、界面显示 Asia/Shanghai，**来源事件时间与上传/记录时间分开保存**（8）。

**结案不是勾选**：经理人发起结案，**服务端检查**以下条件后才能置为已结案——
1. 所有必需任务处于终态；
2. 必要交接材料齐备；
3. 不存在阻断性异常；
4. 结算已复核、未清余额已有处置决定。

### 3.3 最小接口集（R1）

| 分组 | R1 能力 |
| --- | --- |
| 组织 | 列出可选服务主体、当前成员关系、授权路由 |
| 委托 | 草稿/创建/列表/详情/编辑/提交/认领/改派；客户与经理两套投影 |
| 任务 | 创建/编辑/列表/状态流转/接管/reopen/改派；固定前置条件的合法性校验 |
| 成果 | 创建草稿、版本列表/详情、**表单编辑**、复核、发布、**精确版本客户接受**、字段变化清单 |
| 报价/采购 | 录入/解析/对比、选中、请求、确认（含证据）；过期报价不得支撑新的确认采购 |
| 附件 | 上传、授权下载、**文本/CSV/文本型 PDF 提取**作业与状态、私有草稿绑定到委托 |
| 会话 | 创建/列表/消息/归档、任务绑定、专业选择（仅 2 个开放专业）|
| Agent 作业 | 提交/查询/重试/取消；校验后的成果提案与动作卡 |
| 工作台 | 组合视图与单委托投影（来自权威记录）|
| 事件/财务 | 事件记录与更正；财务行、差异、结算复核与批准、**有证据的收付记录**、结案校验 |

所有有后果的命令请求体携带 `expected_revision` + `idempotency_key` + 精确目标/版本。统一 403/404 不泄漏授权信息、409 版本冲突、422 字段错误、模型错误可恢复（9）。列表分页，避免 N+1。

### 3.4 Agent 运行时（R1 只开放 2 个专业）

- **五个专业共用同一个模型网关**，不做微调、不做多模型集成、不做自治群聊、不新增向量库（7.1）。
- **持久化作业表 + worker 即足够**。作业支持有界重试、超时、租约过期恢复、取消与尝试日志（7.5）。
- 输出必须通过**类型化 Schema 校验**，最小信封：

```json
{
  "assignment_id": "…或未绑定草稿为 null",
  "task_id": "…或 null",
  "base_revision": 7,
  "summary": "中文简述",
  "artifact_proposals": [],
  "missing_fields": [],
  "findings": [],
  "source_refs": [],
  "proposed_actions": [],
  "requires_review": true
}
```

- **确定性 fixture 模式是 CI 的硬要求**。真实模型路径必须实现；若凭证已具备则跑一次有限冒烟，**未跑过就要如实报告"质量未验证"**（7.5）。
- **输出校验失败等于不做业务变更**（AC-08）；类型错误、缺必填、编造来源都要被拒或标记。错误字段或虚构来源**不能形成已确认业务事实**。
- 附件是**不可信数据**：其中的指令不能改权限、不能调工具、不能跨租户、不能授权付款（7.2 / AC-18）。
- 上传文档、模型提案、确定性计算三类输出必须在 UI 上标注不同来源，**不得把确定性操作标成 LLM 推理**。

### 3.5 特性开关、迁移与数据可升级

- 新增 `ENTRUST_ENABLED`：关闭时保留原预览行为并隐藏经理入口；开启时所有必需流程必须是**真的**。
- **开关与服务端权限相互独立，UI 隐藏不是访问控制。**
- 若基线无迁移机制，引入一个**最小文档化的迁移机制**；不要指望 `create_all` 升级已有表（9.2）。
- 迁移非破坏、新增表优先；提供开发数据集的备份/恢复指引；关闭特性只隐藏访问，**不删除记录**。
- AC-25 要求：既有基线数据能无损升级，且升级库与干净库都能跑。

### 3.6 变更影响与依赖：最小处理规则（R1 必须存在）

**问题**：R1 允许经理人修改时间窗、选择新报价、确认附加费。若只实现"货量、起终点"两类影响传播，会出现——客户把装货日期推迟三天，原船期和报价已失效，但旧对客方案仍显示有效。**即使 R1 只有一艘船、一段水运，这个问题也会发生。**

**对策：保留原 PRD 五类关键变更的最小处理规则**（不需要图谱或独立页面）：

| 关键变更 | 触发的待重新核对 |
| --- | --- |
| 货量／货类 | 运输段容量、报价、对客方案 |
| 起终点／运输方式 | 运输段、路径与报价 |
| 装货与交付时间 | 船期、报价有效期、对客方案 |
| 供应商／选中报价 | 采购记录、成本、对客方案 |
| 已批准附加费 | 结算行、对客报价总额 |

**实现方式**：字段 → 成果类型的简单映射表，生成
1. 受影响成果打上 **"待重新核对"** 标记；
2. 自动生成**待办任务**；
3. **阻止失效成果被继续确认或执行**（服务端校验，不是仅 UI 提示）。

**依赖关系同理**：
- 图形化 DAG 编辑**延期**；
- R1 **只支持固定前置条件**，模型与界面都按此限制实现，**不声明支持通用 Dependency**；
- 只要允许录入依赖，**自依赖与循环检查必须存在**（AC-13 本期子用例）。

### 8.1 v1.5 新增工程纪律（防复发）

**① squash 合并必须显式指定提交信息。** GitHub 对**只有一个提交**的 PR，squash 时默认用**该提交自身**的标题与正文，而不是 PR 标题。走「换 tree 落基」的分支会被压成单提交 → develop 上出现`rebased onto develop <sha>` 这种无意义提交，丢失 Conventional Commit 与需求编号。**#63 / #64 / #65 实际如此**（#61 / #62 走 `update-branch` 保留了多提交所以正常）。已合入的历史**不得改写**（禁止改写共享分支历史），故仅登记为 **cosmetic debt**：#63 / #64 / #65 三条提交主题不携带需求编号，追溯需查 PR。此后一律显式传 `commit_title` / `commit_message`（#66 / #67 / #68 已照办，主题正常）。

**② 本地预演门禁的范围必须逐字对齐 `ci.yml`。** 本地若用 `ruff format --check .` 而 CI 是 `ruff format --check app tests`，就会出现「**本地红、CI 绿**」的假警报（本案：`backend/scripts/` 下4 个历史文件）。这类假警报会训练团队怀疑门禁 —— 与 DR-0004 要防的「随机变红」是同一种危害。**出现本地红 / CI 绿，先怀疑范围不一致，而不是先怀疑工具链。**

**③ 权限判定必须指定组织作用域。** `AccessContext.can()` 不传作用域曾退化为「跨组织并集判定」，产生**真实越权**（见 DR-0008）。现在**两个作用域都不给 → `ValueError`**。把约束交给运行时，而不是靠「记得传参数」；新增任何权限判定点时，作用域是**必填项**。

**④ 门禁范围的判定标准是「是否在 CI 执行路径上」，不是「是不是生产代码」。** `backend/scripts/` 虽非生产代码，但 `frontend-e2e` job 会执行 `seed_demo.py` —— 它确实是 CI 会跑的代码，因此纳入 ruff 门禁（DR-0007）。`mypy` 的排除是**显式决策**（已写进 DR 与 `ci.yml` 注释），**不是漏配**。

**⑤ 换基底用 `git reset --soft`（本机零风险手法）。** `git reset --soft <新基底>` 只移动 HEAD，**不触碰索引与工作区**：当「换 tree 换来的 squash 提交」与目标提交 **tree 相同**时，reset 后索引即新基底、工作区即「新基底 + 我的改动」，`git add -A && git commit` 即得干净提交。**前置校验：两个 tree sha 必须相等**，否则中止。这条路不依赖 `rebase`，也不触碰工作区。
