## §3 HO 点名的三处证据口径 —— 逐条给代码证据

HO 在《近期HO 决策：阻塞项与待定调清单决策列表》开头写明要"先纠正三处会影响决策的证据口径"。
这三条我逐条到代码里核，结论如下。

### 3.1 "⑧b 19/19 不能作为完整点击链路通过"（要求**调整统计**，不只是补一句说明）

**已修，而且修在结构上，不是修在措辞上。**

- 未开支付开关时，⑧b 走 `w.rep.not_run(...)`（`:2809`），**不再**走 `rec(..., True, ...)` ——
  源码里那条注释直接写明："⚠️ 且必须走 `not_run()` —— 曾写成 `rec(..., True, ...)`，
  汇总里与真通过**长得一模一样**（HO 2026-09-15 点名要求修正）"（`:2807-2808`）。
- 弹层点击那一条走 `w.rep.limitation(...)`（`:2960` 附近），注释写明"本条**不计入通过**"。
- `rec()` 的 docstring 现在带警告："⚠️ **不要**再用它记「未执行」或「限制」——那是把非通过
  写成通过的经典错法"（`:654`）。
- 分档与退出码：`NON_PASS = (FAIL, ENV_BLOCKED, REVIEW_REQUIRED, NOT_RUN, LIMITATION)`（`:620`），
  `return 0 if verdict == Reporter.PASS else 1`（`:4272`）。

⇒ 最近一轮 `walk-20260916-022603` 的 `tally` 是 `PASS 417 / FAIL 0 / LIMITATION 4`、
`verdict=NOT_RUN` —— **限制没有被算进通过数**，整体判定也没有被写成通过。

### 3.2 "复用路径 1/1 成功"不能表述为稳定

`decisions/0009` §"仍然不同的那一半"前后现在写的是：
"**已做过一次对照实测（各 1 样本）**……⇒ **否掉了'代理是主因'这个猜测**"
（`:614-617`），并且把现象定性为"**新起**的实例注册不稳定（本轮 2/2 失败；历史上也有过成功）、
而**复用已在运行**的实例 1/1 成功 ⇒ 处置仍以'先探测、优先复用'为准"（`:617-618`）。

⇒ 表述是"**有可用缓解**"，不是"已证明稳定"。**无需改动**。
（另：HO 要求的恢复边界"不得默认关闭 HO 的其他 IDE 实例"已实现，见 §2 H4/D2。）

### 3.3 "MySQL 已由 CI 覆盖"必须限定对象

**已满足，且范围可以写得更宽。** 精确口径：

`pytest-mysql` job 覆盖 11 项 = 迁移落定 / 基线建表 / **双认领竞争** / 乐观锁并发编辑 /
幂等并发副作用恰好一次 / 五个模块的时间戳渲染 / **Agent 作业三条并发锚点**
（双 worker 竞争同一作业、租约过期接管、旧 worker 迟到写入作废）。

⚠️ 但要说清两件事：
1. **SQLite 结果不能替代 MySQL 锁正确性**（这条纪律在 CI 注释与测试模块头部都写着）；
2. 上面这 11 项**不等于**"MySQL 上的所有行为都已验证"——未覆盖的部分仍按 `not-run` 记。

### 3.4 自纠：我自己在这一轮误判过一次（留档）

我最初拉 `gh api .../actions/jobs/{id}/logs`，看到三个 H7b 用例名**出现 0 次**，
就倾向判断"它们被 deselect 了"。**这是误判**：那一处 pytest 输出是**点号格式**
（`tests/test_mysql_integration.py ...........`），用例名根本不会逐行出现。

**正确判据**是三条合起来：① `collected 691 items / 680 deselected / 11 selected`；
② 该行有 **11 个点**；③ 模块的 `def test_` 恰好 **11 个**且模块级 `pytestmark` 含 `mysql`。

⇒ 教训：**"名字没出现"不等于"没执行"**。用"选择/通过计数"判执行，别用"字符串是否出现"判执行。

### 9.1 执行过程中触发的本机故障（留档）
